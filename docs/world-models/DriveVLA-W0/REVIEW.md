## What it is

DriveVLA-W0 (ICLR 2026) is not a standalone world model — it is a **training recipe for a driving VLA in which future-image prediction is an auxiliary loss**. The backbone is Emu3, an 8B decoder-only multimodal transformer (`hidden_size: 4096`, 32 layers, vocab 184622 with VQ image tokens inline), finetuned to emit interleaved vision-action-vision-action ("VAVA") sequences; the model predicts the *next frame's VQ tokens* at `vision_loss_weight: 0.5` while a small action expert (`hidden_size: 1024`) predicts the trajectory. Three action-head variants are provided — autoregressive FAST tokens, flow matching (Pi0-style, `action_sample_steps: 10`), and a query/anchor head over 8192 clustered trajectory anchors — and the paper's claim is that the world-modelling loss is what lets performance keep climbing as data scales. Output is 8 future poses x 3 dims; evaluation is NAVSIM PDMS, where they report 90.2 with one camera and 93.0 with a test-time-scaled variant. The images it "predicts" are VQ code grids of 18x32, i.e. **256x144 pixels** — this is a supervision signal, not a renderer. The README states outright: "Due to company policy, only the reviewed part of our codebase is available."

## Security findings

- **No licence is itself the top finding.** Running unlicensed weights in a commercial pipeline is a legal exposure, not a technical one, but it is the reason nothing else here matters much.
- `trust_remote_code=True` at `utils/datasets.py:90,91,95`, `inference/vla/inference_action_navsim_flow_matching_vava.py:124`, `inference/vla/inference_action_navsim_ar_vava.py:106,149`, `inference/vla/inference_action_navsim_query_based_vava.py:124`, `inference/vla/inference_action_navsim_with_previous_action_last_VAVA.py:98,109,112`, `inference/qwen/inference_action_navsim_vava.py:234`, `models/tokenizer/emu3_tokenizer_navsim.py:205`, `utils/train_pi0.py:121`, `utils/train_qwen_vla.py:135,155`. Every one of these will execute Python fetched from a Hugging Face repo. It is unavoidable with Emu3 (its processor is remote-code), but it means the trust boundary is "whatever BAAI and the DriveVLA authors push", not "whatever we downloaded".
- **A published `.pkl` is the dataset format.** `navsim_emu_vla_256_144_test_pre_1s.pkl` is downloaded from HF per the README and unpickled at `utils/datasets.py:52`, `inference/qwen/inference_action_navsim_vava.py:110`, `inference/vla/inference_action_navsim_with_previous_action_last_VAVA.py:86`, `tools/pickle_gen/pickle_generation_navsim_pre_1s.py:28,61,233`, `check_pickle_paths.py:10` and about eight other places under `tools/`. Unpickling a downloaded artifact is arbitrary code execution. Regenerate it locally from NAVSIM with `tools/pickle_gen/` rather than downloading, or at minimum inspect it with `pickletools` first.
- `inference/navsim/navsim/load_va_feature.py:25` — `torch.load(vq_ckpt, map_location="cpu")`, no `weights_only`.
- `utils/datasets.py:636` — a default that rewrites paths on your behalf:
  `path_replacements = os.environ.get('VLA_PATH_REPLACEMENTS', '/mnt/vdb1/yingyan.li/repo/VLA/:/mnt/vdb1/shuyao.shang/VLA_Emu_Huawei/')`.
  If you do not set `VLA_PATH_REPLACEMENTS`, string substitution against two strangers' home directories runs on every image path in your dataset. Harmless in practice, but it is a good illustration of how finished this code is.
- **Broken as shipped:** `inference/vla/config.py:21` defines the project root as the first parent containing **both** `train/` and `reference/`. There is no `train/` directory in this repo (it was renamed to `utils/`), so `setup_paths_early()` (`config.py:38-40`) adds nothing to `sys.path`, and the flagship script's `from datasets import Emu3DrivingVAVADataset` (`inference_action_navsim_flow_matching_vava.py:17`) will resolve to the *Hugging Face `datasets` package* or raise `ImportError` — not to `utils/datasets.py`. The line above it imports `utils.train_pi0` with the package prefix, so the refactor was applied inconsistently. Anyone running `infer_navsim_flow_matching_PDMS_87.2.sh` unmodified will not get the paper's number; they will get a traceback.
- **Dependency pinning:** `requirements.txt` has five lines (`transformers==4.44.0`, `tiktoken==0.6.0`, `flash-attn==2.5.7`, `pillow`, `gradio==4.44.0`). Torch, numpy, deepspeed, scipy, wandb and tensorboard are installed by free-text instructions in the README instead. `flash-attn==2.5.7` against `torch==2.4.0` is a build that will need a matching toolchain. No lockfile.

- **Tests / CI:** zero of each. No `.github/`.

## Physics and dynamics

- **Action space.** `action_dim: 3`, `action_frames: 8` (from the shipped `config.json` of the released checkpoint). That is the NAVSIM convention: eight future poses as `(x, y, heading)` at 2 Hz, i.e. a **4-second** horizon. The normalisation statistics (`configs/normalizer_navsim_trainval/norm_stats.json`) give `mean[0] = 2.31` with `q99[0] = 6.20` for the first channel, which is consistent with *per-step forward displacement in metres* at 0.5 s intervals (≈4.6 m/s mean, ≈12 m/s at the 99th percentile) rather than cumulative displacement. Note the stats are filed under the key `"libero"` — a leftover from the LIBERO manipulation benchmark in the Pi0/OpenVLA lineage that was never renamed, and which the inference code reads literally (`inference_action_navsim_flow_matching_vava.py:148-150`). Actions are min-max normalised to [-1, 1] between `q01` and `q99` and denormalised at output.
- **Action input.** The model is also *conditioned* on 3 previous action frames (`pre_action_frames: 3`, `pre_action` tensor in the inference loop) and on a 4-way one-hot high-level command — `["go left", "go straight", "go right", "unknown"]` (`utils/datasets.py:611-616`). So there is a navigation-command conditioning channel, which is the NAVSIM standard, not a free-form trajectory input.
- **"World model" — what it actually is.** The future-prediction target is the next frame's Emu3 VQ token grid, loaded from `.npy` files shaped `(1, 18, 32)` (`utils/datasets.py:642`) — 576 tokens, decoding to roughly **256x144 pixels**, which is also what the dataset pickle's name says (`navsim_emu_vla_256_144_test_pre_1s.pkl`). The loss weight is `vision_loss_weight: 0.5` against `action_loss_weight: 1.0`. This is a representation-learning trick, not a simulator: there is no autoregressive video rollout, no multi-step horizon, no controllability over the generated future, and the generated frames are never decoded back to pixels in the inference path. Calling it a world model is defensible in the paper's framing (dense self-supervision) and misleading if you arrive expecting rollouts.
- **Frame rate and history.** Input history is 3 frames sampled at stride 2 ending at `cur_frame_idx: 3` (`utils/datasets.py:637`), on NAVSIM's 2 Hz annotated grid, so roughly 1.5 s of context — consistent with the `pre_1s` suffix on the data artifacts.
- **Cameras.** One. The paper's headline is explicitly "1x Cam" beating three-camera baselines.
- **Evaluation.** NAVSIM PDMS and its sub-scores (NC no-collision, DAC drivable-area compliance, TTC, comfort, EP ego progress), computed by the vendored NAVSIM v1.1 code under `inference/navsim/`. This is a **pseudo-closed-loop** metric: the predicted trajectory is replayed through nuPlan's kinematic bicycle model (`navsim/planning/simulation/planner/pdm_planner/simulation/batch_kinematic_bicycle.py`) against a non-reactive recorded world. It is much better than FID/FVD for our purposes — it actually scores collisions and drivable area — but the other agents do not react, so it is not a closed loop in the Isaac Sim sense.
- **Known failure modes.** Not documented upstream. Structurally: a 4 s horizon bounds anything long-range; the 4-way command vocabulary cannot express a specific route; the frozen non-reactive PDMS world hides the multi-agent interaction failures we would care about; and the VQ future-prediction signal at 256x144 carries essentially no fine geometry.

## Motion-control assessment

The mapping to Alpamayo is unusually direct — this repo is solving the same problem as Alpamayo-R1, in the same output format. Alpamayo's `ActionSpace.action_to_traj` (`src/alpamayo_r1/action_space/action_space.py:47-70`) returns `traj_future_xyz (..., T, 3)` and `traj_future_rot (..., T, 3, 3)`. DriveVLA-W0's output is `(T=8, 3)` of `(x, y, heading)`. To convert: take `traj_future_xyz[..., :2]` for the first two channels, extract yaw from `traj_future_rot` (`yaw = atan2(R[...,1,0], R[...,0,0])`) for the third, difference consecutive poses if you want their per-step convention, drop z entirely, and resample to 2 Hz. That is a strictly *lossier* format than Alpamayo's — no z, no full rotation, no roll or pitch — so the conversion is one-way: we could feed an Alpamayo trajectory into their PDMS harness, but nothing they output adds information Alpamayo does not already have.

Which is the point: **there is nothing to integrate.** DriveVLA-W0 is a competitor to Alpamayo, not a component for it. It does not render, so it cannot be a sensor layer over Isaac Sim or Unreal; it does not roll out, so it cannot be a simulator for AlpaSim; it does not model dynamics, so it cannot close a loop. What it offers is an *idea* and a *number*: adding a next-frame VQ-token prediction head at half the action loss weight, on top of a VLA that already tokenises images, reportedly amplifies the data scaling law and buys ~3 PDMS points. If that replicates, it is a cheap change to Alpamayo's training recipe — Alpamayo is already a multimodal model over camera tokens, so the auxiliary head is additive, and the ablation would cost one training run rather than a new codebase. The transferable artifacts are therefore the recipe (VAVA interleaving, `vision_loss_weight = 0.5`, nuPlan pretrain then NAVSIM finetune) and the three action-head variants (`models/policy_head/flow_matching.py`, `diffusion_policy.py`, `moe_experts.py`), which are small, readable, and worth reading as reference implementations even though we cannot copy them under an absent licence.

The second useful artifact is the vendored NAVSIM v1.1 evaluation harness under `inference/navsim/`, which is separately licensed (`inference/navsim/navsim/LICENSE`) and obtainable directly from autonomousvision/navsim. If we want a PDMS number for Alpamayo, get it from upstream NAVSIM, not from this fork.

## Extensibility

- **New dataset**: the pattern is to subclass `Emu3SFTDataset` in `utils/datasets.py` — there are already five variants (`Emu3DrivingDataset:481`, `Emu3DrivingVAVADataset:602`, `Emu3DrivingNuplan6VADataset:808`, `Emu3DrivingVAVA_AR_Dataset:962`) that differ by a handful of lines each and duplicate the rest. Adding a sixth means the same copy-paste. The input contract is a pickle of dicts with `image` (a list of paths to precomputed VQ `.npy` grids) and `action` (an array), so any dataset must first be pushed through `tools/pickle_gen/` and the Emu3 VQ tokenizer.
- **New sensor / camera**: not supported. The sequence format is one image token block per timestep; there is no view axis anywhere.
- **New action space**: `action_dim` and `action_frames` are ints passed down from `DataArguments` to the model config, so widening to 6-DoF is nominally a config change — but it invalidates the checkpoints (the action expert's input/output projections are sized by them) and the normalisation stats file has exactly three entries per statistic.
- **Config system**: a late retrofit. `inference/vla/config.py` implements env-var-over-YAML-over-defaults, `config.yaml.example` shows the shape, and the `.cursor/plans/` document committed to the repo is literally the plan for "remove hardcoding and unify configuration management" — which was evidently applied to `inference/vla/` and not to `scripts/`, `tools/` or the root-level helpers. The result is a repo that is half-configurable and half-hardcoded to two engineers' mount points.
- **Coupling hotspots**: `get_project_root()` looking for a `train/` directory that no longer exists (`inference/vla/config.py:21`); the `"libero"` key in `norm_stats.json`; `cur_frame_idx: 3` and the stride-2 slice `img_list[start_idx-2*(num_frames-1):start_idx+1:2]` (`utils/datasets.py:637`) that hard-encodes the history sampling; `VLA_PATH_REPLACEMENTS`; the vendored `reference/Emu3` tree that `sys.path` must pick up before any `emu3.mllm` import resolves.

## Hardware and cost

The only figure upstream gives is training: **8x L20 (40 GB), ~16 hours** for the NAVSIM finetune — though the nuPlan pretraining stage (`scripts/pretrain/train_nuplan_6va_multi_v0.2_worker.sh`, named `multi_node`) is clearly larger and is not costed. Inference is launched with `torchrun --nproc_per_node=8`, but that is data parallelism over the test set, not model parallelism: a single Emu3-8B copy in bfloat16 is ~16 GB of weights, so one 24 GB card should hold it with `model_max_length: 1400` and `action_sample_steps: 10`. Call it **24 GB minimum, 40 GB comfortable**, with the caveat that we have not run it and upstream publishes no per-sample latency anywhere. The flow-matching head at 10 sampling steps over an 8x3 action is negligible next to the 8B forward pass. Storage: NAVSIM plus precomputed VQ codes plus the multi-GB meta pickles; the HF weights repo is bloated with committed TensorBoard runs, a `wandb/` directory and thousands of per-token output JSONs, so clone it with `allow_patterns` rather than wholesale.

## Verdict and next step

**WATCH.** The licence situation ends the discussion for anything we would ship: there is no `LICENSE` file in the repository, no licence tag on the weights, and the README says only the internally-reviewed subset of the code was released under corporate policy. Default copyright means all rights reserved, so we cannot use the code or the checkpoints commercially regardless of how good the numbers are — and the numbers are good (90.2 PDMS from a single camera is a genuine result). Separately, the code as published cannot run: `inference/vla/config.py:21` looks for a `train/` directory that was renamed to `utils/`, so the flagship reproduction script's imports do not resolve. The next step is a reading task, not an engineering one: have whoever owns Alpamayo's training recipe read arXiv 2510.12796 and the three policy heads under `models/policy_head/`, then decide whether to run one ablation — Alpamayo with and without an auxiliary next-frame image-token prediction loss at weight 0.5 — on our own data and our own code. That is the whole value of this repo to us. If someone still wants the PDMS harness, take NAVSIM v1.1 from autonomousvision/navsim directly, where it is properly licensed, rather than from the vendored copy here. Revisit only if BraveGroup adds a licence.
