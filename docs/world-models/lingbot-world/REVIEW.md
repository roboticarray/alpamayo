## What it is

LingBot-World is Ant Group's (Robbyant) camera-controllable image-to-video world simulator: a fork of **Wan2.2 I2V-A14B** (two 14B "high noise" / "low noise" flow-matching DiT experts sharing a Wan2.1 VAE and a umT5-XXL text encoder) with a camera-control branch bolted on. The control signal is a per-frame **Plücker ray map** computed from camera-to-world 4x4 matrices plus `[fx,fy,cx,cy]` intrinsics (`wan/utils/cam_utils.py:86-119`), patch-embedded by `patch_embedding_wancamctrl` and added into the DiT token stream (`wan/modules/model.py:508-527`). Two checkpoint flavours exist: **Cam** (`control_dim = 6`, full Plücker = ray origins + directions, `wan/modules/model.py:394-395`) and **Act** (`control_dim = 7`, ray *directions only* plus four binary WASD channels, `model.py:396-397`). `generate_fast.py` runs a causal, chunked, KV-cached variant (Self-Forcing style: denoise a 3-latent-frame chunk, then re-run the model at t=0 to write the chunk into the KV cache, `wan/image2video_fast.py:659-664`) which is what the "real-time, 16 fps, sub-second latency" claim refers to. There is **no training or fine-tuning code**, no tests, no CI, and the README states in a banner that the repo is **no longer actively maintained** — development moved to `Robbyant/lingbot-world-v2` (LingBot-World-Infinity).

## Security findings

- `wan/modules/t5.py:494` — `model.load_state_dict(torch.load(checkpoint_path, map_location='cpu'))`, no `weights_only=True`. The file loaded is `models_t5_umt5-xxl-enc-bf16.pth`, an **11.4 GB pickle distributed from Hugging Face**. This runs on every inference, in both entry points.
- `wan/modules/vae2_1.py:612` and `wan/modules/vae2_2.py:882` — `torch.load(pretrained_path, map_location=device)`, no `weights_only`. Loads the 507 MB `Wan2.1_VAE.pth` pickle from the same HF repo.
- `wan/modules/animate/clip.py:519` — same pattern; dead code for this repo's purposes but still importable.
- These three are the only real exposure and they are inherited from Wan2.2. Mitigation is cheap: convert both `.pth` files to safetensors once, locally, and patch the three call sites to `weights_only=True`. Do that before running in any shared cluster.
- **Clean:** no `pickle` import anywhere, no `eval(`/`exec(`, no `os.system`, no `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens or credentials. The only `subprocess` use is `wan/utils/utils.py:72`, `subprocess.run(command, ...)` with an ffmpeg **list argv** (no `shell=True`) — safe.
- The DiT checkpoints themselves are sharded **safetensors** (verified on the Hub), which is the large-surface-area part and it is the safe format.
- `requirements.txt` — every line is a floating bound (`torch>=2.4.0`, `diffusers>=0.31.0`, `accelerate>=1.1.1`, bare `tqdm`/`easydict`/`ftfy`/`scipy`). Only `transformers` has an upper bound (`<=4.51.3`). No lockfile, no hashes. `flash_attn` is listed as a plain requirement, which will attempt a source build inside `pip install -r` and usually fails; the README separately tells you to install it with `--no-build-isolation`.
- Zero tests, zero CI (no `.github/` directory at all). 55 Python files; ~20 of them (`wan/modules/animate/**`, `wan/modules/s2v/**`) are unreferenced Wan2.2 leftovers, including a SAM/pose preprocessing pipeline whose dependencies are not in `requirements.txt` — dead attack surface and dead maintenance burden.

## Physics and dynamics

- **Action space (this is the headline).** Primary input is `poses.npy` of shape `[num_frames, 4, 4]` — **camera-to-world SE(3) matrices in OpenCV convention** — plus `intrinsics.npy` of shape `[num_frames, 4]` = `[fx, fy, cx, cy]` (README "Inference" section; loaded at `wan/image2video.py:316, 384`). These are converted to frame-to-frame relative poses (`compute_relative_poses(..., framewise=True)`, `wan/image2video.py:404`) and then to per-pixel Plücker coordinates `[rays_o (3), rays_d (3)]` (`cam_utils.py:110-118`). **This is a fully continuous 6-DoF action space, not key codes.**
- **The keyboard path is a convenience layer on top, not the native space.** `--action_string "w-10,a-10,d-10,iw-15,none-10,..."` is parsed into binary WASD/IJKL arrays and then *integrated into camera poses* by a hand-written kinematic stub with `move_speed = 0.05` and `rotate_speed_rad = deg2rad(2.0)` hardcoded (`wan/utils/wasd_ijkl_to_c2ws.py:169-170`), yaw-then-pitch composition, and an 85-degree pitch clamp. The model still only ever sees Plücker maps.
- **Two action encodings, and the difference matters.** Cam mode (`control_dim = 6`) feeds full Plücker including ray origins, i.e. translation *is* in the conditioning. Act mode (`control_dim = 7`) calls `get_plucker_embeddings(..., only_rays_d=True)` (`wan/image2video.py:409-414`) so **translation is thrown away** and movement is re-supplied as four binary WASD channels broadcast over the whole frame (`image2video.py:420-430`). For roboticarray, Cam is the only interesting variant; Act is literally a game controller.
- **Metric scale is destroyed.** `compute_relative_poses` defaults to `normalize_trans=True` and divides all translations by their max norm (`cam_utils.py:67-72`, with an in-code note citing CameraCtrl-II). So "drive forward 3 m" and "drive forward 30 m" produce identical conditioning if the trajectory shape is the same. Any metric control loop needs this disabled and the model retrained — which you cannot do, because there is no training code.
- **Intrinsics are hardcoded to a 480x832 source.** `get_Ks_transformed(Ks, height_org=480, width_org=832, ...)` at `wan/image2video.py:386-393` assumes your `intrinsics.npy` was authored at 480p; a real camera calibration at any other resolution is silently mis-scaled.
- **Horizon / resolution / fps.** 480x832 or 720x1280. `frame_num` must satisfy `F = 4n+1`; examples use 81, 121, 161, and the README claims `961` frames (~60 s at 16 fps) is reachable with enough VRAM — that is the "minute-scale memory" claim. In the base (non-fast) path this is **full bidirectional attention over the whole clip**, so memory is O(F^2) attention, not a memory mechanism. In the fast path there is a real KV cache with optional sliding window (`--local_attn_size`, default `-1` = unbounded) and attention sinks (`--sink_size`, default `0` = none). **Both defaults are off**, so out of the box the fast path also just grows its cache. There is no retrieval, no explicit scene memory, no 3D cache — the "long-term memory" is attention over past latents and nothing more.
- **Evaluation: none in the repo.** No FVD, no FID, no controllability metric, no trajectory-following error, no collision check, no benchmark script. Claims rest on demo videos and a bundled 48 MB PDF. Compare to OpenDWM, which checks FID/FVD into its configs.
- **Known failure modes.** Inferred, not documented: scale-free conditioning means translation magnitude is uncontrollable; the WASD kinematic stub has no inertia or ground plane (free-flying camera, moves are projected onto the horizontal plane at `wasd_ijkl_to_c2ws.py:196-206`); the fast path drops CFG entirely (single forward per step, `image2video_fast.py:636`), which typically costs prompt adherence; `self.control_type` is only assigned if the string `cam` or `act` appears in your checkpoint path (`image2video.py:98-101`) — rename the directory and you get an `AttributeError` deep in the pipeline.

## Motion-control assessment

The one thing worth taking from this repo is that **its action space is already the right shape for us**. Alpamayo-R1's `ActionSpace.action_to_traj` emits `traj_future_xyz (..., T, 3)` and `traj_future_rot (..., T, 3, 3)`; compose those into 4x4 matrices, write them to `poses.npy`, write the real camera calibration to `intrinsics.npy`, and LingBot-World renders that trajectory with **no retraining of the action encoder** — the encoder is a Plücker map, and a Plücker map does not care whether the pose came from a game pad, COLMAP, Isaac Sim or a planner. The same applies to an Isaac Sim / Isaac Lab camera prim: dump `c2w` per tick, feed it in. That makes it a plausible drop-in neural renderer for AlpaSim-style rollouts where Isaac owns physics.

Three things break that story in practice. First, **scale normalisation** (`cam_utils.py:67-72`) means the conditioning is a trajectory *shape*, not a metric path — you cannot ask for a specific speed, and two manoeuvres differing only in magnitude are indistinguishable to the model. For motion control that is disqualifying, and fixing it requires retraining. Second, **there is no training code**, so every adaptation we would want (metric scale, vehicle-frame conventions, multi-camera rigs, adding a steering/throttle channel) is blocked at the repo level; we would be reimplementing the training loop from the paper. Third, the model conditions the *camera*, not the *scene*: there are no object boxes, no map, no other agents, so a driving or manipulation scenario cannot be scripted the way it can in OpenDWM or Cosmos-Drive-Dreams.

The architectural patterns are worth copying regardless. `examples/persistent_inference.py` is the best serving example in this survey — construct the pipeline once, `prewarm()` once, then loop, with documented cold-start amortisation. The fast path's chunked causal denoise + KV-cache write-back (`image2video_fast.py:600-664`) is a clean, readable implementation of streaming autoregressive video that we could lift into our own stack. And `--local_attn_size` / `--sink_size` give the exact knobs a bounded-memory streaming rollout needs, even though they ship disabled.

## Extensibility

- **New trajectory / action source:** zero code. Write `poses.npy` (`[F,4,4]` OpenCV c2w) and `intrinsics.npy` (`[F,4]`) into a directory, pass `--action_path`. This is the integration point for Isaac Sim, AlpaSim or Alpamayo.
- **New intrinsics resolution:** patch `wan/image2video.py:386-393` — `height_org=480, width_org=832` is hardcoded and wrong for any other calibration source.
- **Metric-scale conditioning:** flip `normalize_trans=False` at `wan/image2video.py:404`. Expect it to break, because the checkpoint was trained on normalised input; there is no retraining path to fix it.
- **New conditioning channel (throttle, steering, joint angles):** `control_dim` is set once per checkpoint at `wan/modules/model.py:394-397` and consumed by `patch_embedding_wancamctrl`. Adding a channel means a new input projection and retraining. **Blocked — no training code.**
- **Bounded-memory streaming:** `--local_attn_size N --sink_size M` in `generate_fast.py:157-166`. Undocumented, untested, defaults off; the first thing to sweep if we prototype long rollouts.
- **Coupling hotspots:** `control_type` inferred from the checkpoint path string (`image2video.py:98-101`); `frame_num` must be `4n+1` (auto-padded by `pad_frame_num_to_4n_plus_1`, `wasd_ijkl_to_c2ws.py:126-135`); `chunk_size=3` is hardcoded in `generate_fast.py:276` and must divide the latent frame count; `wan/modules/animate/` and `wan/modules/s2v/` are dead weight that should be deleted from any fork on day one.

## Hardware and cost

All published commands are `torchrun --nproc_per_node=8 ... --dit_fsdp --t5_fsdp --ulysses_size 8`, i.e. **8 GPUs with FSDP sharding and Ulysses sequence parallelism**. The weights justify it: each DiT expert is ~74 GB on the Hub (8 shards of ~9.3 GB), two experts for the base model, plus an 11.4 GB T5 and a 0.5 GB VAE — roughly **160 GB of parameters** for the base Cam model. 8xH100 (80 GB) is the intended configuration; `--t5_cpu` and `--convert_model_dtype` are the memory escape hatches, and the community NF4 quant (`cahlen/lingbot-world-base-cam-nf4`) is the single-GPU option, inference-only with acknowledged quality loss. No single-GPU number is stated anywhere in the repo.

The only concrete timing in the repo is the docstring of `examples/persistent_inference.py:20-23`: on **8xH100 at 480x832, 81 frames**, a naive `generate_fast.py` invocation takes **~126 s**, and the persistent pipeline takes **~104 s load + ~7 s prewarm + ~15.5 s per clip**. Take the steady-state number seriously: 81 frames in 15.5 s is **~5.2 generated fps on eight H100s**. The README's "real-time interactivity, under 1 second latency at 16 fps" is a per-chunk latency claim on presumably-tuned serving infrastructure, not the throughput this code achieves — at 16 fps playback, 81 frames is 5.1 s of video produced in 15.5 s, i.e. **3x slower than real time on 8xH100**. The base (non-fast) path with 70 sample steps and CFG is far slower still. Budget an 8xH100 node and do not plan a closed loop around this.

## Verdict and next step

**WATCH.** The licence is the best in this batch (genuine Apache-2.0 on both code and weights, no Chinese-lab rider, no user cap), and the action space is genuinely the right abstraction — continuous SE(3) camera poses encoded as Plücker rays, which an Alpamayo trajectory or an Isaac Sim camera prim can drive without touching the action encoder. But the value stops there: translations are scale-normalised so metric control is impossible, there is no training or fine-tuning code so none of that can be fixed, there is no physics or controllability evaluation of any kind, nothing in the repo has been demonstrated on a robot or a vehicle, real throughput is ~5 generated fps on eight H100s rather than the advertised real time, and the maintainers have put a banner on the README saying the repo is dead. The concrete next step is **not** to stand this up: it is to spend a day reading `wan/image2video_fast.py:600-664` and `examples/persistent_inference.py` and porting the chunked-causal-KV-cache and persistent-pipeline patterns into our own streaming harness, then track `Robbyant/lingbot-world-v2` and re-review it the moment training code appears. If someone insists on a demo, the cheap version is: export a 5-second Isaac Sim camera path to `poses.npy`, run the Cam checkpoint at 480p on an 8xH100 node, and see whether the rendered trajectory actually tracks the input — that single experiment tells us whether the Plücker conditioning is tight enough to be worth revisiting at all.
