## What it is

Cosmos-Drive-Dreams is a synthetic-data-generation *pipeline* for autonomous driving, not a model in its own right: it renders condition videos (HD map + bounding boxes, LiDAR depth, or "world scenario" 3D geometry) from structured AV labels, rewrites captions with a VLM to diversify weather and conditions, then drives Cosmos-Transfer1-7B-Sample-AV to produce a 121-frame front-view RGB video, and finally expands that into a 7-camera multiview clip with the Single2MultiView model. Alongside the pipeline it ships the **Cosmos-Drive-Dreams dataset** — labels (HD map, 3D boxes, LiDAR) for 5,843 real 10-second NVIDIA clips plus 81,802 synthetic video samples generated from them, about 3 TB total — and a toolkit directory that is arguably the most valuable part of the repo: an interactive viser-based visualiser that lets you **edit the ego trajectory and re-render**, a Waymo Open Dataset converter into the repo's RDS-HQ format, f-theta-to-pinhole rectification, and LiDAR point-cloud-to-range-map conversion. A separate `cosmos-transfer-lidargen/` subtree contains a LiDAR tokenizer and an RGB-to-LiDAR diffusion model with post-training scripts, built on Cosmos-Predict1. The generation backbone is Cosmos-Transfer1 (a git submodule), i.e. the *previous* generation — Transfer2.5 has since absorbed the world-scenario rendering path.

## Security findings

- **`eval()` on an interpolated attribute name**: `cosmos-drive-dreams-toolkits/utils/animation_utils.py:680` executes `eval(f"self.scene.{attrib_name} = attrib_val")` for animator entries keyed `"free"`. `attrib_name` comes from the animation/keyframe event dictionary, so a crafted scene or pose file reaches `eval`. (Note it is also plain wrong — `eval` cannot execute an assignment; this branch would raise `SyntaxError` if ever hit, which tells you it is untested code.)
- **Unpinned dependency from a personal GitHub fork**: `requirements.txt` contains `viser @ git+https://github.com/yifanlu0227/viser.git` with no commit pin or tag. Whatever is on that account's default branch at install time is executed. This is the single biggest supply-chain issue in the repo.
- **Wrong-package pin**: `requirements.txt` has `apex==0.9.10dev`, but the code imports NVIDIA Apex (`from apex.multi_tensor_apply import multi_tensor_applier` at `cosmos-transfer-lidargen/cosmos_predict1/utils/fused_adam.py:17` and `.../diffusion/training/models/model.py:21`). PyPI `apex` is an unrelated project; NVIDIA Apex must be built from source. You will silently install a stranger's package and then fail at import.
- **Spurious/confusable pin**: `requirements.txt` lists both `attr==0.3.2` and `attrs==25.3.0`. The code's `import attr` (`.../cosmos_predict1/utils/config_helper.py:24`) is satisfied by `attrs`; `attr` is an unrelated PyPI package pulled in for no reason. Also `Pillow==11.2.1` and a second unpinned `pillow`.
- **`torch.load` without `weights_only`, including of TorchScript archives**: `cosmos-transfer-lidargen/cosmos_predict1/diffusion/module/pretrained_vae.py:204,215` load `encoder.jit` / `decoder.jit` with `weights_only=False`; `.../diffusion/inference/inference_utils.py:328,354` fall back to `weights_only=False`; `.../diffusion/training/utils/checkpointer.py:149` passes no `weights_only` at all. The AV checkpoints are distributed as `.pt` (`base_model.pt`, `hdmap_control.pt`, `lidar_control.pt`), i.e. pickles, not safetensors.
- **`exec(compile(...))` config loading**: `cosmos-transfer-lidargen/cosmos_predict1/utils/lazy_config/lazy.py:218,280`, with a `cloudpickle`/`dill` serialisation fallback at `lazy.py:338-346`. `dill==0.4.0` and `cloudpickle==3.1.1` are direct dependencies.
- **`pickle.load` on dataset side-files**: `.../training/datasets/dataset_multiview.py:93,212`, `.../lidar_dataset/imagetolidar_dataloader.py:390`, `.../dataset_3D.py:362`, `.../dataset_3D_binary.py:132`, `.../dataset_video.py:164`.
- **Token in a documented command line**: `cosmos-transfer-lidargen/README.md` instructs `export YOUR_TOKEN=xxxx` then `pip install ncore --extra-index-url https://__token__:${YOUR_TOKEN}@gitlab-master.nvidia.com/...`. The token is an env var rather than a literal, but this pattern leaks credentials into shell history, `pip` logs and CI transcripts. It is optional (NVIDIA-internal) — do not run it.
- **Repository hygiene**: two `.gitmodules` files are tracked (`git ls-files` shows `.gitmodules` and `"\342\200\216.gitmodules"` — the second filename begins with U+200E LEFT-TO-RIGHT MARK). The effective one points at `git@github.com:nvidia-cosmos/cosmos-transfer1.git` (SSH), so `git submodule update --init` fails for anyone without a GitHub SSH key; the invisible-name duplicate holds the HTTPS URL. Probably an accident, but an invisible-character filename in a tracked tree is exactly the shape of a homoglyph attack and should be deleted in our fork.
- No hardcoded tokens, API keys or cloud credentials found. No `trust_remote_code`. No `shell=True`.

## Physics and dynamics

- **"Action" space**: the ego trajectory — a sequence of 6-DoF camera/vehicle poses. You author keyframes in the viser GUI (`visualize_rds_hq.py`), the tool interpolates the intermediate poses and writes them as a `.tar` into a novel-pose folder, and `render_from_rds_hq.py --novel_pose_folder` re-renders every condition view along that new path. This is ego-pose conditioning, not vehicle control (no steering, throttle, brake, no dynamics constraint), and nothing checks the trajectory is kinematically feasible.
- **Other agents**: replayed from the recorded label track (`all_object_info`); they do not react to the edited ego trajectory. Counterfactual ego motion therefore produces physically inconsistent interactions at anything beyond small perturbations — the classic log-replay limitation.
- **Horizon / resolution / fps**: clips are 10 s; generation is 121 frames per chunk (the output filename carries a `_0` chunk suffix), 7 camera views for multiview, f-theta 120-degree FOV cameras natively with a rectification path to pinhole.
- **LiDAR**: `cosmos-transfer-lidargen` generates 512 x 1800 range maps from multi-view RGB; the tokenizer is a continuous-latent 8x8 spatial compressor.
- **Evaluation**: the paper reports downstream-task gains from training on the synthetic data (the headline claim is that the 81,802-clip corpus improves AV models); the LidarGen README reports reconstruction accuracy. There is no dynamics evaluation, no closed-loop metric, and no check of geometric consistency between the edited trajectory and the generated pixels.
- **Known failure modes**: large ego-trajectory edits move the camera away from where the real sensor was, so the conditioning geometry becomes extrapolation and the generator hallucinates; static-actor replay breaks interaction realism; chunking at 121 frames bounds the horizon; the world-scenario renderer needs a GPU and moderngl, which is a frequent headless-server failure.

## Motion-control assessment

Of the five repos reviewed, this one is closest to the AV data problem roboticarray actually has, and the integration path is the clearest. RDS-HQ is a plain directory-of-folders format (`pose`, `vehicle_pose`, `all_object_info`, `ftheta_intrinsic`, `pinhole_intrinsic`, `captions`, `3d_*` map layers, `lidar_raw`) and the repo ships `convert_waymo_to_rds_hq.py` as the worked example of importing a foreign AV dataset. Writing an AlpaSim-to-RDS-HQ exporter is therefore a bounded task with a reference implementation, and once it exists, three things become possible: render Alpamayo-style multiview conditions from our own scenarios; generate photoreal counterfactual variants of our logged drives; and — the most interesting for planning — sweep the ego trajectory to produce matched sets of "what the world would have looked like if the car had done X", which is exactly the augmentation a planner or a VLA reward model wants.

The limits are hard and should be stated plainly: this is open-loop. There is no dynamics model, actors do not react, the generator cannot be stepped at control rates, and nothing produces a state estimate you could feed back. It cannot replace Isaac Sim or AlpaSim for closed-loop evaluation, and it is not a world model in the predictive sense — Cosmos-Predict2.5 is the repo for that. Treat Cosmos-Drive-Dreams as (a) a dataset we can legally use, (b) a set of AV toolkits worth vendoring, and (c) a rendering front-end that now feeds Cosmos-Transfer2.5's `auto/multiview` model. If we adopt anything here, prefer the world-scenario renderer plus Transfer2.5 over the repo's own Transfer1 pipeline.

## Extensibility

- **Bring your own AV dataset**: convert to RDS-HQ. `cosmos-drive-dreams-toolkits/convert_waymo_to_rds_hq.py` plus `docs/convert_public_dataset.md` is the template; `cosmos-drive-dreams-toolkits/config/dataset_*.json` defines the camera set used for rendering (`rds_hq` for front-only, `rds_hq_mv` for multiview).
- **New camera rig / intrinsics**: add a dataset config JSON and supply `ftheta_intrinsic` or `pinhole_intrinsic`; `rectify_ftheta_to_pinhole.py` converts outputs between models.
- **New conditioning signal**: rendering modes are `hdmap`, `lidar`, `world_scenario`, each independently skippable via `--skip`. Adding a fourth means editing `render_from_rds_hq.py` and the utils under `cosmos-drive-dreams-toolkits/utils/` — a fork, but a small and readable one (this code is far more approachable than the Cosmos `_src` trees).
- **New ego trajectory / action sweep**: the viser GUI writes pose tars; for programmatic sweeps, skip the GUI and write the same tar format directly from a script — that is the seam to automate, and it is the highest-value change we would make.
- **LiDAR post-training**: `cosmos-transfer-lidargen/examples/lidar_tokenizer.md` and `lidar_diffusion.md`, with `convert_lidar_pointcloud_to_rangemap.py` for data prep.
- **Coupling hotspots**: the generation scripts (`scripts/generate_video_*.py`) require `PYTHONPATH=cosmos-transfer1` and the submodule checked out, so they inherit all of Transfer1's install pain; parallelism is Ray, with a `USE_RAY=False` flag inside `render_from_rds_hq.py` for single-process debugging (undocumented outside the toolkit README).

## Hardware and cost

The top-level repo does not state VRAM requirements — treat that as **unclear** and budget from the models: Cosmos-Transfer1-7B-Sample-AV is a 7B diffusion model and upstream Transfer1 documents roughly an 80 GB GPU for single-GPU inference. Measured numbers that *are* published, in `cosmos-transfer-lidargen/README.md`: on a single **A100-SXM4-80GB**, the LiDAR tokenizer runs at 1.7 fps for a 512 x 1800 range map at fp32, and the RGB-to-LiDAR diffusion model takes about **160 s per range map**. Condition rendering is CPU-only for HD map but needs a GPU (moderngl) for LiDAR depth and world scenario. Storage dominates the real cost: the full dataset is about **3 TB** (about 700 GB for the synthetic videos alone), and the Transfer1 checkpoint download is about **300 GB**. Environment: conda, Python 3.12, CUDA 12.4 toolkit per `environment.yaml`, torch 2.7.0, plus a manually installed cu128 flashinfer wheel, vllm 0.9.0 and transformer-engine 2.4.0 — tested on Ubuntu 20.04/22.04 only. Expect the install to be the hardest part of adopting this repo.

## Verdict and next step

**TRIAL**, scoped tightly: trial the *dataset and toolkits*, not the Transfer1 generation stack. The 81,802-clip corpus with paired HD map and LiDAR labels is stated to be commercially usable and is worth evaluating on its own merits against our data needs, and the RDS-HQ format plus the Waymo converter give us a cheap, reference-backed route to make our own scenarios renderable by both this pipeline and Cosmos-Transfer2.5. Recommended next step, about two weeks: (1) legal reads the HF dataset card's exact terms and confirms the "commercial use" claim; (2) download the `hdmap` subset only (skip the 700 GB of synthetic video initially), run `render_from_rds_hq.py` on `assets/example` to validate the toolchain, and use the viser tool to produce one edited ego trajectory end to end; (3) prototype an AlpaSim-to-RDS-HQ exporter against `convert_waymo_to_rds_hq.py` and render our own scenario. Before any of that, fix the repo hygiene in our fork: delete the invisible-character `.gitmodules`, repoint the submodule at the HTTPS URL, pin `viser` to a commit SHA, and drop the bogus `apex`/`attr`/duplicate-`pillow` lines from `requirements.txt`. Do not run `cosmos-transfer-lidargen`'s optional `ncore` install command.
