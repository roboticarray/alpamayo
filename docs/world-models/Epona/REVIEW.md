## What it is

Epona (ICCV 2025) is a **single-front-camera** autoregressive diffusion world model for driving that decouples temporal reasoning from spatial generation. A multimodal spatio-temporal transformer (`models/stt.py`, `n_layer=[12,6,6]`, `n_embd=2048`) consumes 10 past frames of DC-AE latents plus per-frame discretised ego motion and emits a context feature; two rectified-flow DiT heads then sample from it — `models/traj_dit.py` (`TrajDiT`, ~1024-dim, 2 blocks) produces a 15-step future trajectory, and `models/flux_dit.py` (a Flux-derived DiT, 2048-dim) produces the next frame's latent, conditioned on the *next* ego-motion token. Images are 512x1024, encoded by a temporal-aware DC-AE at f32c32 (`temporal_patch_size=6`), and video is rolled out frame-by-frame with a 10-frame sliding window, so the horizon is bounded only by drift and wall-clock. Training is nuPlan (5 fps) with a nuScenes finetune (10 fps) and an unreleased in-house "China" finetune; three checkpoints are public under MIT. The same forward pass yields both a predicted trajectory and a predicted frame, which is what makes this repo interesting for motion control rather than just video.

## Security findings

- `models/model.py:110` — `state_dict = torch.load(load_path, map_location='cpu')["model_state_dict"]`. No `weights_only=True`. Combined with the fact that the *published artifacts are named `.pkl`* (`epona_nuplan.pkl`, 5.18 GB, on HF), this is the highest-risk item in the repo: loading the official weights executes whatever the pickle says. Mitigate by converting to safetensors once, in a throwaway container, before any routine use — or patch this line to `weights_only=True` and see whether the checkpoint still loads (it is a plain state dict, so it should).
- `utils/running.py:155` — `ckpt_file = torch.load(resume_load_path, map_location="cpu")`, same issue on the resume path.
- `scripts/train_deepspeed.py:174,180` — two more unguarded `torch.load` calls for `--load_stt_path` and `--resume_path`.
- `models/modules/dcae_layers/utils/network.py:73` — `checkpoint = torch.load(file, map_location="cpu")` for the DC-AE. Note `models/modules/dcae.py:726` does the right thing (`weights_only=True`) — the repo is inconsistent, so the safe path exists and simply was not applied to the main loader.
- `utils/config_utils.py:1405,1589,1710` — vendored mmengine `Config`: `eval(codeobj, ...)`, `exec(compile(modified_code, filename, mode='exec'), ...)`, `eval(compile(base_code, '', mode='eval'))`. Config files are executable Python by design (`configs/*.py` are `.py`), so "run this config" means "run this code". Standard for mmengine, still worth knowing before accepting a config from outside.
- `utils/distributed.py:32` — `subprocess.getoutput(...)` to resolve the SLURM head node address; shell string, but the input is `SLURM_NODELIST` from the scheduler, not user data. Low risk.
- **Not found:** no `trust_remote_code`, no `curl | sh`, no hardcoded tokens or API keys, no network fetch at import time.
- **Dependency pinning:** `requirements.txt` is fully exact-pinned (23 entries, all `==`), which is better than most of this batch — but it pins `torch==2.1.0+cu121` and `triton==2.1.0`, a 2023-era stack, and the README itself tells you to comment torch out and install something else, which silently unpins the most important dependency. `nuplan-devkit==1.2.0` drags in a large and stale transitive tree. No lockfile, no `pyproject.toml`, no `setup.py`.
- **Tests / CI:** zero. `scripts/test/` contains demo runners, not tests. No `.github/` directory.

## Physics and dynamics

- **Action space.** Per-frame relative ego motion in the vehicle frame: `pose_x` = forward translation (m), `pose_y` = lateral translation, right positive (m), `yaw` = heading change, left positive, **in degrees** — documented in the docstring at `scripts/test/test_ctrl.py:78-85`. These are *deltas between consecutive frames*, not absolute waypoints. Before entering the transformer they are quantised into discrete tokens (`poses_to_indices` / `yaws_to_indices`, `models/model.py:228-229`) over `pose_x_vocab_size=128`, `pose_y_vocab_size=128`, `yaw_vocab_size=512` spanning `pose_x_bound=50`, `pose_y_bound=10`, `yaw_bound=12` (`configs/dit_config_dcae_nuplan.py:79-82`). At 5 fps a 50 m per-frame forward bound is 250 m/s — absurdly generous — while the 12-unit yaw bound is the binding constraint on hard turns. There is no explicit "unconditioned" sentinel; the model always gets a motion token.
- **Trajectory output.** `TrajDiT` emits `traj_len=15` future steps of the same (Δx, Δy, Δyaw) triple, denormalised by `denormalize_traj` (`models/model.py:132-135`). At nuPlan's 5 fps that is a **3-second** planning horizon; at the nuScenes config's 10 fps, 1.5 s. This is short by planner standards (Alpamayo and the nuScenes open-loop convention both work at 3 s, so it is comparable for nuScenes-style L2, but it will not support a 6-8 s horizon without retraining `traj_len`).
- **Horizon — the 120 s / 600-frame claim.** The README says "minutes-long driving videos"; the paper's claim of 120 s corresponds to 600 frames at 5 fps. **The code does not contain that number anywhere.** The shipped default is `test_video_frames=50` (`configs/dit_config_dcae_nuplan.py:76`), i.e. 10 s. What the code *does* support is an unbounded loop: `test_free.py:90` iterates `range(0, args.test_video_frames, args.temporal_patch_size)` and the sliding window at `test_free.py:112` keeps only the last 10 latents, so memory is constant and you can set `test_video_frames=600` and get 600 frames. So 120 s is reachable, but it is a config edit that upstream never exercises, and there is no drift metric, no long-horizon evaluation, and no re-grounding mechanism — the reference window is 10 frames and everything beyond that is the model's own output fed back in. Treat "120 s" as "the loop does not stop", not "the loop stays correct".
- **Resolution / fps / cameras.** 512x1024 single front camera (`image_size=(512,1024)`; the dataloader reads only `CAM_F0`, `dataset/dataset_nuplan.py:111`). nuPlan's other seven cameras are indexed by `data_preparation/create_nuplan_json.py:31-39` but never loaded by the model. 5 fps for nuPlan, 10 fps for the nuScenes finetune. There is **no** multi-camera capability and no cross-view consistency mechanism — this is the sharpest limitation versus OpenDWM.
- **Evaluation.** None is shipped. `test_traj.py` runs the trajectory head, writes `%03d.npy`, and calls `plot_trajectory` — no ADE/FDE, no collision rate, no FID/FVD, no controllability metric. Every number in the paper would have to be recomputed with our own harness.
- **Known failure modes.** Latent-space drift over long rollouts (unmeasured, and structurally likely given a 10-frame window and self-predicted motion in `test_free.py:104-106` where the predicted pose is duplicated into the next two slots); yaw clipped at `yaw_bound=12`; degenerate out-of-distribution behaviour if you hand it a trajectory the quantiser saturates; DC-AE `temporal_patch_size=6` means frames are decoded in groups of six, so the "frame rate" of the decoder is coupled to the config.

## Motion-control assessment

Epona's conditioning format is the *closest* in this batch to something an Alpamayo planner can drive directly, but the mapping is lossy in a specific way worth stating. Alpamayo's `ActionSpace.action_to_traj` (`src/alpamayo_r1/action_space/action_space.py:47-70`) returns `traj_future_xyz (..., T, 3)` and `traj_future_rot (..., T, 3, 3)` — full 3D translation and full SO(3) rotation. Epona wants `(Δx, Δy, Δθ)` per step in the previous frame's ego frame. The adapter is:

1. Compose Alpamayo's absolute future poses into relative ones: `Δp_t = R_{t-1}^T (p_t - p_{t-1})`, take `Δx = Δp_t[0]`, `Δy = -Δp_t[1]` if Alpamayo is x-forward/y-left (Epona is y-**right** positive, per the `test_ctrl.py:81` docstring — sign check this on real data before trusting any result).
2. `Δθ_t = yaw(R_{t-1}^T R_t)` in **degrees** — Epona takes degrees at the script boundary while `utils/preprocess.py` works in radians internally, so this is an easy place to be off by 57x.
3. Drop z, pitch and roll entirely. Epona has no vertical channel, so slopes, pitch under braking and suspension motion are invisible to it. For a flat-ground driving scene this is tolerable; for any of our off-road or rough-terrain work it is a hard mismatch.
4. Resample to 5 Hz (nuPlan checkpoint) or 10 Hz (nuScenes checkpoint). Alpamayo's horizon must be decimated to match, and the per-step deltas depend on the rate, so this is not a free reindex.

`alpamayo_r1.geometry.rotation` already has what step 1 and 2 need, so the adapter is maybe forty lines. The useful shape of a trial is: take an Alpamayo-planned trajectory, render it through Epona, and ask whether the generated video is consistent with the commanded motion — a cheap qualitative controllability check that we currently have no tool for. Feeding Epona's output *back* into Alpamayo is not possible: Alpamayo is multi-camera, Epona produces one front view.

For Isaac Sim / AlpaSim there is no ready hook comparable to OpenDWM's CARLA loop. Epona has no layout conditioning (no boxes, no map), so a simulator cannot tell it what the scene contains — it can only tell it how the ego moved. That makes it unusable as a neural renderer *on top of* Isaac (the world it invents will not match Isaac's world) and instead confines it to open-loop, dataset-seeded rollouts. The `num_sampling_steps=100` rectified-flow sampler run twice per frame (trajectory head then image head) also rules out anything close to real-time closed loop; the paper's "real-time motion planner" claim refers to the trajectory head alone with `traj_only=True` (`models/model.py:247`), which skips the expensive image DiT — that path is genuinely cheap and is the one worth benchmarking if we care about the planner claim.

## Extensibility

- **New dataset**: copy `dataset/dataset_nuplan.py` into a new class and register it in `dataset/create_dataset.py`; then set `train_data_list` / `val_data_list` and `datasets_paths` in the config. The contract is narrow and easy: return `(img [F,3,H,W], rot_matrix [F,4,4])` per item and let `utils/preprocess.get_rel_pose` derive the motion tokens. That 4x4 return is convenient for us — it is the same object Alpamayo's poses assemble into.
- **New sensor / camera**: not supported without surgery. `dataset/dataset_nuplan.py:111` hardcodes `CAM_F0`, and `models/stt.py` has no view axis. Adding surround view means a new positional-embedding scheme and a full retrain; there is no cross-view attention to reuse.
- **New action space**: the quantiser lives in `utils/embeddings.py` (`poses_to_indices`, `yaws_to_indices`) and the bounds in the config, so widening the yaw bound or adding a channel is a contained change — but it invalidates the released checkpoints, since the embedding tables are sized by `*_vocab_size`. The continuous side (`normalize_traj` / `denormalize_traj`, `models/model.py:126-135`) is a trivial affine and would be the place to bolt on a z channel.
- **Config system**: vendored mmengine `Config` (`utils/config_utils.py`, ~1700 lines copied in). Flat Python files; `Config.fromfile` then `merge_from_dict(args.__dict__)`, so every CLI flag silently overrides a config key of the same name. There is no schema and no validation — a typo in a config key is a silent no-op.
- **Coupling hotspots**: `condition_frames=10` appears in the config, in every test script's slicing, and in `prepare_ids`; `temporal_patch_size=6` couples the decoder to the rollout loop stride (`test_free.py:90`); `image_size` and `downsample_size` determine the token count baked into the positional IDs; the constructor calls `.cuda()` unconditionally (`models/model.py:102`), so the model cannot be instantiated on CPU for a smoke test.

## Hardware and cost

The README states plainly: "All the inference scripts can be run on a single NVIDIA 4090 GPU", i.e. **24 GB** is sufficient for inference. The world-model checkpoints are 5.18 GB on disk (roughly 1.3 B parameters in fp32) plus a 1.32 GB DC-AE, so weights alone are ~6.5 GB and the rest is activations at 512x1024 with 100 sampling steps. Training is documented as `NODES_NUM=4`, `GPUS_NUM=8` — **32 GPUs** with DeepSpeed at `batch_size 2` per rank, which puts full retraining out of scope for a spike. No wall-clock inference numbers are published anywhere in the repo, but the code is instrumented for it: `models/model.py:235,242,262` print "MST time", "TrajDiT time" and "VisDiT time" per step, so a first run measures itself. Expect the image DiT to dominate at `num_sampling_steps=100`; the `traj_only=True` path skips it entirely and is the only plausible real-time mode. Storage: nuPlan sensor blobs are tens of TB, so anything beyond the provided test meta data implies a serious data-engineering commitment.

## Verdict and next step

**TRIAL.** Epona is the cleanest licensing story we will find — MIT code, MIT weights, no gating, no Stable Diffusion base model dragging a revenue-capped licence behind it — and it is the only model reviewed here that both consumes and produces trajectories, which makes it directly comparable to Alpamayo rather than merely adjacent. Against that: it is one camera, one domain, 512x1024, planar 3-DoF motion, zero tests, zero CI, zero shipped metrics, and the published checkpoints are pickles loaded without `weights_only`. It is a paper artifact of above-average quality, not a platform. The concrete spike, at about a week: (1) in a disposable container, load `epona_nuplan.pkl` and immediately re-serialise it to safetensors, then patch `models/model.py:110` to `weights_only=True` in our fork; (2) write the ~40-line Alpamayo-pose → (Δx, Δy, Δθ°) adapter and verify the sign and unit conventions against a nuPlan clip where ground truth is known; (3) run `test_ctrl.py` with an Alpamayo-planned trajectory and judge, qualitatively, whether the video follows the command — that is a controllability probe we do not currently have; (4) set `test_video_frames=600` and find out empirically where drift makes the 120 s claim stop being true, since upstream never measured it. Do not plan to extend the codebase, do not plan to retrain (32 GPUs), and do not expect it to plug into Isaac Sim — without layout conditioning it cannot render a simulator's world, only its own.
