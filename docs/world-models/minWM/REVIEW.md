## What it is

minWM is not a model — it is a **detectron2-style training framework** for turning a bidirectional text-to-video foundation model into a real-time action-conditioned world model, and it is the only repo in this survey that ships the *whole* pipeline: data preprocessing, bidirectional SFT, teacher-forced autoregressive diffusion, causal ODE and consistency distillation, asymmetric DMD with self-rollout, and 4-step inference. Two reference backbones are integrated end to end (Wan 2.1, 1.3B, cross-attention DiT; HunyuanVideo 1.5, 8B, MMDiT), sharing one trainer, one loss module and one dataset abstraction, so a third backbone is explicitly framed as "a wrapper-and-config exercise". Conditioning comes in two flavours: an **81-class discrete action label** (`trans_label * 9 + rotate_label`, `minwm/data/datasets/action.py:1-12`) and **PRoPE camera conditioning**, which feeds continuous `viewmats [B, F, 4, 4]` plus intrinsics `Ks` into zero-initialised per-block projections that modulate self-attention (`minwm/modeling/wan21/model.py:171-173, 291-308, 470-472`). The repo has 234 Python files, **49 test files**, GitHub *and* GitLab CI, black/isort/flake8 with pre-commit, a mkdocs site, a fully pip-frozen requirements set, working Dockerfiles, and three packaged Claude skills. It is by a wide margin the best-engineered repository in this batch.

## Security findings

- **Config files are executable Python.** `minwm/config/loader.py:29-33` builds a module spec from a file path and calls `spec.loader.exec_module(module)`; `minwm/config/lazy.py:65,78` resolve targets through `importlib.import_module`. This is the detectron2 LazyConfig pattern and it is idiomatic, but it means **every file under `configs/` is code**. Never run a config you have not read, same rule as OpenDWM's `_class_name`.
- **`weights_only=False` on checkpoint loads:** `minwm/engine/checkpoint/checkpointer.py:302` and `minwm/engine/checkpoint/formats.py:168`. The native checkpoint format is `.pt` (pickle), and the published `MIN-Lab/minWM` stage weights are `model.pt` files. `minwm/modeling/wan21/text_encoder.py:58` is also explicit `weights_only=False`; `minwm/modeling/wan21/vae.py:644`, `t5.py:527` and `minwm/modeling/hy15/encoders/byt5_mapper.py:74` omit the flag entirely.
- **Credit where due:** the *data* path deliberately uses the safe loader — `minwm/data/datasets/camera_pt.py:55,56,114,199` and `minwm/modeling/hy15/adapter.py:140,141` all pass `weights_only=True`. Someone thought about this and drew the line in a defensible place. `tools/export_checkpoint.py` exists specifically to convert to safetensors, and `tools/auto_sample.py:165` describes `.pt` as "opaque pickle" in a comment — the authors know.
- **`pickle` in the distributed layer:** `minwm/distributed/sp/parallel_state.py:377,418` and `stateless_pg.py:56,73,85,91` serialise objects for collective communication. This is vLLM/Megatron-derived code operating inside a trusted process group over the torch distributed store, not a file-loading surface. Acceptable, but it means a compromised rank can execute code on its peers.
- **`subprocess.Popen(cmd, ...)`** at `tools/auto_sample.py:245` — list argv, no `shell=True`. Safe.
- **No `eval(`, no `exec(` outside the config loader, no `os.system`, no `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens or keys anywhere in `minwm/`, `tools/`, `scripts/` or `demos/`.**
- **Dependency pinning is the best in the survey.** `requirements/base.txt` is a full `pip freeze`: every transitive dependency at an exact version (`accelerate==1.13.0`, `diffusers==0.35.0`, `av==13.1.0`, `decord==0.6.0`, ...). `docker/Dockerfile` pins the flash-attn wheel by exact release URL (`v2.8.3 ... cu12torch2.9cxx11abiTRUE-cp312`) rather than building from source. CI pins its lint tools (`black==26.5.1`, `isort==8.0.1`, `flake8==7.3.0`).
- Note for our own infra: `.gitlab-ci.yml:7` sets `PIP_INDEX_URL` to the Tsinghua mirror. Harmless upstream, but override it in any fork so builds resolve against our own index.
- CI: `.github/workflows/{ci,docs}.yml` plus `.gitlab-ci.yml` with lint and test stages on CPU torch. 49 test files under `tests/`, including `test_sp_consistency.py`, `test_fsdp.py`, `test_rng.py` and `test_seed.py` — determinism and distributed correctness are actually tested, which is rare.

## Physics and dynamics

- **Action space, both variants, precisely.**
  1. **Discrete, 81 classes.** `action_label = trans_label * 9 + rotate_label` (`minwm/data/datasets/action.py:1-12`). Translation classes are `{none, forward, backward, left, right, fwd+left, fwd+right, back+left, back+right}`; rotation classes are the same pattern over `{yaw_right, yaw_left, pitch_up, pitch_down}`. `discretize_poses_to_actions(viewmats)` (`action.py:69`) takes real `(T,4,4)` w2c matrices and **quantises them into these 81 buckets**, with `_MOVE_NORM_THRESHOLD = 0.01` and `_ROT_THRESHOLD_DEG = 5e-2` deadzones. Any continuous control signal fed through this path is destroyed: a 3-degree-per-step turn and a 30-degree-per-step turn are the same label.
  2. **Continuous, 6-DoF, via PRoPE.** `minwm/modeling/wan21/model.py:291-308` takes `viewmats: [B, F, 4, 4]` (w2c, OpenCV) and `Ks`, and each block's `prope_o` projection modulates self-attention. The projections are **zero-initialised** (`model.py:470-472`) so they can be grafted onto a pretrained T2V backbone and learned. This is the path that matters for us.
- **The shipped interface is a keyboard DSL, not either of those directly.** `minwm/processors/camera.py:9-22` defines the trajectory string: `w/s/a/d` translate, `u/dn` up/down, `j/l` yaw, `i/k` pitch, each step being **0.08 units of translation or 3 degrees of rotation**, chained as `"w*10,d*9"` or `"d*8,i*5,l*6"`. That string is expanded into w2c matrices and passed as PRoPE tensors. So the model's conditioning is continuous, but every released benchmark and checkpoint was driven by a quantised grid.
- **Horizon / resolution / fps.** Wan Action2V outputs **832x480, 77 frames at 16 fps** (~4.8 s) — `README.md:225`, `docs/getting-started.md:113`. Latent frames are 20 (trajectory segment counts must sum to 19). The HY15 line is 480p i2v. Long-horizon rollout is autoregressive chunk-by-chunk; the only memory mechanism is the causal KV context — there is no retrieval, no frustum selection, no explicit scene memory. Their own `debug-world-model` Claude skill lists **"memory attenuation"** and **"camera drift"** among the collected failure modes, which is a more honest statement of the long-horizon limit than any benchmark in the repo.
- **Evaluation: none.** No FVD, no FID, no controllability metric, no physics benchmark, no closed-loop test, no reported numbers. `tools/auto_sample.py` automates sampling during training so you can eyeball results. For a framework this is a defensible choice — it is a scaffold, not a model release — but it means we cannot tell how well the shipped checkpoints track a commanded trajectory without measuring it ourselves.
- **Known failure modes, named by the authors** (README, Claude-skills section): loss NaN, frame-to-frame jitter, camera drift, memory attenuation, distillation collapse. Publishing your failure taxonomy is a strong signal about engineering maturity.

## Motion-control assessment

Every other repo in this batch gives us a *model*. minWM gives us a *method*, and for roboticarray that is the more valuable thing. The question we keep hitting — "can a continuous vehicle or robot control signal replace the keyboard without retraining the action encoder?" — is answered "no" everywhere else, and the follow-up "then can we retrain it?" is answered "no training code" everywhere else. Here both answers change. PRoPE consumes `viewmats [B,F,4,4]` and `Ks` directly; its per-block projections are zero-initialised so they attach to a frozen pretrained backbone without disturbing it; and the full path from bidirectional SFT through teacher-forced AR diffusion, causal ODE/CD distillation and asymmetric DMD to a 4-step real-time student is released and tested. That is exactly the recipe for building *our* action-conditioned model on *our* driving data with *our* control signal.

The concrete plan writes itself. Take the **Wan 2.1 path only** (1.3B, Apache-2.0 base, cheap to train, and free of the Tencent licence on the code side). Replace `minwm/data/datasets/action.py` with a continuous action head that takes throttle, steering and, if we want, the full ego `traj_future_xyz` / `traj_future_rot` from Alpamayo — instead of discretising into 81 buckets, feed the 6-DoF poses to PRoPE and add a small MLP for the scalar controls, mirroring the zero-init trick. Build the dataset from AlpaSim or Isaac Sim rollouts where the commanded action and the resulting ego pose are both known exactly, which is precisely the supervision this pipeline wants and which real driving logs only approximate. Then run the four stages and measure trajectory-tracking error on held-out manoeuvres. `minwm/data/datasets/mock.py` and the `integrate-new-backbone` skill exist to make the first two weeks of that cheap.

What is missing, and it is not small. There is **no physics evaluation anywhere**, so the framework will happily train us a model we cannot assess; we would need to bring our own metrics (trajectory error, collision rate against an Isaac ground truth). The released checkpoints are trained on HunyuanVideo-generated game footage and are of no direct use to us — this is a framework adoption, not a model adoption, and the scoring should be read that way. 77 frames at 832x480 is a research-scale output. And the licence position needs care: the *framework* is Apache-2.0 and the *Wan 2.1 code path* is Apache-2.0, but `minwm/modeling/hy15/` is THCL and `THIRD_PARTY_LICENSES.md:40-41` admits the shipped training videos came out of HunyuanVideo, so a model we distil from their released Wan checkpoints may inherit the THCL output restriction. The clean move is to delete `minwm/modeling/hy15/` from our fork, start from `Wan-AI/Wan2.1-T2V-1.3B` directly rather than from `MIN-Lab/minWM` weights, and train on our own data. Then we are entirely inside Apache-2.0 and the trap never closes.

## Extensibility

- **New backbone:** the documented primary use case. Two reference integrations (`minwm/modeling/wan21/`, `minwm/modeling/hy15/`) behind shared trainer/loss/dataset abstractions, plus a packaged `integrate-new-backbone` Claude skill. Adding Cosmos or our own DiT is a wrapper plus a config.
- **New action space:** `minwm/data/datasets/action.py` (discrete) and `minwm/processors/camera.py` (continuous PRoPE) are the two edit points; `minwm/data/datasets/` also has `camera_pt.py`, `geometry.py`, `lmdb.py`, `mock.py`, `text.py`, `image.py` behind one interface. PRoPE's zero-init (`minwm/modeling/wan21/model.py:470-472`) is the pattern to copy for any new conditioning channel.
- **New training recipe:** `minwm/engine/training/recipes/` holds one file per stage (`bi_sft`, `ar_tf`, `ar_ode`, `ar_cd`, `ar_dmd`, plus `_flow_base`). Adding a stage is adding a file and a config.
- **New dataset:** `minwm/data/datasets/` + `minwm/data/preprocessing/trajectory.py`. LMDB is the production path; `mock.py` lets you smoke-test the whole trainer with no data at all.
- **Config:** lazy config (`--config-file configs/...py`) with inline dotlist overrides (`inference.checkpoint=...`, `inference.sp_size=N`). Configs are Python and are `exec`'d.
- **Checkpoint portability:** `tools/export_checkpoint.py` converts sharded FSDP checkpoints to plain `torch.load`-able or **safetensors** files. Use the safetensors output for anything we distribute.
- **Coupling hotspots:** the HF release names (`dmd`, `causal_cd`) differ from the config names (`stage3_ar_dmd`, `stage2_ar_cd`) and must be bridged with `ln -sfnT` symlinks — the README documents this at length, which is honest but is a papercut; trajectory segment counts must sum to `num_latent_frames - 1`; the ODE data-curation tool expects the Wan base mirrored at `wan_models/` relative to the repo root; `.gitlab-ci.yml` hardcodes a Tsinghua pip mirror.

## Hardware and cost

Underspecified, which is the main documentation gap. **No VRAM figure appears anywhere** in `README.md`, `INSTALL.md` or `docs/`. What can be pinned down: the demos run with `torchrun --nproc_per_node=1`, i.e. **single GPU inference**, for both the 1.3B Wan and the 8B HY lines at 4-step DMD; sequence parallelism is available via `inference.sp_size=N` with a matching `--nproc_per_node`. The runtime image is built on `nvidia/cuda:13.0.1-cudnn-devel-ubuntu24.04` with Python 3.12 and `torch 2.9.1` + `torchvision 0.24.1` compiled against **CUDA 12.8** (the base image's 13.0 userspace is not what torch links against, as the Dockerfile comment carefully explains), so the host driver needs to support 12.8. The only memory number in the repo is `docs/auto-pipeline.md:161`: "the 14B Wan model peaks ~6 GB RSS" — that is host RAM during checkpoint consolidation, not VRAM. Training is FSDP + sequence parallel, single- or multi-node, with `tools/profile_activation_memory.py` provided to measure activation memory yourself. Practically: a 1.3B Wan model at 832x480 x 77 frames will fit inference on a 24 GB card; the four-stage distillation of even the 1.3B line should be budgeted as a multi-GPU, multi-day job, and the 8B HY line as a multi-node one. Measure before committing — the tooling to do so is in the repo.

## Verdict and next step

**ADOPT, scoped as a framework rather than a model, and on the Wan 2.1 path only.** minWM is the most professionally built repository in this survey by a distance — 49 tests, two CI systems, pre-commit, a docs site, a pip-frozen dependency set, working Dockerfiles, honest failure-mode documentation and the most careful third-party licence disclosure I have seen in any research release. More importantly it is the only repo that answers the question this whole survey keeps running into: it ships the full training and distillation pipeline, and its PRoPE conditioning takes continuous `[B,F,4,4]` extrinsics through zero-initialised projections, so grafting our own action space onto a pretrained video backbone is a supported workflow instead of a fork. The released *models* are worth nothing to us — 81-class keyboard actions, 77 frames of HunyuanVideo-generated game footage, no physics evaluation — and the scores above reflect a framework, not a product. The licence needs one deliberate decision up front: delete `minwm/modeling/hy15/` from our fork, start from `Wan-AI/Wan2.1-T2V-1.3B` rather than from `MIN-Lab/minWM` weights, and train on our own data, so the Tencent Hunyuan Community License (no EU/UK/South Korea, output-restriction, derivatives bound) never attaches to anything we build. Concrete next step: a four-week spike on the Wan line — reproduce the `Wan21/Action2V` 4-step DMD demo to validate the environment, then replace `minwm/data/datasets/action.py` with a continuous throttle/steering/ego-pose conditioning head modelled on the PRoPE zero-init pattern, build a dataset from AlpaSim rollouts where commanded action and resulting pose are both exact, run stage 0 and stage 1 only, and report trajectory-tracking error on held-out manoeuvres. If that error is low, minWM becomes our world-model training stack and the rest of this survey becomes a catalogue of weights to evaluate against it.
