## What it is

This monorepo holds three generations of Skywork's interactive world model. **Matrix-Game-1.0** (May 2025) is a 17B Minecraft model whose lasting value is `Matrix-Game-1/GameWorldScore/` — a controllability and *physical-rule* benchmark, the only quantitative dynamics evaluation anywhere in this repo. **Matrix-Game-2.0** (Aug 2025) is a 1.3B SkyReels-V2-based streaming model at 25 fps with three checkpoints (universal, **GTA driving**, TempleRun) and a real `inference_streaming.py`. **Matrix-Game-3.0** (Mar 2026), reviewed here as the newest usable release, is a ~6.5B Wan2.2-TI2V-5B finetune that conditions on **three** signals simultaneously: a 6-dim keyboard vector, a 2-dim continuous mouse vector, and a per-frame **Plücker ray map built from full 4x4 camera extrinsics** (`utils/utils.py:119-148`). Its distinctive contribution is a geometric long-horizon memory: `select_memory_idx_fov` (`utils/cam_utils.py:298`, `445`) picks past frames by **camera-frustum overlap** with the chunk being generated, and those frames are re-injected as latents with their own Plücker embeddings and sentinel action tokens (`pipeline/inference_pipeline.py:475-530`). Real-time claims (40 fps at 720p) rest on DMD distillation plus int8 quantisation of q/k/v/o (`pipeline/inference_pipeline.py:139-143`) and a distilled "LightVAE" decoder. There is **no training code** for MG-3, no tests, and no CI anywhere in the monorepo.

## Security findings

- `Matrix-Game-3/wan/modules/t5.py:495` — `model.load_state_dict(torch.load(checkpoint_path, map_location='cpu', mmap=True))`, no `weights_only=True`. Target is the 11.4 GB `models_t5_umt5-xxl-enc-bf16.pth` pickle from the Hub. Note `mmap=True` does not make unpickling safe.
- `Matrix-Game-3/wan/modules/vae2_2.py:140` — `raw_state = torch.load(vae_pth, map_location="cpu")`, and `:1043` — same for `pretrained_path`. These load `Wan2.2_VAE.pth` (2.8 GB) and the two `MG-LightVAE*.pth` files (2.7 GB / 0.84 GB), all `.pth` pickles distributed from Hugging Face.
- So **four** of the six shipped artifacts are pickles. Only the DiT itself (`base_model/diffusion_pytorch_model.safetensors`, `base_distilled_model/...`) is safetensors. Convert the four `.pth` files locally and patch the three call sites before any shared-cluster run.
- **Clean:** no `pickle` import, no `eval(`, no `exec(`, no `os.system`, no `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens or API keys in MG-3. The only `subprocess` use is `wan/utils/utils.py:72`, `subprocess.run` with an ffmpeg list argv, no `shell=True`.
- **Dependency pinning is good and worth calling out**: `Matrix-Game-3/requirements.txt` pins `torch==2.10.0`, `torchvision==0.25.0`, `torchaudio==2.10.0`, `transformers==4.57.3`, `numpy==2.2.6`, `opencv-python==4.10.0.84`, `safetensors==0.7.0` exactly. Floating: `diffusers>=0.36.0`, `tokenizers>=0.20.3`, `accelerate>=1.1.1`, and bare `tqdm`/`easydict`/`ftfy`/`scipy`/`einops`/`pandas`/`decord`/`tensorboard`/`trimesh`. No lockfile. FlashAttention is not in the file at all — the README tells you to install it yourself, and `--fa_version 3` requires FA3, which needs Hopper.
- `Matrix-Game-1/GameWorldScore/GameWorld/third_party/` vendors whole external projects (DROID-SLAM with an embedded Eigen tree, UMT, AMT). That is a large untracked supply-chain surface. It is irrelevant to MG-3 but it is in the same clone; if we fork, take only `Matrix-Game-3/`.
- No `.github/` directory, no CI, no test files outside the vendored third-party trees.

## Physics and dynamics

- **Action space, precisely.** Three parallel conditioning streams, all consumed by `ActionModule` (`wan/modules/action_module.py:39`, credited to GameFactory arXiv 2501.08325):
  1. `keyboard_condition` — `[T, 6]` float, in practice binary. Index map is `{forward:0, back:1, left:2, right:3}` (`utils/conditions.py:73-75`); the remaining two columns are unused in the shipped benchmark generator. Encoded by a plain MLP, `nn.Linear(keyboard_dim_in=6, 128)` (`action_module.py:70`) — **not an embedding lookup**, so it will *accept* continuous floats, though the model was trained on 0/1.
  2. `mouse_condition` — `[T, 2]` **genuinely continuous** float (pitch rate, yaw rate), benchmark values `±0.1` (`utils/conditions.py:78-87`), fed through an MLP and cross-attended against image tokens (`action_module.py:75-95`). There is a `MOUSE_THRESHOLD = 0.02` deadzone (`utils/utils.py:12`).
  3. `plucker_emb` — per-latent-pixel 6-channel Plücker rays derived from full `[T,4,4]` **camera-to-world extrinsics** (`utils/cam_utils.py:93-118`, assembled in `utils/utils.py:119-148`).
- **The keyboard and the pose are redundant by construction, which is the opening for us.** `compute_next_pose_from_action` (`utils/utils.py:38-93`) is a hand-written forward-kinematics stub: `WSAD_OFFSET = 12.35` units per frame (Unreal centimetres — roughly 2 m/s at 16 fps), `DIAGONAL_OFFSET = 8.73`, `MOUSE_PITCH_SENSITIVITY = MOUSE_YAW_SENSITIVITY = 15.0` degrees per unit, planar motion only (`delta_z = 0.0`, `:88`), yaw averaged over the step for path symmetry. The resulting 5-DoF pose `[x,y,z,pitch,yaw]` becomes the extrinsics that become the Plücker map. **You can skip this function entirely and supply your own extrinsics** — the pipeline only ever consumes the tensor.
- **But scale is normalised away again.** `compute_relative_poses(..., normalize_trans=True)` at `utils/cam_utils.py:76-79` divides translations by their max norm, exactly as in lingbot-world. The Plücker stream therefore encodes trajectory *shape*; magnitude information survives only through the binary keyboard channel. Metric speed control is not available.
- **Memory mechanism (the real contribution).** `select_memory_idx_fov` (`utils/cam_utils.py:298`) and `select_memory_idx` (`:445`) build camera frustums from past extrinsics, compute 3D FOV intersection ratios against the chunk being generated (`cal_intersection_ratio_gpu`, `:410`), and select `memory_num` past frames that geometrically overlap the current view — using frames 3, 7, 11 of the chunk as multi-centre anchors. Those frames are re-injected as latents with their own Plücker embeddings and **sentinel action tokens** (`mouse_cond_memory = +1`, `keyboard_cond_memory = -1`, `pipeline/inference_pipeline.py:525-526`) so the model can tell memory from present. This is retrieval by geometry, not attention over everything, and it is the first mechanism in this survey that could plausibly hold a scene consistent over a minute. `ActionModule` additionally has `local_attn_size = 6` (`action_module.py:63`) bounding the action-attention window.
- **Horizon / resolution / fps.** 704x1280 (720p) default. Chunked autoregression: `57 + (num_iterations - 1) * 40` frames, so the README's `--num_iterations 12` gives 497 frames. At the claimed 40 fps that is ~12 s; the "minute-long" claim needs roughly `num_iterations 37`. Chunk sizes 57 (first) and 40 (subsequent) are hardcoded in `pipeline/inference_interactive_pipeline.py:480,498`. Frame counts must be `4k+1` (asserted at `utils/conditions.py:9` and `utils/cam_utils.py:470`).
- **Evaluation: none in MG-3.** No FVD, no FID, no controllability score, no collision or trajectory-error metric, no eval script. The Hub card carries an `eval-results` tag but the repo ships nothing to reproduce it. The one real benchmark in the monorepo is `Matrix-Game-1/GameWorldScore/`, which scores keyboard accuracy, mouse accuracy, object consistency, scenario consistency and "physical rule understanding" — on Minecraft, for the 17B MG-1 model, and it was not rerun for MG-3.
- **Known failure modes.** Inferred: planar-only kinematics (no vertical motion, no terrain following) in the pose generator; scale-free Plücker conditioning; memory selection degenerates to `[0]*memory_num` when fewer than `memory_num*4` frames exist (`cam_utils.py:465-468`), i.e. no memory for the first ~3 chunks; int8 quantisation of q/k/v/o is applied without any accuracy gate unless you pass `--verify_quant`.

## Motion-control assessment

Matrix-Game-3.0 is the best-shaped world model in this batch for a simulator-in-the-loop architecture, for one specific reason: **it already treats camera extrinsics as a first-class conditioning input, separate from the game controls.** The integration path with Isaac Sim / Isaac Lab / AlpaSim is short and concrete: instead of `get_data` (`utils/utils.py:95`) calling `Bench_actions_universal` and integrating fake WASD into poses, dump the Isaac camera prim's `c2w` per tick into `extrinsics_all`, and pass a keyboard/mouse vector that is either zeroed or filled with a coarse discretisation of the ego motion. Everything downstream — `build_plucker_from_c2ws`, the FOV memory selection, the chunked rollout — works unchanged. For Alpamayo, `traj_future_xyz` plus `traj_future_rot` compose into exactly the `[T,4,4]` this expects, same as for OpenDWM, with no bicycle-model approximation in between.

The FOV-based memory is the part most worth stealing outright. A driving or manipulation rollout revisits the same geometry constantly (a parked car you drove past, a bin you turned away from), and frustum-overlap retrieval is a principled, cheap way to decide which past frames matter — far better than a sliding window. `utils/cam_utils.py:298-530` is self-contained, depends only on extrinsics and intrinsics, and could be lifted into our own streaming harness with almost no modification.

What is missing is everything that makes a world model a controller. The action vector is a game pad: four directional bits plus a 2-DoF look rate. There is no throttle, no steering angle, no joint command, no gripper, and because the keyboard branch is an MLP over floats you *can* push continuous values into it but the model has only ever seen `{0,1}`, so the response is undefined. Translation scale is normalised out, so "forward" has one speed. There are no other agents, no object boxes, no map, so you cannot script a scenario. And with no training code released for MG-3, none of this can be fixed by fine-tuning inside the repo — adapting the action space means reimplementing the DMD distillation pipeline from the technical report. Finally, "interactive" in `--interactive` mode means a blocking `input('Please input the mouse action (e.g. `U`):')` prompt once per 40-frame chunk (`pipeline/inference_interactive_pipeline.py:53-60`) — there is no game loop, no socket, no streaming server. The 40 fps figure is a generation-throughput claim, not a demonstrated closed loop.

## Extensibility

- **New trajectory source (the main hook):** replace `get_data` (`utils/utils.py:95-117`) so `extrinsics_all` comes from Isaac Sim / AlpaSim / Alpamayo rather than `compute_all_poses_from_actions`. Everything downstream is trajectory-agnostic. This is a ~30-line change.
- **Metric-scale conditioning:** `compute_relative_poses(..., normalize_trans=...)` at `utils/cam_utils.py:76-79`. Flipping it to `False` is one argument; the checkpoint has never seen unnormalised input, so expect degradation with no retraining path.
- **Vehicle kinematics instead of WASD:** `compute_next_pose_from_action` (`utils/utils.py:38`) is where a bicycle or Ackermann model would go. `WSAD_OFFSET`, `DIAGONAL_OFFSET` and the two mouse sensitivities are module-level constants at `utils/utils.py:8-12` — trivially replaceable, but note that changing them changes the *poses*, not the keyboard bits the model was trained on, so the two conditioning streams will disagree.
- **New action channel (throttle, steering, joint angles):** `ActionModule.__init__` takes `mouse_dim_in` and `keyboard_dim_in` as constructor arguments (`wan/modules/action_module.py:45-46`) — the architecture is parameterised, which is better than most. But the checkpoint fixes them at 2 and 6, and there is no training code. **Blocked without reimplementing training.**
- **Memory policy:** `select_memory_idx_fov` / `select_memory_idx` (`utils/cam_utils.py:298`, `445`) take `fov_half_h`, `fov_half_v`, `memory_num` as arguments. Swapping the retrieval heuristic (e.g. semantic rather than geometric) is a contained change.
- **VAE / speed:** `--vae_type {wan, mg_lightvae, mg_lightvae_v2}`, `--lightvae_pruning_rate`, `--use_int8`, `--compile_vae`, `--use_async_vae` are all CLI flags (`generate.py:65-75`). This is the most serious inference-optimisation surface in the survey.
- **Coupling hotspots:** chunk sizes 57 and 40 hardcoded (`inference_interactive_pipeline.py:480,498`); the `4k+1` frame-count assertion (`utils/conditions.py:9`, `utils/cam_utils.py:470`); intrinsics synthesised by `get_K(height, width)` (`utils/cam_utils.py:209`) rather than taken from a real calibration; `--fa_version 3` requires Hopper-class hardware.

## Hardware and cost

MG-3's README states only "A/H series GPUs", Linux, 64 GB system RAM, and "supports one gpu or multi-gpu inference" — **no VRAM figure is given anywhere**, so treat single-GPU as unverified. What can be measured: the download is ~55 GB (base 12.9 GB + distilled 25.9 GB + T5 11.4 GB + Wan2.2 VAE 2.8 GB + two LightVAEs 3.6 GB). The base DiT at bf16 is ~13 GB of weights; with the umT5-XXL encoder (11.4 GB) resident you are over 24 GB before activations, which is why `--t5_cpu`, `--use_int8` and the distilled LightVAE decoders exist. The repo's own `test.sh` runs **8 GPUs** (`SYNC_GPU_NUM=8`, or 7 plus a dedicated async-VAE worker) with `--dit_fsdp --t5_fsdp --ulysses_size 8` at 704x1280 — that is the configuration the authors actually exercised. MG-2, by contrast, documents a clear "at least 24 GB (A100/H100)".

The only speed number is the README's "**40 fps real-time generation at 720p with a 5B model**", achieved with DMD distillation (`--num_inference_steps 3`), int8 quantisation of q/k/v/o, a distilled LightVAE decoder, `torch.compile`, FlashAttention-3 and asynchronous VAE decoding on a separate rank. There is no benchmark script, no measured wall-clock anywhere in the repo, and no statement of how many GPUs the 40 fps figure assumes. Given `test.sh` uses 7-8 GPUs, assume it is a multi-GPU number until proven otherwise. MG-2 claims 25 fps with a 1.3B model on a single 24 GB card, which is the more credible published datapoint.

## Verdict and next step

**TRIAL.** Matrix-Game-3.0 has the cleanest licence position of any Chinese-lab repo here (verbatim Apache-2.0 code, Apache-2.0 weights, Apache-2.0 Wan2.2 base — I read the licence file rather than the badge, and there is no territorial or user-count rider), and it is the only model in this batch that accepts a full SE(3) extrinsics stream as a named conditioning input alongside its action vector. That makes the Isaac-Sim-owns-physics / world-model-owns-pixels pattern a short integration rather than a research project. The FOV-overlap memory retrieval in `utils/cam_utils.py:298-530` is the single most transferable piece of code in the survey and is worth reading even if we never run the model. Against that: no training code, no evaluation of any kind shipped with MG-3, scale-normalised conditioning, a four-bit-plus-look-rate action space that cannot express throttle or steering, `.pth` pickles for four of six artifacts, and a "real-time interactive" mode that is a blocking `input()` prompt. The concrete next step is a two-week spike: fork `Matrix-Game-3/` only (leave MG-1's vendored DROID-SLAM behind), convert the four `.pth` files to safetensors, replace `get_data` with an Isaac Sim extrinsics exporter, generate a 500-frame rollout along a known camera path, and then **measure what nobody has measured** — re-estimate the camera trajectory from the generated video (ViPE or COLMAP) and report tracking error against the commanded path. That number decides whether the Plücker conditioning is tight enough to use as a renderer for AlpaSim. In parallel, note MG-2 for a separate reason: its GTA driving checkpoint is the only driving-domain interactive model in this batch, it is MIT-licensed, and it documents a 24 GB single-GPU budget at 25 fps.
