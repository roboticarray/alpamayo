## What it is

This is the actual software behind Cosmos 3 — the training and serving framework that `NVIDIA/cosmos` documents. Everything lives in one coherent `cosmos_framework/` package (trainer with FSDP/TP/CP/PP and DCP checkpoints, two inference stacks, model definitions, data adapters for JSONL/WebDataset/LeRobot, quantization, guardrails, and closed-loop simulation harnesses), with two thin ecosystem shims under `packages/` for `transformers` and `vllm`. Two entry points do almost everything: `python -m cosmos_framework.scripts.train` and `python -m cosmos_framework.scripts.inference`. For our purposes the important content is the action stack: a registry of **30+ embodiments** mapped to domain IDs and raw action widths, a declarative native→canonical action schema, ready-made input specs for AV forward dynamics, inverse dynamics and **policy**, and three closed-loop policy servers (LIBERO, RoboCasa, RoboLab). The single biggest structural change from the deprecated generation is that **the vendored `_src/` monolith is gone** — no more imaginaire/predict2/transfer2/reason1 fused into one redacted internal export; this is a normal, readable, tested Python package.

## Security findings

The two patterns the previous pass flagged split: one is fixed, one is not.

- **FIXED — dotted-path RCE via user config.** `load_callable()` still exists (`cosmos_framework/utils/serialization.py:85-94`) but has exactly one caller, `cosmos_framework/utils/config.py:561`, which passes `config.__module__` — an internal value. The Predict2.5 pattern of resolving an arbitrary `action_load_fn` dotted path out of a user-supplied JSON inference file is gone.
- **NOT FIXED — `exec(compile(...))` config loading.** `cosmos_framework/utils/lazy_config/lazy.py:155` and `:217`, reached via `importlib.machinery.ModuleSpec(_random_package_name(cur_file), None, origin=cur_file)` at `lazy.py:150`. A `.py` config is executable code by design. It is still the path for `--config-file` in `scripts/train.py`, `scripts/export_model.py` and all three `scripts/action_policy_server_*.py` (`importlib.import_module(config_helper.get_config_module(setup_args.config_file))`, e.g. `action_policy_server_robocasa.py:447`). **Never accept a config file from outside the team.** The `dill`/`cloudpickle` serialisation fallback at `lazy.py:275-291` is the same story in the save direction.
- **`torch.load(..., weights_only=False)`** — full pickle deserialisation: `cosmos_framework/utils/checkpointer.py:211`, `cosmos_framework/utils/object_store.py:102`, `cosmos_framework/utils/generator/input_probe.py:169`.
- **`torch.load` with no `weights_only`**: `cosmos_framework/utils/checkpointer.py:410`, `cosmos_framework/utils/easy_io/handlers/torch_handler.py:16` (a generic handler, so whatever it is pointed at), `cosmos_framework/scripts/_convert_model_to_diffusers.py:258`, `cosmos_framework/inference2/_convert_model_to_diffusers.py:172`, `cosmos_framework/model/generator/tokenizers/audio/avae.py:148`, `.../dc_ae/convert_pt_to_distcp.py:22`. Much of the tokenizer path *does* pass `weights_only=True` (`model/tokenizer/checkpoint_io.py:156-181`), so this is inconsistency rather than policy.
- **`pickle.loads` on payloads**: `cosmos_framework/callbacks/wall_clock_checkpoint.py:753` (broadcast metadata), `cosmos_framework/data/generator/augmentors/video_editing_transform.py:280` (dataset payload — the webdataset-shard RCE shape from omni-dreams, now narrower), `cosmos_framework/utils/generator/rand_state.py:69,75`, `cosmos_framework/inference/common/args.py:999-1008` (loads a user-named `.pkl` of input tensors).
- **`trust_remote_code` defaults to `True`**: `cosmos_framework/model/generator/hf_model.py:102` (parameter default, used at `:117,:156,:176`) and `cosmos_framework/model/tokenizer/models/text_decoder.py:475,504`. Loading any third-party HF repo through these paths executes its Python. Credit where due: `model/generator/reasoner/cosmos3_edge/__init__.py:8` documents a deliberate move *away* from `trust_remote_code` for the Edge snapshot.
- **`curl … | bash`** at image build: `Dockerfile:34` (`just` 1.46.0, TLS- and tag-pinned) and four `curl -LsSf https://astral.sh/uv/install.sh | sh` in `docs/setup.md:79,148,310` and `docs/faq.md:82`.
- **CI on self-hosted runners with a `pull_request` trigger**: `.github/workflows/gpu-tests.yml:36-39,54` (`[self-hosted, gpu, h200]`) and `docker-build.yml:7,46`. An untrusted fork PR would run on our hardware with an `HF_TOKEN` secret in scope. **Fix this before mirroring the repo internally** — same finding as omni-dreams.
- **Dependency hygiene is good**: `uv.lock` (16k lines) is committed and the Dockerfile uses `uv sync --locked`; `[tool.uv.audit]` is configured. The 20-of-22 unpinned core deps in `pyproject.toml` are therefore not a practical risk as long as you install from the lock.
- No hardcoded tokens, keys or credentials found.

## Physics and dynamics

- **Action representation.** `data/generator/action/utils/action_spec.py` builds specs from a small DSL: `build_action_spec(Pos(), Rot("rot6d"))` → **9D, no gripper** (the AV/ego case), `build_action_spec(Pos(), Rot("rot6d"), Gripper())` → 10D single arm, dual-arm by prefixing. Identity rot6d is `[1,0,0,0,1,0]`, i.e. the first two rows of a 3×3 rotation matrix. `rot9d` (full matrix) and other conventions are supported.
- **Canonical schema.** `unified_action_schema.py` defines `unified_v1`, a 59D superset: `[ego_pose9d, right_wrist_pose9d, right_fingertips15d, right_openness, left_wrist_pose9d, left_fingertips15d, left_openness]`, with `action_valid_mask` for missing slots and validated non-overlapping `UnifiedActionMapping` declarations per dataset. Ego pose occupies slots 0-8 — so an AV trajectory is a strict subset of the canonical contract.
- **Embodiment registry.** `data/generator/action/utils/domain_utils.py` maps 30+ embodiments to domain IDs and raw widths: `av: 9`, `camera_pose: 9`, `umi/bridge/droid/fractal/robomind-franka: 10`, `robotwin/robodojo: 14`, `geniesim3_g2a_joint: 16`, `xdof_yam/maniparena: 20`, `behavior1k: 23`, `agibotworld/embodiment_c: 29`, `webhumanaction_body: 57`. Each domain gets its own `DomainAwareLinear` action↔LLM projector, so embodiments do not interfere.
- **Three modes, and an AV policy that actually exists.** `inputs/omni/` ships `action_forward_dynamics_av.json`, `action_inverse_dynamics_av.json` and **`action_policy_av.json`** — the last with `model_mode: "wam"` (world-action model), `domain_name: "av"`, `action_chunk_size: 60`, `fps: 10`, `image_size: 480`, `view_point: "ego_view"`. That is video + prompt in, **60-step ego trajectory + video out, from the base `Cosmos3-Nano` checkpoint**, with no AV-specific post-training. The prompt is literally `"You are an autonomous vehicle planning system."`
- **Horizon / resolution / fps for AV**: 60 action steps at 10 FPS = **6 seconds**, 480p ego view. Robot policies use chunk 32 at 20 Hz (DROID, RoboCasa) or 16 at 15-20 Hz.
- **Evaluation.** Closed-loop: `cosmos_framework/simulation/libero/closed_loop_eval.py` and `cosmos_framework/simulation/robocasa/closed_loop_eval.py` (+ `eval_utils.py`), driven by `scripts/action_policy_server_{libero,robocasa,robolab}.py` over a websocket protocol. Open-loop regression: the action specs carry `golden_psnr_min: 14.0` and `golden_mse_max: 0.05` in their `extra` block, and `tests/action_policy_regression_test.py` plus the `generator-inference-smoke` CI job check them on every PR. This is the first Cosmos repo where action quality is actually gated in CI.
- **Known failure modes / gaps**: no rigid-body or contact metric; no AV closed-loop environment at all (LIBERO and RoboCasa are manipulation); no multi-camera AV rig; no kinematic feasibility check on a commanded trajectory; `docs/inference.md:77,124` describes Super as "32B" and Edge as "2B" while the model cards say 64B and 4B, which is either stale documentation or an active/total-parameter confusion — resolve it before sizing anything.

## Motion-control assessment

This is the repo to integrate. The AV action contract is **9D = 3D translation + 6D rotation per frame**, and `alpamayo_r1/action_space/action_space.py` already produces `traj_future_xyz (…, T, 3)` and `traj_future_rot (…, T, 3, 3)`. The adapter is short in both directions — `rot[..., :2, :].reshape(*rot.shape[:-2], 6)` to go out, Gram–Schmidt on the two 3-vectors to come back — and it should be written once as an `alpamayo ↔ cosmos_framework` action bridge. Three things to pin down empirically before trusting it: (1) Cosmos consumes **frame-to-frame deltas**, not absolute poses, so Alpamayo trajectories must be differenced and reintegrated; (2) `data/generator/action/action_normalization.py` applies statistics baked into the checkpoint — read them out, do not guess; (3) the rate is 10 Hz over 60 steps, so our horizon and sampling must be resampled to match.

Given that bridge, four integrations open up, in increasing ambition. **(a) Inverse dynamics as an evaluator and label source** — run `action_inverse_dynamics_av.json` over our log corpus, compare the recovered ego trajectory against odometry, and use the residual as a hard-case miner for Alpamayo. Cheapest, no training, immediate value. **(b) Forward dynamics as a neural sensor simulator beside AlpaSim** — feed an Alpamayo-planned trajectory and one real frame, get the counterfactual 6-second ego view; this is the "what would the camera have seen if we had steered left" regression suite that Isaac Sim can only give us with authored assets. **(c) `action_policy_av.json` as a baseline planner** — the base Nano already emits 60-step ego trajectories from video; benchmark it head-to-head against Alpamayo-R1-10B on our own eval set. That comparison is a week of work and tells us whether a 16B omnimodal generalist is competitive with our 10B specialist, which is a strategically important number to have. **(d) An AV policy fine-tune** — the DROID/RoboCasa recipes are the template, the embodiment registry is three declarative edits, and the LeRobot v3.0 dataset format is the only real work.

What is missing for us: no AV closed-loop environment (the two shipped evaluators are manipulation sims, so closing the loop for driving means writing an AlpaSim-backed evaluator against the same websocket policy-server protocol — that protocol is the clean seam and it is documented in `docs/action_policy_droid_server.md`); no multi-camera conditioning for a full AV rig (single `ego_view`); no HD-map, bounding-box or other-agent conditioning, so nothing reacts to us; no kinematic or dynamic feasibility constraint; no Isaac Sim / Isaac Lab / Unreal bridge; and **no stated policy-server latency anywhere in the repo** — for a 16B diffusion-based policy this is the number that decides whether closed-loop AV evaluation is affordable, and it is unclear. Measure it first.

## Extensibility

- **New embodiment / action space**: add an entry to `EMBODIMENT_TO_DOMAIN_ID` and `EMBODIMENT_TO_RAW_ACTION_DIM` (`data/generator/action/utils/domain_utils.py`), declare a `UnifiedActionMapping` (`unified_action_schema.py`) if you want the canonical 59D path, and build the spec with `build_action_spec(...)` (`action_spec.py`). The `__post_init__` validators catch overlapping slices at construction, which is the kind of thing that saves a week. New domain IDs append above the current maximum; the comments explicitly reserve retired gaps (10/11/14/18/19).
- **New dataset**: `docs/custom_dataset.md` and `docs/dataset_jsonl.md`. Adapters exist for JSONL, WebDataset and LeRobot v3.0; `data/generator/action/datasets/cosmos3_action_lerobot.py` is the worked action example. LeRobot is the path of least resistance for our AV logs.
- **New SFT run**: TOML under `examples/toml/` plus a `launch_sft_*.sh`; `docs/sft_config.md` documents the schema and `cosmos_framework/configs/toml_config/sft_config.py` is the parser. The five action post-training configs under `configs/base/experiment/action/posttrain_config/` are the copy-paste starting points.
- **New closed-loop evaluator**: implement against the websocket contract in `scripts/action_policy_server_utils.py` and mirror `simulation/robocasa/closed_loop_eval.py`. This is where an AlpaSim adapter belongs.
- **Serving**: `packages/vllm-cosmos3` and `packages/transformers-cosmos3` are deliberately thin shims for downstream projects — that is the supported way to expose Cosmos 3 from our own service without forking the framework.
- **Coupling hotspots**: `cosmos_framework/inference` and `cosmos_framework/inference2` coexist with overlapping responsibilities (both have a `_convert_model_to_diffusers.py`) and it is not documented which is canonical — expect churn there. `apex` is an optional build-arg dependency (`INSTALL_APEX=0` skips the slowest Docker layer). The LazyConfig `.py` config system and the TOML SFT config system are two parallel config worlds; training SFT uses TOML, everything structural uses LazyConfig.

## Hardware and cost

- **Requirements** (`docs/setup.md`): Linux, Ampere or newer, Hopper/Blackwell recommended; Python 3.13; `uv sync --all-extras --group=cu130-train` (or `cu128-train`); `--ipc=host` for torchrun shared memory.
- **Inference** (`docs/inference.md`): **Edge fits comfortably on a single GPU** and is the recommended single-GPU starting point (no audio — the checkpoint ships without a sound tokenizer). **Super does not fit on one 80 GB H100** and needs 4 or 8 GPUs with FSDP sharding. Nano is the single-GPU workhorse by implication; budget **80 GB**. Two presets: `--parallelism-preset=latency` (context parallelism, split one sample across GPUs; add `--dp-shard-size=1` on multi-GPU) and `throughput` (shard weights, batch it). OOM ladder is documented: `PYTORCH_CUDA_ALLOC_CONF`, then `--dp-shard-size`, `--device-memory-utilization`, `--offload-guardrail-models`.
- **Training**: the shipped `examples/` recipes are **8-GPU configurations tested on 8× H100 80 GB**. The reference DROID policy reproduction documented in the `NVIDIA/cosmos` cookbook is far larger (256 ranks on GB200); RoboCasa is 16 ranks.
- **CI hardware** tells you what the maintainers consider a working box: a self-hosted **4-GPU H200** runner runs the full smoke + regression suite per PR.
- **Guardrails** (`nvidia/Cosmos-Guardrail1` + `Qwen/Qwen3Guard-Gen-0.6B` + RetinaFace) consume unquantified GPU memory; `--offload-guardrail-models` trades latency for it and `--no-guardrails` removes it.
- **No wall-clock or latency figure is stated anywhere in this repo** — including for the policy server. Use `NVIDIA/cosmos`'s `inference_benchmarks.md` for generation latency (Nano 720p t2v ≈ 208 s/189 frames on one H100) and measure the policy path yourself.

## Verdict and next step

**ADOPT.** This is the best-engineered repository in the entire world-models collection and the first one where the Cosmos codebase is genuinely readable: the vendored `_src/` monolith that made Predict2.5 and omni-dreams painful to fork is gone, replaced by a single tested package with GPU CI, golden regressions, a committed lockfile, a working Dockerfile and agent skills. Combined with OpenMDW-1.1 on both code and weights, the licence and maintenance objections that made every prior Cosmos review a TRIAL no longer apply. The action stack is the reason to move now: a 30+ embodiment registry, a canonical action schema whose ego-pose slot is exactly what Alpamayo emits, AV forward-dynamics/inverse-dynamics/policy specs shipped in `inputs/omni/`, and a closed-loop policy-server protocol we can point at AlpaSim. Recommended next step, roughly three weeks: (1) build the image (`docker build --build-arg INSTALL_APEX=0 -t cosmos-framework:latest .`) and run all three `inputs/omni/action_*_av.json` specs on `Cosmos3-Nano` to confirm the environment and capture the golden-threshold results; (2) write the `alpamayo ↔ cosmos` action bridge (`traj_future_xyz`/`traj_future_rot` ↔ 9D delta + rot6d) plus a normalization-statistics extractor, and land it as a small tested module in our tree; (3) benchmark `action_policy_av.json` against Alpamayo-R1-10B on our own eval set and **measure policy-server latency**, because that number decides whether closed-loop AV evaluation is affordable at all; (4) in parallel, before mirroring the repo internally, fix the self-hosted-runner `pull_request` trigger in `gpu-tests.yml` and `docker-build.yml`, and write down a rule that `--config-file` arguments are trusted code.
