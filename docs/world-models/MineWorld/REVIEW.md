## What it is

MineWorld is Microsoft Research's interactive Minecraft world model: a **decoder-only Llama** (`transformers.LlamaConfig`, 20 layers, hidden 2048, `vocab_size: 8262`, `configs/1200M_16f.yaml`) that autoregresses over a single interleaved sequence of **visual tokens and action tokens**. A VQ-VAE encodes each 224x384 frame to 336 tokens (ids 0-8191); each action is tokenised to 11 tokens (including BOS/EOS) drawn from a 70-token action vocabulary at offset 8192; `max_position_embeddings: 5552` is exactly `16 * (336 + 11)`, i.e. a 16-frame context. The action encoding is lifted from OpenAI VPT: ~22 binary keyboard buttons plus a 2-axis camera delta that is **mu-law quantised** into bins (`CameraQuantizer`, `mcdataset.py:149-204`, defaults `camera_binsize=9`, `camera_maxval=90`, `mu=11.4887`). The headline contribution is **Diagonal Decoding** (`diagonal_decoding.py`, its own paper), a parallel decoding scheme that lifts generation to a claimed 4-7 fps for real-time play through a Gradio demo. Uniquely in this batch, it ships a genuine **action-following benchmark**: an OpenAI VPT inverse-dynamics model recovers actions from the generated video and compares them to the commanded ones, alongside FVD/LPIPS/SSIM/PSNR. There is no training code.

## Security findings

- `inference.py:90` — `line = eval(line.strip(), {"__builtins__": None}, safe_globals)` on every line of the user-supplied action `.jsonl`. Passing `{"__builtins__": None}` is a **well-known weak sandbox**, bypassable through attribute traversal on any object reachable from `safe_globals`. This should be `json.loads`; the file is line-delimited JSON.
- `metrics/common_metrics.py:67` — `args.size = eval(args.size)` on a command-line string, with no sandbox at all.
- `inference.py:79` — `os.system(f"cp {input_action_path} {output_action_path}")`. A shell invocation built by f-string from paths that come from `--data_root`. `shutil.copy` exists.
- `metrics/IDM/inverse_dynamics_model.py:254` — `agent_parameters = pickle.load(open(model, "rb"))`, on `4x_idm.model`, which `scripts/setup_metrics.sh` downloads over `wget` from `openaipublic.blob.core.windows.net`. **A distributed pickle, unpickled by design**, exactly the pattern flagged in OpenDWM's LiDAR path. This is inherited from VPT, but it is in this tree.
- `vae.py:26` — `torch.load(path, map_location="cpu", weights_only=False)`, explicit opt-out. `utils.py:55,57` — `torch.load(ckpt)` and `torch.load(ckpt, map_location="cpu")["state_dict"]` with no `weights_only` at all, on the `.ckpt` files the README tells you to download.
- `scripts/setup_metrics.sh:2` — `git clone git@github.com:CIntellifusion/common_metrics_on_video_quality.git`, an **unpinned clone of a personal third-party repository over SSH**. The SSH URL will fail for most users (no deploy key), and there is no commit pin, so the metric implementation can change under you. Whatever FVD number you reproduce is not tied to a known revision.
- **Good:** `requirements.txt` pins every dependency exactly (`torch==2.6.0`, `transformers==4.48.1`, `diffusers==0.32.2`, `gradio==5.24.0`, ...) — better than most of this batch. No `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens or credentials. Microsoft ships `SECURITY.md`, `SUPPORT.md` and `CODE_OF_CONDUCT.md`.
- No `.github/` workflows, no tests, no CI. 26 Python files, 20 of which are the vendored VPT IDM.

## Physics and dynamics

- **Action space, precisely.** Two parts, both discrete by the time the model sees them:
  1. **Buttons** — a ~22-entry `NOOP_ACTION` dict (`mcdataset.py:39-60`): `forward`, `back`, `left`, `right`, `jump`, `sneak`, `sprint`, `attack`, `use`, `drop`, `inventory`, `swapHands`, `pickItem`, `ESC`, `hotbar.1`-`hotbar.9`. All binary. Mutually contradictory pairs are zeroed (`forward`+`back`, `left`+`right`, `mcdataset.py:273-278`).
  2. **Camera** — a continuous `(dy, dx)` pitch/yaw delta in degrees, clipped to `±90`, then run through `CameraQuantizer.discretize` (`mcdataset.py:182-192`) with **mu-law** companding (`mu=11.4887`) and a linear bin size of 9 degrees. Mu-law gives fine resolution near zero and coarse resolution at the extremes — a sensible choice for a mouse, and exactly wrong for a vehicle whose interesting steering range is not centred on zero.
- **Everything becomes tokens.** `get_action_index_from_actiondict(line, action_vocab_offset=8192)` maps the action dict to indices in a 70-token vocabulary appended to the 8192-token visual codebook. **This is the hardest action space in the survey to repurpose**: it is not an MLP over floats (Matrix-Game), not a Plücker map (lingbot-world), not a pose matrix (minWM's PRoPE). It is a fixed embedding table. Substituting a continuous vehicle control means new tokens, a resized embedding and retraining — and there is no training code.
- **Horizon / resolution / fps.** 224x384 frames, 336 visual tokens each. Context is 16 or 32 frames (`max_position_embeddings: 5552` = `16 * 347`). Generation is frame-by-frame autoregressive with KV cache; the Gradio demo shows the last 8 frames plus the newest. Claimed **4-7 fps** with Diagonal Decoding, versus naive autoregressive decoding — the repo exposes both via `--accelerate-algo {naive, image_diagd}`. There is no long-horizon memory mechanism beyond the 16/32-frame attention window; this is the shortest context in the batch.
- **Evaluation is the best part of the repo, and it is the reason to read it.** `scripts/compute_metrics.sh` runs two families: (a) video quality — FVD, LPIPS, SSIM, PSNR via a cloned third-party harness; (b) **action-following accuracy** — OpenAI VPT's 4x inverse-dynamics model watches the *generated* video, infers what actions were taken, and compares them against the actions that were commanded (`metrics/IDM/inverse_dynamics_model.py`). Results aggregate to `metrics_log/latest_metrics.csv`. This closed IDM loop is precisely the controllability measurement that OpenDWM, lingbot-world and Matrix-Game all lack, and the idea transfers directly to driving: re-estimate the ego trajectory from generated video and compare it to the commanded one.
- **Failure modes, stated by Microsoft** in the README's "Risks and Limitations": Minecraft only, fixed low resolution, cannot generate other video domains, "the input of other images than Minecraft will result in incoherent imagery being created and should not be attempted", research/experimental only.

## Motion-control assessment

There is no integration path. The weights do not exist, the action space is a frozen token vocabulary tied to Minecraft's button set, the camera is mu-law-quantised around zero, the context is 16 frames, and the resolution is 224x384. Nothing about this connects to Isaac Sim, AlpaSim or Alpamayo, and pretending otherwise would be dishonest. Per the brief: **this repo's only value is architecture worth copying, and it is scored accordingly.**

Two ideas are worth the hour it takes to read them. The first is **Diagonal Decoding** (`diagonal_decoding.py`, 22 KB, its own paper at arXiv 2503.14070): a way to parallelise autoregressive token generation across the spatial and temporal axes so a next-token video model can run at interactive rates without distillation. Every other real-time model in this survey gets there through few-step diffusion distillation (DMD, Self-Forcing); this gets there through a decoding schedule, which is orthogonal and cheaper to try. If we ever build a token-based world model, this is the decoding strategy to evaluate.

The second, and the more immediately useful, is the **IDM-based action-following benchmark**. Everyone in this batch reports FVD; FVD measures whether the video looks like the training distribution and says nothing about whether the model did what it was told. MineWorld closes the loop with an inverse dynamics model and reports controllability as a number. The driving analogue is straightforward and we should build it regardless of which world model we adopt: run a pose estimator (ViPE, COLMAP) or a learned inverse-dynamics model over the generated video, recover the ego trajectory, and report tracking error against the commanded trajectory. That single metric would let us rank every other repo in this survey on the axis we actually care about. MineWorld's contribution to roboticarray is that metric design, not its model.

## Extensibility

- **Adding a continuous action channel:** requires extending the action vocabulary beyond 70 tokens, resizing the Llama embedding from `vocab_size: 8262`, and retraining. **Blocked — no training code, no weights to fine-tune from.**
- **Changing the camera quantisation:** `CameraQuantizer` (`mcdataset.py:149`) is cleanly parameterised — `camera_binsize`, `camera_maxval`, `quantization_scheme` (linear or mu-law), `mu` — with a helpful table of mu values for given precision targets in the docstring. Genuinely reusable code if we ever tokenise a continuous control.
- **Changing model size / context:** five omegaconf YAMLs in `configs/` differing in `hidden_size`, `num_hidden_layers` and `max_position_embeddings`. Clean, but every one points at a checkpoint that does not exist.
- **Swapping the decoder:** `--accelerate-algo {naive, image_diagd}` at `inference.py`, with a third `vid_diagd_generate` path in `lvm.py:500`. Self-contained enough to lift.
- **New dataset:** `mcdataset.py` is Minecraft-specific end to end (VPT JSON action format, MineRL key mapping). Not a dataset abstraction.
- **Coupling hotspots:** `action_vocab_offset=8192` is passed as a literal at `inference.py:91`; `action_length=11` and the VAE's 336-tokens-per-frame must both match `max_position_embeddings`; `scripts/setup_metrics.sh` needs an SSH key for a third-party GitHub account.

## Hardware and cost

The README says only: "We recommend using high-end GPU for inference. We have done all testing and development using A100 and H100 GPU." **No VRAM figure is published.** By inspection the largest model is 1.2B parameters, loaded at `float16` (`utils.py:60`, `model.to(torch.float16)`) with a bfloat16-configured transformer, plus a VQ-VAE — so the weights are roughly 2.5 GB and a 5552-token KV cache is small. This should run comfortably on a single 24 GB card; the A100/H100 recommendation is presumably about achieving the interactive frame rate, not about fitting the model. The speed claim is **4-7 frames per second** with Diagonal Decoding, which if real makes this the only genuinely single-GPU real-time model in the batch. None of it is verifiable: there are no weights to load. The Gradio demo additionally warns that "initialization and the first action may take some time due to compilation".

## Verdict and next step

**SKIP.** The decisive fact is not a licence or an architecture judgement — it is that the checkpoints were withdrawn from Hugging Face in May 2025 and `microsoft/mineworld` still returns 404 sixteen months later. There are no weights, no validation data, no Gradio scene, and no training code, so this repository cannot produce a single output; every score above is an assessment of source code that has nothing to run on. Even if the weights returned tomorrow, the model is 224x384 Minecraft with a 16-frame context and an action space frozen into a 70-token vocabulary, which is the least adaptable conditioning scheme in this survey, and Microsoft's own "Out-of-scope Uses" section says non-Minecraft inputs "should not be attempted". Do not plan work on this. The recommended next step is a reading exercise, not an engineering one: spend an hour on `diagonal_decoding.py` (and arXiv 2503.14070) to understand parallel autoregressive decoding as an alternative to diffusion distillation for real-time generation, and then **steal the evaluation design** — build the driving analogue of the IDM action-following benchmark, where a pose estimator recovers the ego trajectory from generated video and we report tracking error against the commanded trajectory. That metric is the thing this survey is missing, MineWorld is where the idea is best demonstrated, and it costs us nothing to adopt it into the evaluation of whichever model we do pick.
