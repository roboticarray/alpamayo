## What it is

Genie Envisioner is AgiBot's three-part manipulation world-model platform built on a multi-view LTX-Video 2B backbone (plus a second Cosmos-Predict2-2B backbone for GE-Sim). **GE-Base** is the video world model: it takes 4 sparse "memory" frames from 3 synchronised cameras (`observation.images.top_head`, `hand_left`, `hand_right`) plus a T5-encoded language instruction and generates a multi-view future at 192x256 per view, in "slow" (action-synchronised) and "fast" (low-latency) variants. **GE-Act** bolts a small action expert (`action_expert: true`, `action_in_channels: 14`, `models/action_patches/patches.py`) onto the same transformer, so the model **produces** 54-step action chunks in joint or end-effector space rather than merely consuming them — this is a genuine world-action model, not an action-conditioned video model. **GE-Sim** inverts the arrow: it takes an end-effector action sequence plus per-frame camera extrinsics/intrinsics (`gesim_video_gen_examples/infer_gesim.py:156-227`), renders the action as a projected trajectory map (`utils/get_traj_maps.py`) and generates the resulting video at 384x512 — an action-conditioned neural simulator. Closed-loop policy evaluation is shipped and scored: `experiments/eval_calvin.py` and `experiments/eval_libero.py` drive real CALVIN/LIBERO environments with `env.step()` and `experiments/RUN.md` reports 4.26 avg subtasks on CALVIN and 0.965 average success on LIBERO. Data comes in via LeRobot parquet, AgiBot World, or LIBERO-RLDS-converted-to-LeRobot.

## Security findings

- `main.py:22-24` + `utils/__init__.py:50-90` — `import_custom_class(args.runner_class, args.runner_class_path)` loads a class from an **arbitrary filesystem path** given on the command line, and every config does the same for the dataset, VAE, transformer, scheduler and pipeline (`configs/ltx_model/policy_model_lerobot.yaml:11-28`). A YAML config is therefore executable content. Review any config before running it; this is the same class of risk as OpenDWM's `_class_name` resolution but narrower (paths, not arbitrary importable modules).
- No `torch.load` anywhere in the repo. Weight loading is `safetensors.torch.load_file` only (`utils/model_utils.py:35,68`) — better than every other repo in this batch.
- No `pickle.load`, no `eval(`/`exec(`, no `os.system`, no `subprocess`, no `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens or credentials. `web_infer_utils/openpi_client/msgpack_numpy.py` deliberately uses msgpack *instead of* pickle for the policy-server wire format, and says so at line 4.
- The GE-Act deployment server (`web_infer_scripts/run_server.sh`) binds a websocket policy server with no authentication; `IP_ADDRESS_OF_SERVER="localhost"` is the default, keep it that way or put it behind something.
- Dependency hygiene is good: 35 of 38 entries in `requirements.txt` are exact `==` pins (`torch==2.7.1`, `diffusers==0.32.0`, `transformers==4.51.3`, `xformers==0.0.31.post1`). Only `tensorboard`, `fastparquet` and `av` float. `PyYAML==6.0.2` is duplicated. No lockfile, no hashes.
- Vendored third-party code (`models/ltx_models`, `models/cosmos_models`, `web_infer_utils/openpi_client`) is copied, not pinned to an upstream commit — security fixes upstream will not reach this fork.

## Physics and dynamics

- **Action space (out)**: GE-Act emits a chunk of `action_chunk: 54` actions with `action_in_channels: 14`. For a dual-arm AgiBot platform that is 6-DoF pose + gripper per arm; `data/utils/get_actions.py:14-56` builds `[xyz, rpy, gripper]` x2 for the `eef` space, and `get_actions_joint` (line 59+) builds `[7 joints, gripper] x 2` for the `joint` space. `action_type` selects `absolute`, `delta` or `relative`; the delta variant differences consecutive poses and wraps angles through `normalize_angles`. Gripper is carried as a raw continuous channel, not binarised.
- **State (in)**: `add_state: True` concatenates `observation.state` to the action chunk, so the policy is state-conditioned.
- **Action space (in, GE-Sim)**: `action_in_channels: 7` in `configs/cosmos_model/acwm_cosmos.yaml:77` — a single-arm `xyz + quat` end-effector pose, per frame. The action is injected two ways: as a conditioning token stream (`action_cond_mode: true`) and, more interestingly, by **projecting the future EE trajectory into each camera image** (`utils/get_traj_maps.py`) so the model sees where the hand will go. Camera extrinsics per frame are required; `README.md` ships a `get_cam2base` helper that derives them from an EE pose sequence plus one initial camera-to-base extrinsic.
- **Horizon / resolution / fps**: GE-Base/GE-Act at 192x256 per view, `chunk: 9` generated latent frames per iteration against `action_chunk: 54` actions, 4 memory frames. GE-Sim at 384x512, `chunk: 25` (the 4n+1 Cosmos constraint), `action_chunk: 25`. Effective video fps is derived, not configured: `runner/ge_trainer.py:838` computes `fps = basic_fps(30) / (action_chunk // chunk)`, so the slow model renders at 5 fps against a 30 Hz action stream. Long rollouts are autoregressive over the memory buffer (`experiments/eval_libero.py:268-284`).
- **Evaluation**: closed-loop success rate in real simulators, which is exactly the right metric and rare in this batch. CALVIN: 0.950/0.898/0.857/0.808/0.747 for chains of length 1-5, 4.26 avg subtasks. LIBERO: goal 0.958, object 0.976, long-10 0.944, spatial 0.982. Video quality is evaluated separately through the authors' EWMBench, which lives in a different repo.
- **Known failure modes**: the README itself recommends a task-specific "video adaptation" stage before action post-training for unseen robots, i.e. zero-shot transfer to a new embodiment is weak. The memory buffer is only 4 frames with `previous_pick_mode: 'random'`, so anything outside that window is forgotten. GE-Sim needs per-frame camera extrinsics that a real deployment usually does not have, hence the `get_cam2base` workaround. No contact, force or mass modelling of any kind.

## Motion-control assessment

This is the closest thing in the batch to what roboticarray actually wants architecturally: a shared visual backbone that is simultaneously a simulator (GE-Sim) and a policy (GE-Act), with the loop demonstrably closed in CALVIN and LIBERO. The Isaac Lab integration path is short and obvious. `experiments/eval_libero.py` already defines the whole contract: a class with `play(obs, prompt, excution_step, state)` that takes `v x 3 x H x W` uint8 images plus a proprioceptive state vector and returns an action chunk, driven by a loop that calls `env.step()`. Swapping the LIBERO env for an Isaac Lab `ManagerBasedRLEnv` is a ~100-line adapter: map Isaac camera sensors to the three `valid_cam` names, map `env.scene["robot"].data.joint_pos` to `observation.state`, and feed the returned chunk into a joint-position action term. `exec_step=8` of a 54-step chunk is the receding-horizon rate they use.

GE-Sim is the other half: give it an EE action sequence and camera poses and it renders the consequence. That makes it usable as a *learned* alternative to Isaac's renderer for appearance domain randomisation, or as a cheap pre-screen for candidate trajectories before you pay for a physics rollout. `get_cam2base` in the README is precisely the transform Isaac already knows exactly, so the extrinsics input is free on our side.

What blocks it. First and decisively: **CC BY-NC-SA 4.0**. Non-commercial kills product use, and share-alike means any derivative we build would have to be published under the same terms. There is not even a `LICENSE` file — only a README paragraph — so the boundary between the Apache-2.0 vendored directories and the NC original code is a judgement call we would be making, not one the authors made for us. Second, the embodiment is hard-wired to a 3-camera dual-arm humanoid-style rig with 14-D actions; retargeting to a different arm count or DoF means retraining, not reconfiguring. Third, GE-Sim weights are ModelScope-only, which is an awkward dependency for a build pipeline. Fourth, there is no reported inference latency anywhere in the repo — the "fast" GE-Base exists specifically for low-latency use but no number is given, so real-time control claims are unverified here.

## Extensibility

- **New dataset**: write a class under `data/` and point `train_data_class_path`/`train_data_class` at it (`configs/ltx_model/policy_model_lerobot.yaml:11-14`). Three already exist: `data/lerobot_like_dataset.py` (`CustomLeRobotDataset`, standard LeRobot parquet + per-camera mp4 chunks), `data/agibotworld_dataset.py`, `data/libero_dataset.py`. A LeRobot dataset needs only `data_roots`, `domains`, `valid_cam`, `action_key`, `state_key` plus a statistics JSON from `scripts/get_statistics.py`.
- **New action space**: `action_space` (`joint`|`eef`) and `action_type` (`absolute`|`delta`|`relative`) are config fields consumed by `data/utils/get_actions.py`; a new space means a new `get_actions_*` function there plus a matching `action_in_channels` in the diffusion-model config. Normalisation is meanstd from the stats JSON (`action_norm_type="meanstd"`, `runner/ge_inferencer.py:45`).
- **New camera / view count**: `valid_cam` is a plain list; the multi-view attention (`models/ltx_models/transformer_ltx_multiview.py`) is built over however many views you name. Changing it requires retraining but not a rewrite.
- **New backbone**: already demonstrated — `configs/cosmos_model/acwm_cosmos.yaml` swaps the entire LTX stack for Cosmos-Predict2 by changing class paths. This is the strongest evidence the abstraction is real.
- **Coupling hotspots**: `device="cuda:0"` hardcoded in `runner/ge_inferencer.py:45`, `experiments/eval_libero.py:51`, `experiments/eval_calvin.py:181`, `gesim_video_gen_examples/infer_gesim.py:57`, `video_gen_examples/infer.py:54`, `web_infer_utils/MVActor.py:60` — multi-GPU inference needs edits. The `fps = basic_fps / (action_chunk // chunk)` relation at `runner/ge_trainer.py:838` silently couples video rate to action rate. Every config ships with `PATH_TO_*` placeholders that must be filled before anything runs.

## Hardware and cost

Nowhere stated in the repo — no VRAM table, no GPU count, no wall-clock latency, which is a real gap. Inferred: the backbone is LTX-Video 2B and the checkpoints are 3.9 GB in bf16, so single-view inference should fit in ~24 GB, but the model runs 3 views x 9 latent frames jointly with `enable_tiling`/`enable_slicing` on the VAE and `gradient_checkpointing: True` — budget 40-80 GB for comfort and assume 80 GB for training. Training is explicitly multi-node: `scripts/train.sh` fans out over `$WORLD_SIZE` nodes x 8 GPUs with DeepSpeed ZeRO stage 2 and `batch_size: 8` per rank. Inference is single-GPU (`scripts/infer.sh` hardcodes `--nproc_per_node 1`). Denoising is short — `num_inference_step: 5` for the policy config, `--denoise_step 10` on the server — so latency should be far better than a typical video diffusion model, but no one measured it in this repo.

## Verdict and next step

**TRIAL, strictly as a research and benchmarking exercise.** Technically this is the best-aligned repo in the batch for motion control: it is the only one that both emits controls and simulates them, the only one with published closed-loop success rates, the code is genuinely config-driven, and the security posture (safetensors only, no pickle, msgpack wire format) is the cleanest here. But the licence is a wall — CC BY-NC-SA 4.0 with no `LICENSE` file, plus revenue-capped LTX weights underneath — so nothing derived from it can ship, and share-alike makes even internal derivative work legally awkward to keep. The right spike is two weeks: port `experiments/eval_libero.py`'s `play()` contract onto an Isaac Lab `ManagerBasedRLEnv` with a Franka or dual-arm asset, run GE-Act zero-shot to measure how far a 14-D AgiBot-trained action head transfers, and separately feed a known Isaac trajectory + exact extrinsics into GE-Sim to see whether the rendered result is good enough to fool a perception model. Both answers are worth having. What we should copy outright is the *architecture* — a shared backbone with a detachable action expert, receding-horizon chunk execution at `exec_step=8`, and the openpi msgpack policy-server interface — none of which is encumbered, since it is an idea rather than their code. Do not plan on the weights. Ask AgiBot for a commercial licence if the trial goes well.
