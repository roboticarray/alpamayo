## What it is

open-oasis is a **six-file reference implementation** of Oasis 500M, a downscaled release of Decart and Etched's interactive Minecraft world model. Architecture: a ViT-L/20 VAE encodes 360x640 frames into an 18x32x16 latent, and a causal spatio-temporal DiT (`DiT-S/2`: patch 2, hidden 1024, depth 16, 16 heads, ~500M params, `dit.py:325-332`) denoises frame-by-frame in **Diffusion Forcing** style — each context frame is held at a low fixed noise level (`stabilization_level = 15`) while only the newest frame is denoised through 10 DDIM steps, over a sliding 32-frame window (`generate.py:83-116`). Action conditioning is a 25-dimensional float vector per frame — 23 binary Minecraft buttons plus `cameraX`/`cameraY` normalised to `[-1,1]` (`utils.py:30-79`) — projected by a **single `nn.Linear(25, 1024)`** whose output is *added to the diffusion timestep embedding* and thereby drives AdaLN modulation in every block (`dit.py:226`, `dit.py:308-310`). There are no tests, no CI, no requirements file, no training code, no evaluation, and the last commit is from November 2024.

## Security findings

- `utils.py:111` — `actions = one_hot_actions(torch.load(path))` for `*.actions.pt` files, **no `weights_only`**. The very next branch, `utils.py:113`, does pass `weights_only=True` for `*.one_hot_actions.pt`. So the safe flag was applied to one branch and not the other; the repo ships four `*.actions.pt` files in `sample_data/` that exercise the unsafe branch. One-word fix.
- `generate.py:31,41` — both `torch.load` calls pass `weights_only=True`, and both prefer `safetensors.torch.load_model` when the extension is `.safetensors`, which is what the published checkpoints are. **This is the correct pattern and it is rare in this batch.**
- **No other findings.** I grepped the whole tree: no `pickle` import, no `eval(`, no `exec(`, no `os.system`, no `subprocess`, no `trust_remote_code`, no curl-pipe-sh, no hardcoded tokens, keys or URLs with credentials. For a 2024 research drop this is an unusually clean security posture and it deserves saying.
- **Dependency management is the real weakness: there is none.** No `requirements.txt`, no `pyproject.toml`, no lockfile. The README's entire install is `pip install torch torchvision --index-url .../cu121` followed by `pip install einops diffusers timm av` — four unpinned packages and an unpinned torch. Two years on, `diffusers` and `timm` have both had breaking releases; reproducing this build means pinning versions yourself by trial and error.
- `generate.py:18-19` — `assert torch.cuda.is_available()` and `device = "cuda:0"` at **module import time**. Importing anything from this file on a CPU box raises; there is no device flag. A papercut, not a vulnerability, but it means the code cannot be unit-tested without a GPU, which is presumably part of why there are no tests.
- No `.github/` directory, no CI, no tests. Six Python files, three of which (`attention.py`, `rotary_embedding_torch.py`, `vae.py`) are adapted third-party code with attribution in the docstrings.

## Physics and dynamics

- **Action space, precisely — and this is the interesting part.** A single `[T, 25]` **float** tensor. The 25 slots (`ACTION_KEYS`, `utils.py:30-56`) are: `inventory`, `ESC`, `hotbar.1`-`hotbar.9`, `forward`, `back`, `left`, `right`, **`cameraX`**, **`cameraY`**, `jump`, `sneak`, `sprint`, `swapHands`, `attack`, `use`, `pickItem`, `drop`. Twenty-three are asserted to be in `[0,1]` and are binary in practice; **`cameraX` and `cameraY` are continuous in `[-1,1]`**. There is no tokenisation, no embedding lookup, no codebook — just floats.
- **The conditioning mechanism is the minimal one.** `self.external_cond = nn.Linear(external_cond_dim, hidden_size)` (`dit.py:226`), then in the forward pass `c = self.t_embedder(t); if torch.is_tensor(external_cond): c += self.external_cond(external_cond)` (`dit.py:306-310`), and `c` is the AdaLN modulation vector for every `SpatioTemporalDiTBlock`. **One linear layer, added to the timestep embedding.** That is the whole action encoder. Nothing else in this survey is this legible.
- **A trap in the camera normalisation.** `one_hot_actions` (`utils.py:66-73`) computes `max_val = 20`, `bin_size = 0.5`, `num_buckets = int(max_val / bin_size)` = 40, then `value = (value - num_buckets) / num_buckets`. Read that carefully: the *input* `current_actions["camera"][i]` must already be a **bucket index in `[0, 80]`**, not degrees — otherwise the `assert -1 <= value <= 1` fires. The variable names (`max_val`, `bin_size`) imply degrees and mislead. Anyone writing a converter from a real control signal will get this wrong on the first attempt; the `.one_hot_actions.pt` files bypass it entirely.
- **Horizon / resolution / fps.** 360x640 frames (hard-resized in `load_prompt`, `utils.py:100`), 18x32 latent with 16 channels, `max_frames = 32` sliding window (`dit.py:211`), default output 32 frames written at **20 fps** — so the model's entire memory is **1.6 seconds**. This is by far the shortest context in the survey and there is no memory mechanism of any kind: no KV cache retrieval, no frustum selection, no sink tokens.
- **Diffusion Forcing scheduling.** Context frames are pinned at `stabilization_level = 15` while the newest frame walks down `ddim_noise_steps = 10` levels from `max_noise_level = 1000` on a sigmoid beta schedule (`generate.py:48-54, 92-116`). Noise is clamped to `noise_abs_max = 20`. This is a clean, short, correct implementation of the technique that everything else in this batch (Self-Forcing, causal ODE/CD, DMD) is a descendant of.
- **Evaluation: none.** No metrics, no benchmark, no numbers, no comparison, not even a qualitative table. The README's evidence is two GIFs. This is the only repo in the batch with *zero* evaluation.
- **Known failure modes:** none documented. Inferred from the architecture: 1.6 s of memory means anything you look away from is regenerated from scratch; 500M is explicitly "a downscaled version" of the model behind the live demo, so quality is below what the marketing shows; the fixed 360x640 resize means non-16:9 prompts are distorted.

## Motion-control assessment

**There is no integration path, and the repo's only value is architectural — say it plainly.** Oasis 500M is a 22-month-old, downscaled, Minecraft-only demo with a 1.6-second context, no evaluation and no training code. It cannot be driven by a planner, cannot be evaluated against ground-truth dynamics, and has nothing to do with vehicles or robots.

What it does have is the clearest answer in this entire survey to the question "how do you attach an action space to a video diffusion transformer?" The answer, in three lines: make the action a fixed-width float vector, project it with `nn.Linear(action_dim, hidden)`, and add it to the timestep embedding so it modulates AdaLN everywhere. Two of Oasis's 25 dimensions are already continuous, which proves the mechanism does not care whether the signal is a button or a real number — a throttle, a steering angle, a joint velocity or a full 6-DoF twist would drop into the same vector with no architectural change at all. Contrast this with MineWorld (a frozen 70-token vocabulary, unrepurposable), Matrix-Game (an MLP but split across three heterogeneous streams), lingbot-world (Plücker maps, elegant but scale-normalised), and minWM (PRoPE, powerful but 200 lines of machinery). If we are building our own action-conditioned world model — which after reviewing minWM looks like the right move — Oasis is the 40 lines to start from and minWM is the training framework to grow it in.

The one practical caution to carry forward: `external_cond_dim` is fixed at construction and the `nn.Linear` is sized to it, so every change to our action-vector layout invalidates the checkpoint. Design the vector once, with spare slots, before training anything.

## Extensibility

- **Change the action space:** `external_cond_dim=25` is a `DiT.__init__` argument (`dit.py:209`). Set it to whatever our control vector needs and the `nn.Linear` resizes. Requires retraining — and **there is no training code**, so this is a fork-and-write-your-own-trainer operation. Pair with minWM.
- **Feed continuous values into the existing 25 slots:** zero code change. The `assert 0 <= value <= 1` in `one_hot_actions` (`utils.py:75`) is the only guard, and the `.one_hot_actions.pt` path skips it entirely — you can hand `load_actions` any `[T,25]` float tensor. Out of distribution for the 23 binary slots, in-distribution for `cameraX`/`cameraY`.
- **Change the horizon:** `max_frames=32` (`dit.py:211`) sets the sliding window; the temporal rotary embedding scales with it, but the checkpoint was trained at 32 and will degrade beyond it.
- **Change resolution:** `input_h=18, input_w=32` (`dit.py:202-203`) must match `360//20, 640//20` from the ViT-L/20 VAE, and `load_prompt` hard-resizes to `(360, 640)` (`utils.py:100`). Three places to keep in sync.
- **Sampler:** the DDIM loop is inline in `generate.py:92-116`, not abstracted. Easy to read, easy to modify, impossible to swap without editing the script.
- **Coupling hotspots:** `scaling_factor = 0.07843137255` hardcoded in `generate.py:70,120` (it is `1/12.75`, the VAE latent scale); `device = "cuda:0"` and `torch.manual_seed(0)` hardcoded (`generate.py:19,24-25`); the camera bucket-index convention in `one_hot_actions` is undocumented; `DiT_S_2()` passes `depth=16` while the class default is 12, so reading the class signature alone tells you the wrong model size.

## Hardware and cost

**Nothing is documented** — no VRAM figure, no GPU recommendation, no timing, no throughput. By inspection: a 500M DiT plus a ViT-L VAE, run under `autocast(dtype=torch.half)` with batch size 1 over an 18x32 latent and at most 32 frames of context. That is roughly 1 GB of weights and a small activation footprint; it should run comfortably on a **single 8-12 GB consumer GPU**, and is by a wide margin the cheapest model in this survey. Generation cost is `(total_frames - n_prompt_frames) x ddim_steps` forward passes — 310 for the default 32-frame clip at 10 DDIM steps — over a context that grows to 32 frames. No real-time claim is made anywhere in the repo; the interactive experience the blog post advertises is the *large* Oasis model running on Etched's hardware, not this checkpoint. Treat any Oasis latency number you have seen as belonging to the hosted demo, not to this code.

## Verdict and next step

**SKIP as a dependency.** open-oasis is a two-year-old, unmaintained, deliberately downscaled 500M demo of a Minecraft model with a 1.6-second memory and no evaluation whatsoever; there is no version of our roadmap in which we deploy or fine-tune it, and with no training code and no requirements file even reproducing it is an afternoon of dependency archaeology. It earns its 2.5 almost entirely on hygiene — genuine MIT for code *and* weights, safetensors checkpoints, `weights_only=True` in three of four load sites, and not a single `eval`, `pickle` or `trust_remote_code` in the tree, which is better than every other repo reviewed here. The reason to keep the clone is forty lines of architecture: `utils.py:30-79` (a 25-dim float action vector with two continuous camera channels), `dit.py:226` (`nn.Linear(external_cond_dim, hidden_size)`) and `dit.py:306-310` (add it to the timestep embedding so it modulates AdaLN everywhere). That is the minimal, correct, provably-continuous-capable way to attach an action space to a video DiT, and it is the pattern to copy when we build our own conditioning head inside minWM. Concrete next step: no engineering on this repo. Read those three sites alongside minWM's PRoPE injection (`minwm/modeling/wan21/model.py:291-308, 470-472`), decide which conditioning style we want for a driving action vector (throttle, steering, plus 6-DoF ego twist), and fix that vector's layout *before* any training run — because `external_cond_dim` is baked into the checkpoint and every later change to it throws the weights away.
