## What it is

This is the missing inference half of `nv-tlabs/omni-dreams` — and it turned out to be far more than that. FlashDreams is a high-performance runtime and serving library for **interactive autoregressive video and world models**: it began as the optimized runtime behind NVIDIA's OmniDreams closed-loop driving demo at GTC 2026 and has grown into a general platform with nine first-party model integrations (OmniDreams, Self-Forcing, LingBot-World, Waypoint, Wan2.1/2.2, Causal-Forcing, Causal Wan2.2 MoE, FlashVSR, Cosmos-Predict2.5) behind one protocol-based application layer. The architecture is four clean layers — `api_v2` protocols (`IApplication`/`ISession`/`IModelLoop`/`IUILoop`), `runtime_v2` (lifecycle, two-thread session loop, event buffering, presentation), integrations, and client windows (MP4, WebRTC, native Vulkan). The part that matters for us is `apps/interactive_drive`: a real closed driving loop where keyboard/gamepad/steering-wheel input feeds an **ego-vehicle kinematic model with collision handling and ground snapping**, which produces rig poses, which render the HD map, which condition the world model, which renders the next chunk — at a default **30 fps** target. It is the only repository in this collection that closes a driving control loop in real time.

## Security findings

**No concrete issues found in first-party code.** This is the only repo in the collection where that sentence is unqualified, and it was verified rather than assumed:

- `pickle` / `cloudpickle` / `dill`: **zero occurrences** anywhere in the repository.
- `exec(compile(...))` / dynamic `.py` config execution: **absent**. The config system is typed Python dataclasses composed with `derive_config()` (`integrations_v2/omnidreams/config.py`), not executed files. **Both patterns flagged in the previous Cosmos pass — the `exec(compile(...))` LazyConfig loader and the dotted-path config RCE — do not exist here.**
- `trust_remote_code`: **zero occurrences**, including in docs.
- `os.system` / `subprocess(..., shell=True)`: **zero occurrences**.
- `curl … | sh` / `| bash`: **zero occurrences** in the Dockerfile, scripts or docs. `uv` is copied from `ghcr.io/astral-sh/uv` rather than curl-installed.
- `torch.load`: ~20 call sites, and every production path passes `weights_only=True` — `flashdreams/core/checkpoint/load.py:599,756,1095`, `recipes/cosmos/transformer/impl/network.py:515`, `omnidreams/impl/_drift_corrector.py:308,522`, `omnidreams/impl/_edit_lora.py:97`, `omnidreams/impl/omnidreams_singleview/python/vae_weights.py:277`, `omnidreams/impl/ludus-renderer/ludus_renderer/scene_cache.py:685,707`, `flashvsr/impl/pipeline.py:87`. The single exception is test-only: `integrations_v2/flashvsr/tests/parity_check/test_tcdecoder_parity.py:189`, which loads a locally staged upstream checkpoint and is `skipif`-guarded on the file existing.
- No hardcoded tokens, keys or credentials.
- CI runs on **managed GPU runners** (`linux-amd64-gpu-rtxpro6000-latest-2`), not on self-hosted labels reachable from fork PRs — a meaningful improvement over `omni-dreams` and `cosmos-framework`, both of which expose self-hosted runners to `pull_request`.
- `docker/Dockerfile` creates and uses a non-root `flashdreams` user.

Residual items, all minor and all ours to fix in a fork:

- `docker/Dockerfile` pulls `ghcr.io/astral-sh/uv:latest` (mutable tag) and downloads the AWS CLI v2 zip from `awscli.amazonaws.com` at build time with no checksum verification. Pin both.
- The base image `nvidia/cuda:13.2.1-cudnn-devel-ubuntu24.04` is a mutable tag; pin by digest.
- The WebRTC demo is documented as `--host 0.0.0.0 --port 8089` with no authentication, and the docs tell you to open it "in any browser on the same network". That is a world-model server exposed to the LAN. Bind to localhost and front it with something before it leaves a workstation.
- Model checkpoints are fetched over HTTPS from Hugging Face by URL string (`AVAILABLE_OMNIDREAMS_CHECKPOINT_PATHS`) as `.pt` files, not safetensors. They are loaded with `weights_only=True`, which is the right mitigation, but the artefact format is still pickle-based.

## Physics and dynamics

- **Control interface.** `apps/interactive_drive/` accepts keyboard (`W`/`S` throttle-brake, `A`/`D` or arrows steer, Space brake), gamepad, or a real steering wheel with pedals. Those commands go through `simulation/ego_vehicle_kinematics.py` (`steer_rad = command.steer * max_steer`, `max_steer_rad = 0.5`, clamped to 0.4 under manual control), `simulation/game_physics.py` (collision response with `max_collision_yaw_rate_radps = 0.35`) and `simulation/ground_snap.py` (re-aligns `(x, y, yaw)` to terrain). **This is a real, if game-grade, vehicle kinematic model** — the first one in this collection. It is not a dynamics model: no tyre slip, no load transfer, no actuator lag.
- **Conditioning path.** Kinematics produce ego rig poses; `impl/conditioning/renderer.py` and the BSD-licensed `ludus-renderer` CUDA rasterizer render the HD map and bounding boxes from those poses; the world model consumes them. So steering changes the conditioning image, which is how interactive driving works — the same mechanism `omni-dreams` documented, now with a controller in front of it.
- **Model configuration** (`integrations_v2/omnidreams/config.py`): checkpoint `single_view/2b_res720p_30fps_i2v_hdmap_distilled.pt` — **720p, 30 fps, image-to-video, HD-map conditioned, distilled**. Scheduler is flow-matching with **`num_inference_steps=2`** (`denoising_timesteps=[1000, 500]`), `guidance_scale=1.0` (no CFG). Transformer: `num_views=1`, `len_t=2` → `frame_chunk_size = len_t * 4 = 8` frames per chunk, `window_size_t=6` sliding KV window, ring context parallelism, CUDA graphs on, a light VAE encoder and a TAEHV light decoder. `enable_cross_view_attn=False` in the public config — the multi-view cross-view path exists in the code but the released single-view checkpoint does not use it.
- **Horizon**: unbounded in principle, autoregressive with a 6-step KV window. `--total-blocks` controls clip length in the offline runner (20 blocks ≈ 157 frames in the nightly eval).
- **Evaluation.** Two CI-gated harnesses with committed metric baselines: **WorldLens** (`impl/eval/worldlens.py`, baseline `od-26.01-worldlens-40-v1.json`, 40 NuRec scenes, metrics `temporal_consistency_per_frame` and `subject_consistency_per_frame`) and **DrivingGen** (`impl/eval/drivinggen.py`, FVD/FID via a patched StyleGAN-V checkout). A per-commit 3-scene canary (`od-26.01-canary3-tb4-v1.json`) runs on the `omnidreams-worldlens-canary` workflow. There is also a `determinism.yml` workflow. **No physics benchmark, no collision/rule-violation metric on the generated world, no driving-performance score.**
- **Latency — the important gap.** Upstream publishes per-chunk benchmark tables for other models: Self-Forcing **344 ms** on H100 / 203 ms GB200 / 171 ms GB300 (vs 432 ms "official"), LingBot-World **629 ms** H100 / 394 ms GB300 (vs 1950 ms official), Wan2.1 **1040 ms** H100. **There is no published latency or fps figure for OmniDreams anywhere in the repo** — `docs/source/_static/performance/` has directories for seven models and OmniDreams is not one of them. What we know indirectly: the interactive app defaults to `--fps 30`, chunks are 8 frames, so sustaining real time requires **≈267 ms per 8-frame chunk**, and dedicated optimized configs exist for GB300 and RTX PRO 6000. Treat "real-time" as credible-but-unverified and measure it as step one.
- **Known failure modes**: other agents replay recorded behaviour and do not react (HD-map/bbox conditioning); appearance is anchored to the establishing frame so drifting far from it degrades; the first launch spends **several minutes** in `torch.compile`/CUDA-graph capture/Triton autotuning before becoming interactive, longest on the perf configs; the SANA-WM FP4 benchmark shows FlashDreams *slower* than official (4118 vs 1594 ms/chunk), so the optimization story is not uniform across models.

## Motion-control assessment

This is the piece that makes a neural AlpaSim concrete, and the integration seam is already the right shape. In `apps/interactive_drive` a human's steering/throttle/brake is turned into ego poses by `ego_vehicle_kinematics.py` and handed to the world model. **Replace that human with Alpamayo and you have closed-loop policy evaluation on generated sensor data**: Alpamayo consumes the rendered frame, emits `traj_future_xyz` / `traj_future_rot`, we convert that to the rig poses the conditioning wrapper expects, the model renders the next 8-frame chunk, repeat. Two clean places to attach: the `IModelLoop` / `InputSource` protocols in `flashdreams.api_v2` (in-process, lowest latency) or the gRPC service in `integrations_v2/omnidreams/impl/grpc/server.py`, where the client already supplies exactly `frame_chunk_size` rig poses per request and the server returns frames — a language-agnostic seam that would let AlpaSim drive the world model over the wire without linking against it.

That is strictly more capability than anything else reviewed. Cosmos 3 forward dynamics gives us offline counterfactual rollouts at 10 fps; this gives us an interactive loop at 30 fps with a vehicle model in it. The two are complementary rather than competing: Cosmos 3 for offline data generation, breadth of embodiment and an AV policy baseline; FlashDreams for closed-loop evaluation of *our* policy.

What is missing, and none of it is small. **Weight access is the gate**: `nvidia/omni-dreams-models` is confirmed gated, and the scenes dataset `nvidia/omni-dreams-scenes` requires an `HF_TOKEN` with read access too; if we cannot get both, the AV capability is unavailable and what remains is an excellent runtime for models we bring ourselves. **Other agents do not react** — HD-map/bbox conditioning replays recorded actors, so any evaluation that depends on interaction (cut-ins, yielding, negotiation) is invalid, and this rules out most of what closed-loop AV evaluation is actually for. **No ground truth comes back**: no labels, no depth, no collision or rule-violation signal from the generated world, so scoring a rollout means running perception on generated pixels and trusting it, or comparing against the WorldLens/FVD consistency metrics which say nothing about driving quality. **Single view** in the public config, so no full AV rig. **The vehicle kinematics are game-grade**, not our vehicle model, so trajectories that our planner considers feasible and ones the sim considers feasible will differ — swap in our own kinematics before drawing any conclusion about controllability. And **the latency is unpublished**, which is the first thing to measure because a 16B-class loop that runs at 8 fps is a different product from one that runs at 30.

## Extensibility

- **Adding our own model** is the designed path, documented in `ARCHITECTURE.md`, the "add a new method" guide, and the `integrate-a-model` agent skill. Implement `IApplication` / `ISession` / `IModelLoop` (and optionally `IUILoop`) from `flashdreams.api_v2`; `runtime_v2` supplies the lifecycle, the two-thread session loop, the event buffer, presentation and the client windows. `integrations_v2/{null_model,red_screen,color_fade}` are minimal working references — copy one before reading anything else.
- **Adding a control scheme / action space**: `apps/action2v` (keyboard+mouse action vocabulary), `apps/cam2v` (camera control), `apps/interactive_drive` (vehicle control) are three worked examples of the same `InputSource` seam. An Alpamayo-driven input source belongs beside them.
- **Swapping the vehicle model**: `apps/interactive_drive/interactive_drive/simulation/ego_vehicle_kinematics.py` is small, self-contained and separated from `game_physics.py` and `ground_snap.py`. Replacing it with our own kinematics is a contained change.
- **Output surfaces**: MP4, WebRTC and native Vulkan windows are runtime-owned (`Mp4ClientWindow`, `WebRTCClientWindow`), so a headless batch harness and an interactive demo share one application.
- **Performance tuning** is config, not code: `derive_config()` produces `omnidreams-optimized-gb300`, `omnidreams-optimized-rtx-pro-6000`, `omnidreams-perf` and `omnidreams-fast-perf` from one base, toggling attention backends, `torch.compile`, CUDA graphs and KV-cache finalization. There are agent skills for `apply-inference-optimizations`, `profile-model-performance` and `validate-performance-quality`.
- **Coupling hotspots**: the `perf` variants "download their pinned native source dependencies on first use, before compiling the extension" — a build step at first run, which will not survive an air-gapped or immutable-image deployment without pre-staging. The `ludus-renderer` CUDA rasterizer is a C++/CUDA subtree under a different licence; changes to HD-map rendering land there. Two generations of API (`api_v2`/`runtime_v2`/`integrations_v2` alongside older `flashdreams-run` paths) coexist, and some models are only on one of them.

## Hardware and cost

- **Repo baseline** (`README.md`): NVIDIA GPU with **80 GB VRAM or more** (e.g. H100 80GB); driver **R580+**; **CUDA 13.x** by default (torch `2.11.0+cu130`; CUDA 12.8 available via `--group cuda12`, Linux only); Python ≥ 3.10; Linux x86-64 or arm64; **100 GB+ free storage**. Upstream states plainly that inference "can fail (out-of-memory) on consumer and even enthusiast GPUs".
- **OmniDreams specifically** (`docs/source/models/omnidreams.rst`): **minimum VRAM ~48 GB**, PyTorch ≥ 2.11. Multi-GPU via `torchrun --nproc_per_node=4` with ring context parallelism.
- **Measured latency, per chunk, from upstream's own tables**: Self-Forcing 344 ms (H100) / 203 (GB200) / 171 (GB300); LingBot-World 629 / 449 / 394; Wan2.1 1040 / 441 / 382; FlashVSR and HY-WorldPlay have their own tables. In each case FlashDreams beats both the "official" implementation and fastvideo/lightx2v — typically 1.2-3x. The exception is SANA-WM FP4 on GB300, where FlashDreams is **2.6x slower** than official (4118 vs 1594 ms/chunk), which upstream publishes anyway; take that as a sign the tables are honest.
- **OmniDreams latency and fps: unclear.** No figure is published. Derived target for real time at the shipped config: 8-frame chunks at 30 fps ⇒ ≈267 ms/chunk. CI validates OmniDreams quality on an RTX PRO 6000 runner, which is at least a lower bound on what the maintainers run it on.
- **Warmup cost is real**: several minutes on first launch for compile, CUDA-graph capture and Triton autotuning, longest on the perf configs; cached and much faster afterwards. Budget for it in any benchmarking protocol, and never report a cold number.

## Verdict and next step

**ADOPT** — this is the highest-quality engineering in the collection and the only real-time closed driving loop, and unlike `omni-dreams` it is Apache-2.0 code we can build on regardless of what happens to any particular checkpoint. The security posture alone justifies preferring it as our runtime: no pickle, no `exec`, no `trust_remote_code`, `weights_only=True` throughout, non-root containers, managed CI runners — it is the only repo here I would run on a shared box without reservations. The caveat that keeps this from being unconditional is that the AV capability depends on gated weights and a gated scene dataset, and the model itself has no reactive agents and returns no ground truth, so it is a **sensor-realism and policy-smoke-test** tool, not a replacement for AlpaSim's physics and labels. Recommended spike, roughly three weeks, ordered so the cheap gate comes first: (1) **request access to `nvidia/omni-dreams-models` and `nvidia/omni-dreams-scenes` today** — everything AV-shaped downstream depends on it, and the answer is free; (2) regardless of that answer, build `docker/Dockerfile` and run the ungated Self-Forcing runner to validate the environment and reproduce the published 344 ms H100 number, which tells us whether their benchmarks hold on our hardware; (3) if weights arrive, launch `interactive-drive-omnidreams --mode webrtc`, drive it by hand, and **measure the sustained chunk latency and fps**, warm, on our GPU — that single number decides whether closed-loop evaluation is affordable; (4) then write an Alpamayo `InputSource` that replaces the human controller, converting `traj_future_xyz`/`traj_future_rot` into rig poses, and swap `ego_vehicle_kinematics.py` for our own vehicle model. Before any of that goes on shared infrastructure, pin the Dockerfile's `uv:latest`, base-image tag and AWS CLI download, and stop binding the WebRTC server to `0.0.0.0`.
