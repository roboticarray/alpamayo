## What it is

HY-World 2.0 is **not a video world model and has no action space at all** — that framing matters more than anything else in this review. It is a pipeline that turns text, a single image, multi-view images or a video into a **persistent 3D asset** (Gaussian splats, meshes, point clouds) that you then import into Unity, Unreal or Isaac Sim, where a real engine supplies the physics. It has two halves. **World Reconstruction** is WorldMirror 2.0, a ~1.2B feed-forward ViT+DPT model that predicts depth, surface normals, camera intrinsics and extrinsics, 3D point maps and 3DGS attributes in one pass, optionally conditioned on *injected* camera and depth priors, evaluated on 7-Scenes / NRGBD / DTU with numbers in the README. **World Generation** is a five-stage batch pipeline (`hyworld2/worldgen/`): HY-Pano-2 makes a 360-degree panorama, `traj_generate.py` builds a **Recast navmesh** from the coarse geometry and plans camera trajectories with a VLM in the loop, `traj_render.py` renders point clouds along those paths, `video_gen.py` runs WorldStereo-2 to hallucinate the unseen parts, and `world_gs_trainer.py` optimises the final 3DGS. The README argues explicitly against video world models ("watch a video, then it's gone") in favour of exportable assets. There is no training code for any of the models, no tests, and no CI.

## Security findings

- **`trust_remote_code=True`** — `hyworld2/panogen/pipeline.py:175`, passed to `HunyuanImage3ForCausalMM.from_pretrained`. Loading HY-Pano-2 executes arbitrary Python fetched from the Hub. This is the single worst finding in the repo and it is on the default path for world generation.
- **Explicit `weights_only=False`** (i.e. someone opted *out* of the safe loader), all unpickling artifacts produced by earlier stages or downloaded checkpoints:
  - `hyworld2/worldgen/show_gs.py:49`
  - `hyworld2/worldgen/traj_generate.py:301` — `torch.load(f"{scene_path}/render_results/full_depth_prediction.pt", weights_only=False)`
  - `hyworld2/worldgen/src/retrieval_wm.py:749`
  - `hyworld2/worldgen/gs/extract_mesh.py:84` and `:107`
  - `hyworld2/worldgen/gs/sky_depth.py:242`
  - `hyworld2/worldgen/world_gs_trainer.py:442`, `:2232`, `:2539`
  - `hyworld2/worldgen/models/worldstereo.py:141` — `torch.load(model_path, map_location="cpu")` with no `weights_only` at all, on the **published WorldStereo-2 checkpoint**.
- **`os.system` with interpolated paths** — `hyworld2/worldgen/world_gs_trainer.py:1621`: `os.system(f"gsbox p2x -i {self.ply_dir}/point_cloud_{step}.ply -o ...")`. A shell invocation built by f-string. Paths here are internally generated, so this is a latent rather than live injection, but it is the wrong pattern and it also silently requires an undeclared `gsbox` binary.
- **Unpinned VCS dependency** — `requirements_git.txt` pins four of five git installs to exact commits (`nerfview@4538024`, `fused-ssim@328dc98`, `spz@v3.0.0`, `MoGe@0286b49`) but leaves **`git+https://github.com/facebookresearch/pytorch3d.git`** floating on the default branch. The `recastnavigation` submodule is pinned by commit in the git index, which is correct.
- **Wide auto-download surface** — `traj_generate.py:76-82` pulls `naver-iv/zim-anything-vitl`, `IDEA-Research/grounding-dino-tiny`, `facebook/sam3`, `Ruicheng/moge-2-vitl-normal` from the Hub at runtime, in addition to Tencent's own weights and `Qwen/Qwen3-VL-8B-Instruct` for the vLLM server. Six third-party model repos, each its own supply-chain and licence question.
- **No hardcoded secrets found.** The OpenAI clients at `hyworld2/worldgen/traj_generate.py:206` and `src/vlm_utils.py:150` use `api_key="EMPTY"` against a *local* vLLM server (`localhost:8000`), not a cloud endpoint. `hyworld2/panogen/PE/deepseek.py` talks to `lkeap.tencentcloudapi.com` through the Tencent Cloud SDK but reads no credential from the repo; its `ast.literal_eval` at `:125` is the safe variant, not `eval`. `traj_generate.py:65-67` sets `no_proxy` for localhost, which is housekeeping, not exfiltration.
- **`subprocess.run(wm_cmd, cwd="..")`** at `hyworld2/worldgen/src/retrieval_wm.py:1152` — list argv, no `shell=True`. Safe, though the `cwd=".."` relative path makes the pipeline sensitive to where you launch it from.
- No `.github/`, no CI, no test files. 128 Python files.

## Physics and dynamics

- **Action space: none.** There is no keyboard, no mouse, no pose conditioning, no control input of any kind. The closest thing is `prior_cam_path` — a camera-parameters JSON you can inject into WorldMirror to *constrain reconstruction*, not to drive a rollout (`DOCUMENTATION.md:153-154, 180-181`). Say this plainly: this repo cannot be driven by a planner, because there is nothing to drive.
- **Dynamics: none.** Output is a static scene. No moving objects, no articulation, no temporal model, no horizon. The "1 minute vs unlimited playable duration" comparison in the README is a claim about *asset persistence*, not about predicting anything over time.
- **The physics that does exist is borrowed.** `build_navmesh_from_mesh` (`hyworld2/worldgen/src/navi_utils.py:1721-1737`) runs Recast over the reconstructed mesh with `cellSize=0.05, cellHeight=0.05, agentHeight=1.6, agentRadius=0.3, agentMaxClimb=0.4, maxSlope=45.0` — a human-shaped agent, in metres, with real traversability semantics. `filter_navmesh_by_height`, `connect_navmesh_components` (`max_bridge_z_diff=5.0`) and `snap_navmesh_to_surface` clean it up. Beyond that, collision and lighting come from whatever engine you import the mesh into. That is the honest reading of the README's "real physics collision" claim.
- **Resolution and scale.** WorldMirror supports flexible-resolution inference from 50K to 500K pixels and emits per-view float32 depth `.npy`, normals, `camera_params.json` (c2w extrinsics + intrinsics) and `points.ply`. Intrinsics you inject must correspond to the **original** image resolution; the pipeline handles resize and centre-crop itself (`DOCUMENTATION.md:321`).
- **Evaluation is real and quantitative**, which is unusual in this batch — but it is reconstruction accuracy, not dynamics: mean Accuracy and Completeness of point maps on 7-Scenes, NRGBD and DTU under different prior configurations, compared against Pow3R and MapAnything (README, "Performance"). There is no dynamics benchmark because there are no dynamics.
- **Failure modes.** The pipeline degrades gracefully in places and silently in others: `build_navmesh_from_mesh` swallows every exception and returns `("no_recast" / "rc_construct_failed")` if the Recast extension is missing (`navi_utils.py:1724-1746`), so a botched submodule build produces a world with no navmesh rather than an error. Stage-to-stage handoffs are file paths, so a partial failure in stage 3 surfaces as a missing-file error in stage 4. Generation quality outside the first panorama's field of view is entirely WorldStereo-2 hallucination.

## Motion-control assessment

The honest assessment: **HY-World 2.0 has no motion-control value as a model.** It cannot be conditioned on actions, it cannot be rolled out, and it cannot be put in a control loop. What it can do is manufacture environments, and that is a real if narrow use for us. The pipeline's output — a mesh plus 3DGS plus a Recast navmesh in metric units — is exactly the input format Isaac Sim and Unreal want. A plausible workflow is: capture a video of a real warehouse or test route, run WorldMirror 2.0 with **injected camera intrinsics/extrinsics from our calibration and injected depth from our LiDAR** (`prior_cam_path` / `prior_depth_path`, `DOCUMENTATION.md:153-154`), and get a 3DGS digital twin plus a navmesh whose `agentRadius` / `agentHeight` / `agentMaxClimb` / `maxSlope` you set to our robot's footprint rather than the default 1.6 m human. That is a credible path to populating AlpaSim with real-world-derived environments, and the prior-injection interface is the best-designed part of the repo for it.

Two things stop me recommending it anyway. The first is the licence, and it is not a technicality. Section 5(b) of `License.txt` reads: *"You must not use the Tencent HY-WORLD 2.0 Works or any Output or results of the Tencent HY-WORLD 2.0 Works to improve any other AI model (other than Tencent HY-WORLD 2.0 or Model Derivatives thereof)."* Generating environments in order to train or evaluate Alpamayo is, on any plain reading, using the Output to improve another AI model. Section 5(c) separately voids the licence for any use "outside the Territory", where Territory excludes the EU, the UK and South Korea — relevant the moment a European team member opens the repo or a European customer runs the product. Section 4 adds a 1M-MAU gate. This needs counsel before a single scene is generated, and my expectation is that counsel says no for the training-data use case.

The second is that the static-geometry output does not address our hard problem. Our gap is dynamics: how other vehicles, pedestrians and the ego platform behave over time under control. A beautiful frozen 3DGS of a street does not help with that; it helps with appearance, which we can already get from Cosmos-Transfer or OpenDWM under far friendlier licences. If we want reconstruction specifically, WorldMirror's actual competitors — VGGT, MapAnything, MoGe, all permissively licensed — should be evaluated first, and the README's own comparison table tells us roughly where they land.

## Extensibility

- **Prior injection (the best hook):** `prior_cam_path` (a camera-parameters JSON) and `prior_depth_path` (a depth-map directory) constrain WorldMirror's reconstruction (`DOCUMENTATION.md:153-154, 180-181`). This is where our calibration and LiDAR go. Note the intrinsics convention: values must be at the **original** image resolution.
- **Head selection:** `disable_heads` accepts `camera`, `depth`, `normal`, `points`, `gs` and frees the corresponding memory (`DOCUMENTATION.md:81`). Useful for trimming a pipeline down to what we need.
- **Robot-shaped navmesh:** `build_navmesh_from_mesh(verts, faces, cellSize, cellHeight, agentHeight, agentRadius, agentMaxClimb, maxSlope)` (`hyworld2/worldgen/src/navi_utils.py:1721`). Changing the default human agent (1.6 m / 0.3 m) to a robot footprint is a one-call change, and `roof_height_threshold` (`navi_utils.py:3203`) filters ceilings.
- **Adding a sensor or modality:** not feasible. The models have fixed heads and there is no training code; a new output head means retraining WorldMirror from scratch.
- **Multi-GPU:** sequence parallelism plus FSDP via `use_fsdp` / `fsdp_cpu_offload`, with the constraint that **the number of input images must be >= the number of GPUs** (`DOCUMENTATION.md:350-353`) — a real trap when reconstructing from a short clip.
- **Coupling hotspots:** the five generation stages hand off through hardcoded relative paths under `<scene_path>/` (`navmesh/`, `render_results/`, `world_mirror_dir`); `subprocess.run(..., cwd="..")` (`retrieval_wm.py:1152`) fixes the working directory you must launch from; the VLM stage requires a *separately launched* vLLM server hosting `Qwen/Qwen3-VL-8B-Instruct` on `localhost:8000`; `world_gs_trainer.py` shells out to an undeclared `gsbox` binary.

## Hardware and cost

Documented per stage in `hyworld2/worldgen/README.md:29-89`: the generation pipeline wants **>=4 GPUs, tested on 8x H20**, *plus* a separate GPU group or machine running a vLLM server for `Qwen/Qwen3-VL-8B-Instruct`. Stage 1 (trajectory planning) is single-GPU; stages 2-4 are multi-GPU; stage 5 (3DGS training) is written for 8 GPUs, and the README gives an explicit rescaling rule — `max_steps 2000` on 4 GPUs, `4000` on 2, **`8000` on 1** — so a single-GPU world generation is a long batch job, not an interactive one. Model sizes set the floor: HY-Pano-2 is **~80B** (a HunyuanImage-3 MoE, loaded with `device_map="auto"` and `moe_impl` selectable between eager and flashinfer), WorldStereo-2 is **~17B**, WorldMirror 2.0 only **~1.2B**. So the two halves have wildly different budgets: **reconstruction is cheap and reachable on one card**, generation is a multi-node undertaking. No explicit VRAM number appears anywhere in the repo for either. Environment: CUDA 12.8, Python 3.11.15, `torch==2.7.1`, and one of FlashAttention-2 or FlashAttention-3 (the FA3 path is a manual `python setup.py install` from the Hopper directory). No wall-clock timings are published, though the pipeline writes a `pipeline_timing.json` when `log_time` is on.

## Verdict and next step

**SKIP for anything that touches our training or evaluation pipeline; WATCH narrowly, and only after counsel, as an environment-authoring tool.** This is a competent and well-documented piece of engineering solving a problem adjacent to ours — it makes persistent, engine-importable 3D assets rather than pixels, and WorldMirror 2.0's prior-injection interface is genuinely the right shape for turning our calibrated, LiDAR-equipped captures into digital twins. But three things disqualify it. The licence is a bespoke Tencent Community Agreement whose Section 5(b) forbids using its Output to improve any other AI model, whose Territory excludes the EU, UK and South Korea, and which is governed by Hong Kong law — read the file, not the badge, and note that the WorldStereo-2 weights being tagged MIT on a personal Hugging Face account is a discrepancy, not a permission. The security posture is the worst in this batch: `trust_remote_code=True` on the default generation path plus nine explicit `weights_only=False` loads. And most fundamentally it has **no action space and no dynamics**, so it cannot address the thing we actually need a world model for. The only next step I would authorise is a legal read of `License.txt` Sections 4, 5(b) and 5(c) against our intended use; if and only if that comes back clean, run **WorldMirror 2.0 alone** (the ~1.2B model, single GPU, no `trust_remote_code`, no HY-Pano, no vLLM) on one of our own recorded drives with injected calibration and LiDAR depth, and compare its point-map accuracy against VGGT and MapAnything — both of which are permissively licensed and would let us skip this conversation entirely.
