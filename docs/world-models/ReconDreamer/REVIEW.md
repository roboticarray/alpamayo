## What it is

ReconDreamer's paper proposes fixing 3DGS's collapse under large ego-lateral manoeuvres by iteratively re-rendering off-trajectory views, cleaning the artifacts with a trained restoration diffusion model (DriveRestorer), and folding the cleaned frames back into the Gaussian fit — a progressive data update loop. **What is in this repository is [Street Gaussians](https://github.com/zju3dv/street_gaussians) with a single render script bolted on.** `lib/` is Street Gaussians' code (background/actor/sky Gaussian models, a yacs config system, Waymo readers, a COLMAP preprocessing path); `render.py` is the only entry point and it does one thing: loop over lateral camera offsets of -3 to +6 metres, re-render every camera at each offset, and write videos. There is no training script, no restoration model, no progressive update loop, and the two shipped configs (`configs/recondreamer.yaml`, `configs/street_gaussians.yaml`) are **byte-identical except for `exp_name` and a hardcoded GPU index** — so "ReconDreamer" versus "Street Gaussians" here is purely a matter of which pre-fitted checkpoint you point at. The one genuinely valuable artifact is `script/NTAIou/average_iou_results_005.txt`, a checked-in table of how box-detection IoU degrades as you move the camera off the recorded line.

## Security findings

- `render.py:16` — `sys.path.append('/mnt/pfs/users/chaojun.ni/1-code/release-code/')`. A hardcoded absolute path to an author's machine, injected into the module search path at import. Harmless on our systems only because the directory does not exist; if anything ever does exist there it is imported ahead of nothing and shadows nothing, but it is a clear signal of how the release was prepared.
- `lib/models/scene.py:48` — `state_dict = torch.load(checkpoint_path)`. No `weights_only`, no `map_location`. This loads the checkpoint the README tells you to fetch from a **Google Drive link with no checksum**.
- `lib/utils/waymo_utils.py:471,472,866,867`, `lib/datasets/waymo_full_readers.py:155`, `script/data/waymo/generate_lidar_depth.py:44,45` — `np.load(path, allow_pickle=True)` on `.npz`/`.npy` dataset artifacts. `allow_pickle=True` makes a numpy archive arbitrary code execution, and the preprocessed data comes from the same Google Drive link. This is the most likely route to running someone else's code on our hardware.
- `lib/datasets/waymo_full_readers.py:24,29,44,52` — `os.system(f'rm -rf {save_dir}')` and `os.system(cmd)` with interpolated paths; `lib/utils/cfg_utils.py:103,105` — `os.system('mkdir -p {}'.format(...))`; `script/data/waymo/colmap_waymo_full.py:112,226,259,264,283,294-296` — a dozen COLMAP invocations and three more `rm -rf` calls, all built by f-string. None takes untrusted input today, but a dataset path containing a space, a quote or a `;` will do something other than what was intended.
- `script/data/waymo/generate_sky_mask.py:43` — `torch.load(cache_file, map_location='cpu')`, no `weights_only`, for the Segment Anything checkpoint.
- **Benign:** `lib/config/yacs.py:426` uses `literal_eval`, not `eval` — that one is fine.
- **Not found:** no `exec(`, no `trust_remote_code`, no `curl | sh`, no hardcoded API tokens or credentials.
- **Dependency pinning:** essentially absent. `requirements.txt` has 25 entries of which two are pinned — `numpy==1.23.5` and `protobuf==3.19.`, the latter a **malformed version specifier with a trailing dot** that pip will reject or resolve unexpectedly. The last line is `git+https://github.com/NVlabs/nvdiffrast.git` with no ref, so every install picks up whatever nvdiffrast's default branch is that day (and drags in NVIDIA's own research-only licence alongside Inria's). The README installs `torch==1.13.1+cu116` — a 2022 stack, three years stale at review time, which constrains the whole environment.
- **Tests / CI:** none. `script/test_gaussian_rasterization.py` is referenced by the README's install section but is a smoke check for the CUDA extension, not a test suite, and `script/` in this tree contains only `NTAIou/` and `data/` — the file the README tells you to run is **not present**.
- **Committed build artifacts:** `lib/**/__pycache__/` is checked in, containing both `cpython-38` and `cpython-311` bytecode. Stale `.pyc` files for a Python version the project does not support are a good way to get confusing import behaviour.

## Physics and dynamics

- **There is no dynamics model.** This is a static-plus-tracked-actor Gaussian reconstruction of one 80-frame Waymo clip. Nothing predicts, nothing simulates, nothing responds to an action.
- **What "novel trajectory" means here.** `render_trajectory()` (`render.py:64-96`) iterates `for num in [-3,-2,-1,1,2,3,4,5,6]`, sets `args.camera_shifting = num`, and then for every camera does `camera.T[0] += args.camera_shifting; camera.set_extrinsic(camera.get_extrinsic())`. That is a **constant lateral translation in metres applied uniformly to all frames** — not a ramp, not a manoeuvre, and with the camera rotation left exactly as recorded. A "6 m lane shift" is the original drive, rigidly displaced six metres sideways. This is a strictly weaker trajectory model than DriveDreamer4D's (which at least ramps the offset over time), and neither has any heading component.
- **Resolution, cameras, horizon.** Waymo, `selected_frames: [115, 194]` — 80 frames at 10 Hz, i.e. **8 seconds**. Training data uses `cameras: [0]` (front) but rendering composites three — `render.concat_cameras: [1, 0, 2]`, front-left / front / front-right — into one panorama, which is the closest thing to multi-camera in this batch's reconstruction repos. Output video at `fps: 10`, matching Waymo's capture rate, so unlike DriveDreamer4D there is no frame interpolation inflating the result.
- **Evaluation, and the one useful number.** `script/NTAIou/average_iou_results_005.txt` is checked into the repo and contains the measured NTA-IoU (YOLO11 detections on the rendered novel view, IoU'd against projected ground-truth boxes) as a function of lateral shift, for both the Street Gaussians baseline and the ReconDreamer checkpoint:

  | shift (m) | ±1 | ±2 | ±3 | +4 | +5 |
  |---|---|---|---|---|---|
  | street_gaussians | 0.533 / 0.523 | 0.498 / 0.504 | 0.463 / 0.457 | 0.337 | 0.242 |
  | recondreamer | 0.550 / 0.543 | 0.534 / 0.524 | 0.473 / 0.496 | 0.461 | 0.433 |

  Read this as the honest answer to "how far off the recorded line can a driving 3DGS scene be trusted?" — baseline quality is roughly flat to 3 m and then falls off a cliff (0.46 → 0.34 → 0.24 between 3 and 5 m), and the restoration loop mostly arrests that collapse (0.43 at 5 m). It is a small table from one scene, but it is measured, checked in, and directly relevant to any plan of ours that involves re-rendering real drives along planned trajectories.
- **Rendering speed.** `render.py:36-41,52-58` times every `renderer.render` call with `torch.cuda.synchronize()` and prints `average rendering time` in milliseconds. No value is published, but a first run measures itself — this is the only repo in the batch with speed instrumentation built into the shipped entry point. 3DGS rasterisation is normally milliseconds per frame, so this path is plausibly real-time; the cost is the fit, not the render.
- **Known failure modes.** Quantified above, and unusually well: the degradation of scene fidelity with lateral displacement is the repo's whole subject. Beyond that, `opt_track: true` in the config means actor poses are optimised during the fit, so tracked vehicles are only as good as that optimisation; sky and background are separate Gaussian sets and their seams are a classic Street Gaussians artifact.

## Motion-control assessment

The interface is a per-frame camera extrinsic. `render.py:88-90` mutates `camera.T` and calls `camera.set_extrinsic(camera.get_extrinsic())`, so anything that can produce a `(T, 4, 4)` pose sequence can drive this renderer. Alpamayo's `ActionSpace.action_to_traj` (`src/alpamayo_r1/action_space/action_space.py:47-70`) returns `traj_future_xyz (..., T, 3)` and `traj_future_rot (..., T, 3, 3)`, which assemble into exactly that — and critically, an Alpamayo trajectory would supply the **rotation** that the shipped shift code throws away, so a rendered lane change would actually turn the camera instead of crab-walking. Replacing the `for num in [-3,...,6]` loop with "read poses from a file, set the full extrinsic" is a twenty-line change. That is the whole integration story, and it is the same story as DriveDreamer4D's.

What this buys us, in principle, is a sensor-realism layer for counterfactual evaluation: take a real drive, fit a scene, ask what Alpamayo's planner would have seen on a different line, and score it. Relative to roboticarray's stack that is complementary to Isaac Sim rather than competing — Isaac gives controllable dynamics with synthetic appearance, a fitted Gaussian scene gives real appearance with no controllability and no dynamics. Neither closes a loop alone, and this repo in particular cannot: it renders, it does not simulate, other agents replay on rails, and there is no mechanism by which the ego's new position would change anything about the world.

Three things rule out using *this* repository as the vehicle. First, licence: no grant on the first-party code, and `diff-gaussian-rasterization` — which you must compile and install for anything to run — is Inria/MPII research-and-evaluation-only. Nothing derived from it can ship. Second, there is no training script, so we could only ever re-render the one Waymo clip the authors uploaded; we could not fit our own data. Third, DriveRestorer is absent, so even the paper's advantage over the baseline is not reproducible here — the two configs are the same file with a different `exp_name`.

Take forward the measurement, not the code. The NTA-IoU-versus-lateral-shift curve is a cheap, automatable acceptance test for any neural-rendering stack we adopt: "run a detector on the off-trajectory render, IoU against projected ground truth, plot against displacement, and decide how far off the recorded line the output is still usable." That question matters to us regardless of which renderer answers it.

## Extensibility

- **New dataset**: `lib/datasets/` has `waymo_full_readers.py`, `colmap_readers.py` and `blender_readers.py` behind `base_readers.py`, selected by `data.type` in the yacs config. The Waymo path is the only one maintained, and it expects the authors' preprocessed layout (COLMAP sparse model, LiDAR depth `.npz`, sky masks, tracked actor poses) produced by `script/data/waymo/`. Adding a dataset means reproducing that whole preprocessing chain, which is COLMAP plus Segment Anything plus a tracker.
- **New sensor / camera**: `data.cameras` and `render.concat_cameras` are config lists, so rendering more Waymo views is free; the fit in the shipped config uses only camera 0.
- **New trajectory / action space**: `render.py:64-96` is where to do it — replace the `camera_shifting` loop with a pose-sequence reader and set the full extrinsic rather than only `T[0]`. Nothing else in the codebase knows about trajectories.
- **New Gaussian model**: `lib/models/` separates `gaussian_model_bkgd.py`, `gaussian_model_actor.py`, `gaussian_model_sky.py`, composed by `street_gaussian_model.py` and rasterised by `street_gaussian_renderer.py`. It is a clean decomposition, but the composition is hardwired in `StreetGaussianModel`, not config-driven.
- **Config system**: vendored yacs (`lib/config/yacs.py`, `lib/config/config.py`), YAML plus CLI override. Note `cfg.gpus` is a list in the config and both shipped files set it to a single high index (`[4]`, `[5]`) that will simply not exist on a smaller machine.
- **Coupling hotspots**: `render.py:121` (`cfg.mode = 'trajectory'` set unconditionally, defeating the mode dispatch immediately below); `render.py:16` (the author's `sys.path` entry); the absent training script; `submodules/diff-gaussian-rasterization` as a compiled, licence-encumbered hard dependency of every code path.

## Hardware and cost

**Upstream publishes no VRAM figure, no GPU count and no timing.** Inferable: the configs name a single GPU (`gpus: [4]`), so this is single-GPU; `train.iterations: 50000` with `densify_until_iter: 25000` is a long 3DGS schedule for an 80-frame, multi-actor street scene, which in this family of models typically wants **24 GB and lands closer to 40 GB** for scenes with many tracked actors — but since no training script ships, that cost is hypothetical here. Rendering is cheap: Gaussian rasterisation is normally single-digit milliseconds per frame, and `render.py` prints its own measured average, so the first run gives us a real number rather than a guess. The expensive parts are (a) the environment — `diff-gaussian-rasterization`, `simple-knn` and `nvdiffrast` all compile from source against `torch==1.13.1+cu116` on Python 3.8, with `protobuf==3.19.` malformed in the requirements file — and (b) the preprocessing chain for any new scene, which runs COLMAP over the clip. Budget a day for the environment and zero for the compute.

## Verdict and next step

**SKIP.** ReconDreamer is the thinnest release in this batch: the contribution it is named for, DriveRestorer, is not in the repository in any form, the two shipped configs are identical apart from an experiment name, there is no training script, and the single published artifact is one fitted Waymo scene behind a Google Drive link. On top of that it has no licence of its own and hard-depends on the Inria/MPII Gaussian-Splatting rasterizer, which is research-and-evaluation-only — so nothing built on it can leave the lab. The first-party code that does exist carries an author's absolute path in `sys.path`, a mode flag that overrides itself one line before it is read, and GPU indices that assume a six-GPU box. Do not clone it for work. The next step is to take the one thing it did contribute — `script/NTAIou/average_iou_results_005.txt` showing detection IoU collapsing from 0.46 at 3 m of lateral offset to 0.24 at 5 m — and treat that curve as the acceptance criterion for whatever reconstruction stack we do evaluate, which should be **Street Gaussians** (zju3dv, the direct parent, with a training script) or **DriveStudio** (broader dataset support, and the parent of DriveDreamer4D). When we build that evaluation, wire it to Alpamayo trajectories rather than constant offsets: `traj_future_xyz` plus `traj_future_rot` assemble directly into the `(T,4,4)` extrinsics the renderer wants, and unlike a lateral shift they carry a heading, which is the difference between rendering a lane change and rendering a car sliding sideways. Re-check this repo only if GigaAI releases DriveRestorer under a licence.
