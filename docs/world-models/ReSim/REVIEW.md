## What it is

ReSim (NeurIPS 2025 Spotlight, OpenDriveLab) is a driving world model built on CogVideoX-2B: a 30-layer, 1920-hidden DiT video diffusion transformer (`sat/configs/infer_nus.yaml`, `network_config`) trained through the SwissArmyTransformer (SAT) stack with a LoRA mixin (r=128) and a frozen T5-XXL text encoder. Its distinguishing claim over Vista is *reliable* action control across **non-expert** behaviour: it mixes web driving video (OpenDV/YouTube), real trajectory-labelled data (NavSim/nuPlan, nuScenes, Waymo), and CARLA rollouts containing deliberately hazardous manoeuvres, so the model stays coherent when you ask it for actions no human expert would take. Conditioning is a dedicated `TrajEncoder` (`sat/sgm/modules/encoders/traj_encoder.py`) that takes 8 future `[x, y, heading]` points into 9 tokens at 4096-dim, injected alongside a text prompt; a `with_human_drive_token` flag and a `cmd` string (`Moving_Forward` / `Turning_Left` / `Turning_Right`) give coarser control. Output is 49 frames at 10 fps and 512x896 (~4.9 s), chained autoregressively via `n_prediction_round` with 3 fixed conditioning latents. The repo ships training and inference for five dataset loaders behind one JSON schema, but every example config is full of `/path/to/...` placeholders and there are no tests and no CI.

## Security findings

- `sat/sgm/modules/autoencoding/magvit2_pytorch.py:1319` — `config = pickle.loads(pkg["config"])` on data read straight out of a checkpoint at `:1315`. Loading a hostile MAGVIT2 checkpoint is arbitrary code execution. This path appears to be dead vendored code (nothing in the ReSim configs instantiates it), but it is in the tree and `pickle` is imported at `:37`.
- **The published ReSim weights are pickles, not safetensors.** `resim_ckpts/exp0_no_carla/30000-ema/mp_rank_00_model_states.pt` and `vae/3d-vae.pt` are `.pt` files, loaded by `torch.load(..., map_location="cpu")` with no `weights_only=True` at `sat/vae_modules/autoencoder.py:76` and `:565`, `sat/vae_modules/utils.py:281`, `sat/sgm/models/autoencoder.py:540`, `sat/sgm/util.py:289`, and by SAT's own loader for the transformer. Unlike Vista, there is no safetensors alternative — you are executing whatever the checkpoint contains. Fetch only from the official HF repo, verify hashes, and prefer converting to safetensors with `tools/convert_weight_sat2hf.py` before routine use (note that converter itself does `torch.load` at `:164`/`:185`).
- `sat/sample_video.py:121` — `torch.load(latent_file)` with no `map_location` and no `weights_only`, on a user-supplied latent directory (`input_type: latent_dir`).
- `sat/inference_custom.sh:21` and the sibling `finetune_*.sh` — `eval ${run_cmd}` on a string assembled from `$1`. A config path containing shell metacharacters executes. Cosmetic in practice, sloppy in principle.
- `sat/vae_modules/utils.py:105` and `sat/sgm/util.py:113` — bare `eval(s)` in `get_string_from_tuple`, inherited from the SD codebase.
- YAML `target:` strings are imported and instantiated throughout (`sat/diffusion_video.py:148`, `sgm/modules/encoders/modules.py:93`). Hostile config = code execution, as with every sgm derivative.
- No hardcoded tokens or API keys found (`tools/caption/` is documentation only). No `os.system`, no `subprocess` in ReSim's own code, no `curl | sh`, no `trust_remote_code`.
- Dependency hygiene: `requirements.txt` pins most things exactly (good) but declares `SwissArmyTransformer==0.4.11` from PyPI while the README tells you to `pip install -e SwissArmyTransformer` from the vendored copy — the two fight, and install order decides which wins. No lockfile.

## Physics and dynamics

- **Action space**: `fut_traj`, 8 future points of `[x, y, heading]` in the ego frame (`sat/data_share.py:227`, `fut_traj = torch.tensor(fut_traj)  # [8, 3]`), encoded by a 2-layer transformer into 9 tokens (`traj_encoder.py`, `seq_len: 8`, `use_all_tokens: true`, `out_dim: 4096`). Heading can be masked out at training time (`p_mask_out_heading`), so the model tolerates position-only trajectories. Secondary channels: a text prompt, a discrete `cmd`, and a `with_human_drive_token` boolean that distinguishes expert-demonstrated from free-driving behaviour.
- **Conditioning dropout**: `ucg_rate: 0.5` on the trajectory embedder (`infer_nus.yaml`) — the model is trained half the time as an unconditional world model and half as an action-conditioned one, which is deliberate (the config comments it "action (world model) and no-action (planning model)") but means action adherence is a soft constraint, tunable at inference through `DynamicCFG` (`scale: 6`).
- **Horizon**: 49 frames at 10 fps ≈ 4.9 s per round (13 latent frames after 4x temporal compression), extended by `args.n_prediction_round` with the last 3 latents held fixed (`sampler_config.fixed_frames: 3`, `get_cond_inds` at `sat/sample_video.py:175`). Roughly double Vista's per-round horizon.
- **Resolution / fps**: 512x896 at 10 fps (`sampling_video_size: [512, 896]`, `sampling_fps: 10`). A 480x720 variant is commented out in the config; changing it requires matching `latent_width`/`latent_height` and the positional-embedding interpolation factors, which are hand-tuned constants (`height_interpolation: 2.0`, `width_interpolation: 2.3333`).
- **Evaluation of dynamics**: the paper's contribution is a controllability/reliability evaluation under non-expert actions; this repo ships the generation side but no evaluation harness — no metric scripts, no benchmark runner. You would have to build the scoring yourself.
- **Known failure modes**: with `ucg_rate 0.5` and `p_drop_traj`, weak trajectory adherence is expected at low CFG; the released checkpoint is the *expert-only* one, so exactly the hazardous-behaviour reliability the paper advertises is not in the weights you can download; positional-embedding interpolation constants make off-resolution inference silently degrade.

## Motion-control assessment

ReSim has the best-matched action interface of the four repos for Alpamayo. Alpamayo-R1's `ActionSpace.action_to_traj` (`/home/user/alpamayo/src/alpamayo_r1/action_space/action_space.py`) returns `traj_future_xyz (..., T, 3)` and `traj_future_rot (..., T, 3, 3)`; ReSim wants exactly `[x, y, heading]` x 8. The adapter is: drop z, convert each 3x3 rotation to a yaw with `alpamayo_r1.geometry.rotation`, resample to 8 points, write into the `traj_fut` field of a clip JSON matching `sat/data_share.py`'s schema, and set `apply_traj: True`. No retraining, no architecture change — ReSim already consumes heading, which Vista does not. The `UnicycleAccelCurvatureActionSpace` also gives curvature, which integrates to the same heading sequence, so either Alpamayo action parameterisation works.

The bigger draw is that ReSim is the one model here trained to stay coherent when the requested action is *bad*. For evaluating Alpamayo, most of the interesting cases are the failures — a trajectory that cuts a corner, brakes late, or drifts out of lane — and a world model that only ever saw expert data will simply render something plausible-but-wrong. That is the right design for policy evaluation. The caveat is severe: the checkpoint embodying that capability (CARLA, expert + non-expert) is on the roadmap, not on the Hub. Today you can only download the expert-only model.

What is still missing for closed-loop use: no state output (same fundamental limit as Vista — no ego pose, no collision, no other-agent state, so any loop must close through a perception stack on generated pixels), single ego-view camera with no multi-camera or surround path, and no HD-map or BEV-layout conditioning anywhere. Against the roboticarray stack, the honest framing is: ReSim is a photoreal *renderer of consequences* for a proposed trajectory, to sit next to AlpaSim for qualitative and distributional evaluation, while Isaac Sim / Isaac Lab remain the source of truth for physics and state. The NavSim overlap is a practical bonus — if we already have NavSim scenes, `resim_data_jsons/navsim_token2info_val_list.json` is a ready-made eval set.

## Extensibility

- **New dataset**: subclass `SharedDataset` in `sat/data_share.py` the way `sat/data_nus.py:13` does (that file is essentially just a class declaration — the schema does the work). Everything is driven by a JSON of clips with `img_seq`, `cmd`, `traj_fut`, `token`. This is a genuinely good seam.
- **Dispatch hotspot**: `sat/data_multi.py:20-58` selects the loader by **substring matching the data path** (`elif "navsim" in data_dir.lower()`, `elif "carla" in ...`). Name a directory badly and you silently get the wrong loader — and note `"navsim"` maps to `nuPlanDataset`, which is correct but confusing. Fix this to an explicit `type` field in a fork.
- **New action space**: replace or add an embedder under `conditioner_config.params.emb_models`; `TrajEncoder` is an ordinary `AbstractEmbModel` with `seq_len`/`dim`/`out_dim` params, and `is_trainable: true`, so a new action encoder can be trained while the DiT stays frozen (`not_trainable_prefixes: ['model']`). Combined with the LoRA mixin (`r: 128`) this is a realistic finetune on modest hardware, which is the main reason extensibility scores 4.
- **New sensor / camera**: no seam. The patch embedding assumes one video stream at a fixed latent grid; multi-camera would be a rewrite.
- **Resolution changes** are a coupling hotspot: `latent_width`/`latent_height`/`height_interpolation`/`width_interpolation` in `infer_nus.yaml` must be kept consistent with `sampling_video_size` by hand.

## Hardware and cost

The repo states **no** VRAM figure, no GPU count for inference, and no wall-clock — this is a real documentation gap. What can be inferred: the backbone is CogVideoX-2B in fp16 (`fp16: True`) generating 49 frames at 512x896 with 50 sampling steps (`num_steps: 50`) and a 3D VAE decode that the config already splits one sample at a time (`en_and_decode_n_samples_a_time: 1`). Budget a single 40-80 GB card for inference and expect it to be tight at this resolution; `en_and_decode_n_frames_a_time` and `truncate_n_frames_decode` are commented out in the config and are the first knobs to turn on OOM. Training is DeepSpeed multi-GPU (`finetune_multi_gpus_custom.sh configs/train.yaml 8 1 42` — 8 GPUs, 1 node in the README example) plus a frozen T5-XXL, so assume 8x80 GB for any real finetune; LoRA makes a smaller run plausible. Treat every number here as an estimate: **unclear** is the accurate answer, and measuring it is step one of any trial.

## Verdict and next step

**TRIAL, gated on legal.** ReSim is the most technically relevant world model in this batch for roboticarray: its action interface (`[x, y, heading]` x 8) maps onto Alpamayo's trajectory output with a trivial adapter, it trains on NavSim which we can already index, and it is the only model here explicitly designed to remain reliable under non-expert behaviour — the regime where policy evaluation actually matters. Two things hold it back from ADOPT. First, the weights fall under the CogVideoX License, which makes commercial use contingent on registering with a third party under PRC law and caps usage; that needs a legal answer before any engineering investment, and it is why the score sits below 3. Second, the released checkpoint is expert-only, so the headline capability is not yet downloadable. Concrete next step: while legal reviews `MODEL_LICENSE`, spend a few days writing the Alpamayo-trajectory-to-`traj_fut` adapter and running the expert-only checkpoint on the shipped `nus_val_4k.json` to measure actual VRAM and seconds-per-round (both undocumented), then re-evaluate when the CARLA checkpoint lands. Convert the `.pt` weights to safetensors on first download and load everything with `weights_only=True` in our fork.
