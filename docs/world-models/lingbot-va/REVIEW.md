## What it is

LingBot-VA is Ant Group's Robbyant team's **autoregressive video-action world model**: a dual-stream Mixture-of-Transformers built on a Wan2.2 backbone that interleaves video-latent tokens and action tokens in a single causal sequence, so the model predicts visual dynamics and infers actions as one autoregressive process rather than two heads on a shared trunk. The causality is real and implemented, not rhetorical — `wan_va/modules/model.py:160-196` builds block-causal attention masks (`block_causal_mask` and a `block_causal_mask_exclude_self` for the noise-to-clean path), and `WanAttention.init_kv_cache` / `create_empty_cache` (`model.py:345,661-667`) maintain a sliding KV cache sized as `(attn_window // 2) * latent_token_per_chunk + (attn_window // 2) * action_token_per_chunk`. That, plus asynchronous execution, is what lets it run a control loop instead of regenerating a clip per step. The action interface is the most expressive in this batch: a **30-dimensional slot layout** — left EEF 7, right EEF 7, left joints 7, right joints 7, two grippers — with a per-embodiment `used_action_channel_ids` selector and its precomputed inverse, so LIBERO uses channels 0-6, Franka a different subset, and RoboTwin a bimanual EEF+gripper subset, all against the same tensor. Four embodiment configs ship (`robotwin`, `libero`, `franka`, `demo`), data is native LeRobot with pre-extracted Wan2.2 VAE latents, and deployment is a server/client split over the openpi msgpack websocket protocol. Reported results are state of the art: **RoboTwin 2.0 92.9% easy / 91.6% hard** over 50 tasks (against Motus at 88.7/87.0 and π0.5 at 82.7/76.8), **LIBERO 98.5% average**, plus real-robot results on six tasks including deformables (fold clothes, fold pants) from only 50 trials per task.

## Security findings

- `wan_va/dataset/lerobot_latent_dataset.py:145` — `torch.load(config.empty_emb_path, weights_only=False)`, **explicitly opting out** of the safe path. `empty_emb_path` resolves to `<dataset_path>/empty_emb.pt` (`wan_va/configs/va_robotwin_train_cfg.py:10` and the two siblings), i.e. **a pickle that ships inside the Hugging Face dataset you are told to download**. This is the same shape of risk as OpenDWM's `blank_code.pkl`: a distributed artifact that is unpickled by design. Inspect it with `pickletools` or regenerate it locally before any training run.
- `wan_va/dataset/lerobot_latent_dataset.py:219` — `torch.load(latent_file, weights_only=False)` on every `episode_*.pth` latent file. These are generated locally by the documented VAE-extraction step, but the same call reads the pre-extracted latents bundled in the HF datasets. A latent cache is therefore executable content; do not accept one from outside the team.
- `wan_va/train.py:405` — `torch.load(training_state_path, map_location='cpu', weights_only=False)` for resume. Expected for optimizer state, but worth knowing that a shared checkpoint directory is a code-execution vector.
- `evaluation/robotwin/eval_polict_client_openpi.py:682` — `value = eval(value)` inside `parse_override_pairs`, wrapped in a bare `except: pass`. Every `--key value` override pair on the evaluation client's command line is passed through `eval`. It is CLI-supplied so the blast radius is small, but it is a genuine `eval` of user input inside a `try/except` that swallows everything, and any script or CI job that builds that command line from a config file widens it. Replace with `ast.literal_eval`.
- `wan_va/configs/shared_config.py:7-8` — `host = '0.0.0.0'`, `port = 29536`. The inference server binds all interfaces with no authentication; the README notes only that server and client "must be deployed on the same machine". Bind to localhost.
- **Good**: all model weights are **safetensors** (sharded) on Hugging Face — no pickled checkpoints, unlike Motus, opendw and Ctrl-World. The wire protocol is msgpack, and `evaluation/robotwin/msgpack_numpy.py:4` explicitly documents the choice as "secure (as opposed to pickle/dill/etc which allow for arbitrary code execution)". No `os.system`, no `trust_remote_code`, no curl-pipe-sh, no tokens or credentials. The one `subprocess.Popen` (`eval_polict_client_openpi.py:511`) is an ffmpeg pipe with list argv, no shell.
- Dependency hygiene is mixed but better than most here: `requirements.txt` pins `torch==2.9.0`, `torchvision==0.24.0`, `diffusers==0.36.0`, `transformers==4.55.2`, `numpy==1.26.4`, `lerobot==0.3.3` exactly, while `accelerate`, `einops`, `easydict`, `flash_attn`, `safetensors` and others float. `pyproject.toml` disagrees with `requirements.txt` on the transformers pin (`>=4.55.4` vs `==4.55.2`). No lockfile.
- `INSTALL.md` instructs `pip install git+https://github.com/Dao-AILab/flash-attention.git` — an unpinned VCS install — as a fallback.

## Physics and dynamics

- **Action space (in and out)**: a fixed **30-D layout** documented in the README and enforced in the configs — left arm EEF 7, right arm EEF 7, left arm joints 7, right arm joints 7, left gripper 1, right gripper 1, with unused dimensions zero-padded. Which channels are live is a per-embodiment config list: RoboTwin uses `range(0,7) + [28] + range(7,14) + [29]` (both EEF poses plus both grippers, `va_robotwin_cfg.py:33`), LIBERO uses `range(0,7)` (`va_libero_cfg.py:33`), Franka a third subset. The inverse mapping is precomputed in the config. This is the only interface reviewed that carries **both** EEF and joint representations in the same vector, which matters for us because Isaac Lab can emit either and different platforms want different ones.
- **Normalisation**: quantile-based (`action_norm_method = 'quantiles'`) with q01/q99 statistics **hardcoded into the config source** (`va_robotwin_cfg.py:43-56`). The 2026-04-24 release note warns in bold that `action_snr_shift`, `used_action_channel_ids` and `norm_stat` must be kept in sync with the checkpoint — a silent-failure hazard.
- **Causal structure**: block-causal attention with two mask variants (clean-to-clean and noise-to-clean-excluding-self, `model.py:160-196`), a sliding `attn_window` (72 chunks for RoboTwin, 30 for LIBERO and Franka) and a per-block KV cache. `frame_chunk_size = 2`. This is what distinguishes it from the clip-at-a-time models in this batch and is the direct source of its efficiency claims.
- **Rates and resolution**: RoboTwin 256x320 with `action_per_frame = 16`; LIBERO 128x128 with `action_per_frame = 4`; Franka 224x320 with `action_per_frame = 20`. So the video stream runs at a low frame rate while actions are emitted at 4-20x that rate — the same decoupling Motus does with `video_action_freq_ratio`, but here it is per-embodiment. Sampling: `num_inference_steps = 25` for video, `action_num_inference_steps = 50` for actions, `guidance_scale = 5`, `action_guidance_scale = 1` (CFG effectively off for actions). Training latents are extracted at ~256x256 and 5-15 fps.
- **Evaluation**: closed-loop success rate on two physics simulators plus real hardware — the strongest evaluation package in the batch. RoboTwin 2.0: 92.9% easy / 91.6% hard averaged over 50 tasks, explicitly beating Motus (88.7/87.0), π0.5 (82.7/76.8), X-VLA (72.9/72.8) and π0 (65.9/58.4). LIBERO: 98.5 ± 0.3 spatial, 99.6 ± 0.3 object, 97.2 ± 0.2 goal, 98.5 ± 0.5 long, 98.5 average, **with error bars**, which nobody else here provides. Real world: six tasks across long-horizon (Make Breakfast, Pick Screws), precision (Insert Tube, Unpack Delivery) and deformable/articulated (Fold Clothes, Fold Pants), scored on both Progress Score and Success Rate at 50 trials per task, against a π0.5 baseline.
- **Known failure modes**: not documented as such, but three are visible in the code. The `attn_mode` in `transformer/config.json` must be manually flipped between `"flex"` (training only) and `"torch"`/`"flashattn"` (inference only) — the README warns in bold that the wrong value errors out. The norm-stat/channel-id/SNR-shift triple must match the checkpoint or actions are silently wrong. And the sliding window means anything older than `attn_window` chunks is gone, so "long horizon" means long *within* a bounded context.

## Motion-control assessment

This is the model in the batch that most looks like a product. It emits controls and video from one causal sequence, it has a KV cache and asynchronous execution because someone cared about control rate rather than clip throughput, it ships an openpi-compatible websocket policy server, it has been deployed on real hardware for six tasks including deformables, and its numbers beat every baseline it lists including Motus. The weights are Apache-2.0 safetensors.

For Isaac Lab, the integration is the cleanest here because the deployment architecture is already a **server/client split over a network**, chosen — as the README says — specifically so the model environment and the simulation environment do not have to share a Python environment. That is exactly our problem: Isaac Lab drags in a heavy, opinionated dependency stack that does not coexist happily with a diffusion-model environment. The work is to write an Isaac Lab client mirroring `evaluation/libero/client.py` or `evaluation/robotwin/eval_polict_client_openpi.py`: pack observations (camera RGB per `obs_cam_keys`, robot state) into msgpack, call `websocket_client_policy`, receive an action chunk, apply it. No adapter layer is needed on the action side, because the 30-D layout already has slots for both joint positions and EEF poses — we pick the `used_action_channel_ids` that match our platform and regenerate the quantile stats.

Two further things make it a good fit. First, the four shipped embodiment configs are a worked demonstration that adding a robot is a config file, not a fork: `va_franka_cfg.py` differs from `va_libero_cfg.py` in resolution, camera keys, `action_per_frame` and channel selection, and nothing else. Second, LeRobot-native data means our own recordings and Isaac rollouts go in through a standard, documented path — convert to LeRobot, add `action_config` segments to `episodes.jsonl`, extract Wan2.2 VAE latents into `latents/`, train.

What is missing or needs care. The released post-training datasets are **CC BY-NC-SA 4.0**, so we must fine-tune on our own data; that is fine operationally but it also raises the question of whether the Apache-2.0 post-trained checkpoints are consistent with the share-alike terms of the data underneath them — worth a legal read before shipping a derivative of `lingbot-va-posttrain-robotwin`. The `lingbot-va-base` checkpoint's own training data provenance is not documented at all. The packaging is sloppy enough (`pyproject.toml` points at a nonexistent `lingbot_va` package while the code lives in `wan_va`; `INSTALL.md` is unedited Wan2.2 boilerplate down to a stray French sentence) that `pip install .` does not do what it looks like it does. And as with everything else here, it is manipulation only — nothing for Alpamayo or AlpaSim.

## Extensibility

- **New embodiment**: copy `wan_va/configs/va_franka_cfg.py` and set `height`, `width`, `obs_cam_keys`, `action_per_frame`, `attn_window`, `env_type`, and `used_action_channel_ids` (the inverse map is computed in the file). Then regenerate `norm_stat` quantiles with `evaluation/robotwin/calc_stat.py`. Four working examples ship.
- **New action space**: use the existing 30-D slots. EEF (7+7), joints (7+7) and grippers (1+1) are all already there; a new robot is a choice of channels, not a new representation. A space that does not fit those slots (torque, wheel velocity, a >14-DoF humanoid) would need the layout widened, which is a retrain.
- **New dataset**: LeRobot v0.3.3 format, plus two additions documented in detail in the README — an `action_config` list of `{start_frame, end_frame, action_text}` segments appended to each line of `meta/episodes.jsonl`, and a `latents/` tree mirroring `videos/` containing `episode_{idx}_{start}_{end}.pth` files whose exact field schema (`latent`, `latent_num_frames`, `text_emb`, `frame_ids`, `fps`, ...) is tabulated. A converted example dataset is linked from Issue #29. This is the best-documented custom-data path in the batch.
- **New camera**: `obs_cam_keys` is a plain list of LeRobot observation keys; RoboTwin uses three, LIBERO two.
- **Coupling hotspots**: `attn_mode` must be hand-edited in the *downloaded checkpoint's* `transformer/config.json` between training and inference — an out-of-band, undiscoverable state. The `norm_stat` / `used_action_channel_ids` / `action_snr_shift` triple is checkpoint-specific and lives in source, with an explicit upstream warning about desynchronisation. `wan22_pretrained_model_name_or_path = "/path/to/pretrained/model"` placeholders in every config. `pyproject.toml`'s `packages = ["lingbot_va"]` does not match the `wan_va/` directory, so an editable install silently installs nothing useful.

## Hardware and cost

Better documented than most, and unusually honest about offload. **RoboTwin single-GPU evaluation: ~24 GB VRAM** with offload enabled (VAE and text encoder moved to CPU). **Image-to-video-action generation: ~18 GB** under the same conditions. Without offload, expect the full bundle resident: ~10.2 GB transformer + ~11.4 GB umT5-XXL text encoder + 2.8 GB VAE in bf16, so 40 GB+. `enable_offload` is a config flag (`shared_config.py:15`, default `False` — turn it on). Training is FSDP across `NGPU=8` (`script/run_va_posttrain.sh`), with the README recommending a global batch size of 32-64 and `gradient_accumulation_steps` as the fallback for smaller clusters. Multi-GPU evaluation pads the 50 RoboTwin tasks to 56 and shards them into 7 groups for an 8-GPU node. **No wall-clock latency or control frequency is published**, which is the one number a model with a KV cache and "asynchronous execution" in its headline claims really ought to state — measure it first.

## Verdict and next step

**ADOPT.** LingBot-VA is the strongest world-action model in this batch on the dimensions we care about: it produces controls and video from a single causal autoregressive sequence with a real KV-cache implementation aimed at control-rate inference, its weights are Apache-2.0 **safetensors** (the only permissively-licensed non-pickle checkpoints reviewed), its 30-D action layout with per-embodiment channel selection is the most expressive interface here because it spans EEF and joint spaces at once, and its reported results lead every baseline it names — including Motus, which is the other ADOPT in this batch — across two simulators and real hardware with deformable objects. The server/client deployment split is precisely the architecture that makes an Isaac Lab integration tractable without fighting dependency hell. The caveats are real but bounded: the released post-training data is CC BY-NC-SA 4.0 so we must bring our own; `empty_emb.pt` and the latent caches are unpickled with `weights_only=False` by design; there is an `eval()` on CLI overrides; the server binds `0.0.0.0`; and the packaging and install docs are careless enough to cost a day. Concrete next step, about four weeks: (1) reproduce a RoboTwin 2.0 task group with `lingbot-va-posttrain-robotwin` on a 24 GB card with offload on, confirming both the success rate and — the number upstream never gives — the achieved control frequency; (2) write an Isaac Lab websocket client modelled on `evaluation/libero/client.py` and drive the policy against an Isaac scene, using `used_action_channel_ids` to select joint-position channels rather than EEF; (3) build a roboticarray LeRobot dataset with `action_config` segments and Wan2.2 latents and post-train `lingbot-va-base` on one of our embodiments, which is the real test of whether the 30-D slot layout absorbs a new robot as cheaply as the four shipped configs suggest. On day one of the fork: regenerate `empty_emb.pt` locally, replace the `eval()` at `eval_polict_client_openpi.py:682` with `ast.literal_eval`, bind the server to localhost, fix `pyproject.toml` to package `wan_va`, delete `INSTALL.md`, and write down the `attn_mode` flip in a place someone will actually read.
