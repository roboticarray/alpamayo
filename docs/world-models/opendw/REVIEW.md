## What it is

DW05 is Dexmal's **world-action model**: a Mixture-of-Transformers built on a Wan2.2 video backbone with three expert heads — video, action, and (announced but not yet released) state-value. It takes language, image or video, robot type, proprioceptive state and actions, and jointly produces **future video and an action chunk**, so it is a simulator and a policy in one checkpoint rather than an action-conditioned renderer. The most interesting engineering choice for a multi-embodiment company is the action interface: everything is padded to a **32-dimensional universal action/proprio space** with an accompanying `action_dim_mask` and a configurable source-index rearrangement (`dexbotic/data/dataset/dw05/transform/action.py:13-94`), so a 14-D bimanual ALOHA and a 7-D single arm occupy the same tensor slot. Data arrives as RobotWin-style **JSONL episode annotations**, one line per frame, referencing up to three camera streams by URL (local or remote via `megfile`), with cached text embeddings and a `norm_stats.json`. The repo ships genuinely broad runtime surface: open-loop image rollout, action-conditioned JSONL inference, a **RoboTwin 2.0 closed-loop policy adapter** with single-task and multi-task launchers, a **WorldArena** world-model benchmark rollout, a FastAPI **real-robot HTTP service**, and a 2.9 k-line interactive web demo with ALOHA-Tracer and ARX5 URDFs (one of them an Isaac-flavoured variant). What it does not ship is any numbers: no benchmark results appear anywhere in the repository.

## Security findings

- `dexbotic/model/dw05/dw05_core.py:541`, `dexbotic/model/modules/wan22/wan22.py:367`, `dexbotic/model/dw05/modules/action_expert.py:145` — `torch.load(path, map_location="cpu")` with **no `weights_only`**, applied to the published checkpoint bundle. Upstream ships `model.pt` (12 GB), `text_encoder/model.pth` (11 GB) and `vae/model.pth` (2.8 GB) as pickles with **no safetensors alternative**, so ~26 GB of downloaded pickle passes through these calls. Under `torch>=2.6` (the declared floor) the default is `weights_only=True`, which saves it — but the dependency is `torch>=2.6.0` with no upper bound and no explicit flag, so the safety is implicit.
- `dexbotic/policy/dw05_policy.py:109` — `torch.load(..., map_location="cpu", mmap=True)`, same gap, on the deployment path.
- `dexbotic/data/dataset/dw05/transform/text.py:245,296` — `torch.load` on cached **text-embedding** files. These are dataset artifacts that a team might share around informally; treat a text-embedding cache as executable content.
- `hardware/dw05/real_robot_server.py:276` — `uvicorn.run(app, host="0.0.0.0", port=int(_env("SERVER_PORT", 8000)), workers=1)`. The real-robot inference service binds all interfaces with **no authentication, no TLS, no rate limiting**, and accepts `UploadFile` images plus a free-text state string. `playground/online_demos/robotwin_online_demo.py:2716,2890` does the same for the web demo (`--host` defaults to `0.0.0.0`). Anything that can reach the port can command the robot. Put both behind a reverse proxy on a private network, or change the bind to `127.0.0.1`.
- `pyproject.toml` — `torch>=2.6.0`, `transformers>=4.49.0`, `accelerate>=1.10.0`, `deepspeed>=0.18.0`, `omegaconf>=2.3.0`, `hydra-core>=1.3.0` are open-ended ranges; only `numpy==1.26.4`, `boto3==1.35.18`, `botocore==1.35.66` are exact. No lockfile. `megfile`, `modelscope` and `boto3` mean the data layer can reach out to S3-compatible and ModelScope endpoints — audit `DW_LOCAL_MIRROR_PREFIXES` and the path-prefix overrides before pointing this at production storage.
- **Good practice worth noting**: `dexbotic/model/modules/wan22/helpers/io.py:140` does use `weights_only=True`; `playground/online_demos/robotwin_online_demo.py:817-819` explicitly passes `np.load(p, allow_pickle=False)`; every `subprocess.Popen` (`eval_dw05_manager.py:152`, `eval_dw05_single.py:153`, `robotwin_online_demo.py:2249,2696`) uses list argv with no `shell=True`. No `eval(`/`exec(`, no `os.system`, no `trust_remote_code`, no curl-pipe-sh, no tokens or credentials in the tree.
- The HF model card instructs users to `git clone https://gitlab.dexmal.com/robotics/dexbotic-open.git` — a **private GitLab** that will 404 for outsiders. Use this GitHub repo instead; it vendors the runtime in "Dexbotic-native form" per `docs_dw05_runtime.md`. Worth knowing before anyone wastes an hour on it.

## Physics and dynamics

- **Action space**: a **32-dimensional universal action vector**, with proprioception also at 32-D, both zero-padded from the native embodiment dimension by `PadToNDim(ndim=32)` (`dexbotic/data/dataset/dw05/transform/action.py:82-94`) and accompanied by an `action_dim_mask` so the loss and the model know which channels are real (`action.py:13-36`). A configurable source-index rearrangement maps arbitrary robot state layouts into fixed slots. For RobotWin the native space is 14-D bimanual joint position (`split_state_action(qpos)` in `playground/benchmarks/worldarena/eval_dw05.py:103`), and normalisation offers `zscore_14d` or `dw05_quantile` (q01/q99) modes (`--normalization-mode`, `transform/action.py:343-349`). This is the most deliberately cross-embodiment action interface in the batch and the single most reusable idea in the repo.
- **Action output**: yes. `action_horizon` defaults to **32** (`dexbotic/exp/base_dw_exp.py:237`), and `script/dw/infer_aloha_joint.py` writes `pred_action.pt` alongside the generated video. The trainer enforces that the action horizon is divisible by `num_video_frames - 1` (`dexbotic/exp/dw05_trainer.py:81-86`), i.e. actions and video frames are locked at an integer ratio — so a 9-frame video with a 32-action horizon means 4 actions per generated frame.
- **Horizon / resolution / fps**: `num_frames: 9`, `fps: 8`, `num_inference_steps: 10` (`base_dw_exp.py:236-241`); the JSONL inference example runs `--num-video-frames 9 --action-horizon 32 --num-inference-steps 4`. That is roughly **one second of imagination per call** — short, like Motus. Resolution is not fixed in config: `image_size` is optional and `dw05_policy.py:133-189` aspect-preserves and tiles up to three camera views into one canvas at runtime.
- **Conditioning**: language (via cached uMT5 embeddings), image or video history (`dw05_history.py`, 722 lines), robot type, state, proprio, and action. The `worldmodel.caption` / `robot.prompt` split in the JSONL schema lets one episode serve both world-model and action training, flagged per-sample by a `type` list containing `action`, `wm`, or both.
- **Evaluation**: two harnesses ship and neither reports a number. `playground/benchmarks/robotwin2/` drives closed-loop RoboTwin 2.0 with single-task and multi-task GPU-sharded launchers; `playground/benchmarks/worldarena/eval_dw05.py` runs the WorldArena world-model benchmark by reading first frames and ground-truth qpos from held-out episodes and generating the predicted future. The absence of any published score — no success rate, no FID, no action MSE — is the biggest gap in an otherwise well-built repo, and it means we would be reproducing blind.
- **Known failure modes**: not documented. The `NOTICE` does say users are "responsible for evaluating safety, robustness, and legal suitability before redistribution, real-robot deployment, or commercial use", which is honest but not informative. The value expert — the component that would let the model reason about whether an action sequence is *good* rather than merely *likely* — is explicitly deferred to a later release.

## Motion-control assessment

DW05 is the best structural match in this batch for a company that runs more than one embodiment. The 32-D padded action space with a dimension mask is exactly the abstraction we would otherwise have to invent: one checkpoint, one tensor shape, many robots, with the mask carrying the truth about which channels mean anything. Combined with Apache-2.0 weights and a `NOTICE` that actually tracks upstream attribution, this is the repo a commercial robotics team can build on without a lawyer in the loop.

The Isaac Lab path runs through the data schema rather than through a simulator adapter, and that is a feature. DW05 eats **JSONL episode annotations** whose fields are trivially emittable from an Isaac Lab rollout: per-frame camera URLs (`images_1/2/3`, configurable via `data_config.images_keys`), `robot.state`, `robot.prompt`, an action trajectory, a `worldmodel.caption`, and `robot_task_success`. Writing an Isaac Lab exporter that produces that JSONL is a contained job, and it immediately gives us three things — fine-tuning DW05 on our own embodiments, a WorldArena-style measurement of how well it predicts Isaac's own dynamics, and (via `norm_stats`) a principled normalisation for our action spaces. For closed-loop evaluation, `playground/benchmarks/robotwin2/dw05_policy/deploy_policy.py` plus `eval_dw05_single.py` is the template: the policy adapter is already separated from the benchmark launcher, so substituting an Isaac Lab environment means reimplementing one `eval(TASK_ENV, model, observation)` function.

For real deployment there is more here than anywhere else reviewed: `hardware/dw05/real_robot_server.py` is a FastAPI service that accepts multipart camera images plus a state string and returns actions, i.e. the same over-the-wire pattern as openpi's websocket server but over HTTP. That is directly reusable as the shape of a roboticarray inference endpoint — after fixing the `0.0.0.0` bind and adding auth.

What is missing for us. No published results, so the model's actual competence is unknown and a reproduction is a prerequisite to any decision. One-second horizons mean this is a short-horizon dynamics model, not a long-rollout simulator; anything longer is autoregressive and unevaluated. The value expert, which is the part that would make this a planner rather than a policy, is not released. And as with everything else in this batch, there is no driving, no ego-vehicle, no map — nothing that touches Alpamayo or AlpaSim directly. The transferable assets are the action interface, the JSONL schema, and the serving pattern.

## Extensibility

- **New embodiment**: set the action/proprio source indices and rely on `PadToNDim(32)` + `action_dim_mask`. No architecture change, no retraining of the interface — this is what the 32-D space is for. Recompute `norm_stats.json` with `python playground/example_dw_exp.py --compute-norm-stats ...`, which is a first-class documented entrypoint.
- **New dataset**: emit RobotWin-style JSONL (one line per frame) and point `data_config.annotations`, `data_path_prefix`, `index_path_prefix`, `text_embedding_cache_dir`, `norm_stats_path` at it, either via env vars (`DW05_ROBOTWIN_*`) or CLI dotted overrides. Recipes are registered in `dexbotic/data/dataset/dw05/data_source.py` (`robotwin_baseline` is the built-in), and `megfile` means the media can live on S3-compatible storage with local mirrors via `DW_LOCAL_MIRROR_PREFIXES`.
- **New camera / view count**: `data_config.images_keys` is configurable, and `dw05_policy.py:184-189` composes an arbitrary number of views into one canvas by horizontal or vertical tiling. Fewer assumptions baked in than Ctrl-World (hardcoded 3) or Motus (pre-concatenated 3).
- **New transform**: `dexbotic/data/dataset/dw05/transform/` is a clean pipeline of small composable callables (`action.py`, `normalize.py`, `text.py`, `multimodal.py`, `augmentations.py`, `output.py`), each taking and returning an `episode_data_dict`. Adding a sensor or a label is a new transform plus a recipe entry.
- **New experiment**: subclass `DWExpConfig`/`DWInferenceConfig` in `dexbotic/exp/base_dw_exp.py` (423 lines, well-documented docstrings) and override defaults; `playground/example_dw_exp.py --task {smoke,inference}` with dotted overrides is the entrypoint. The trainer is split into a generic `generative_trainer.py` and a DW05-specific `dw05_trainer.py`, which is the right seam.
- **Coupling hotspots**: the integer-ratio constraint between `action_horizon` and `num_video_frames - 1` (`dw05_trainer.py:81-86`) silently couples the two; the 32-D cap is a hard ceiling (a >32-DoF humanoid needs an architecture change); and `DW05_MODEL_BASE_PATH` / `DIFFSYNTH_MODEL_BASE_PATH` must both be set or model loading fails in confusing ways.

## Hardware and cost

**Nothing is published** — no VRAM table, no GPU count, no latency, no throughput. This is the second significant documentation gap. Inference defaults (`base_dw_exp.py:236-241`) are `bf16`, `device: cuda:0`, `num_inference_steps: 10`, `tiled: False` with a tiling option available, which is the usual lever for fitting a Wan VAE into less memory. Inferred from the artifact sizes: `model.pt` is 12 GB of bf16 weights (~6 B parameters), the uMT5-XXL text encoder is another 11 GB, and the VAE 2.8 GB — so naively loading everything is ~26 GB of weights before activations, putting single-GPU inference in **40-80 GB** territory unless the text encoder is dropped (`load_text_encoder: False` exists as a config field, and cached text embeddings in the dataset exist precisely so it can be). Training defaults to `batch_size: 2` with `gradient_accumulation_steps` and DeepSpeed in the dependency list, implying 80 GB cards. Treat all of this as an estimate and measure it first.

## Verdict and next step

**ADOPT** — as the cross-embodiment world-action base model and, more importantly, as the interface design we copy. DW05 is Apache-2.0 from code through weights through both upstream components, with a `NOTICE` file that shows someone actually thought about downstream commercial use. It is a genuine world-action model — video *and* actions out of one checkpoint — with the best-engineered codebase in this batch: a real package, Hydra-style config overrides, a composable transform pipeline, environment-variable configuration rather than someone's cluster paths, and a serving story that runs from RoboTwin adapter to FastAPI real-robot endpoint. The 32-D padded universal action space with a dimension mask is the single most portable idea reviewed and we should adopt that convention in our own stack whether or not we adopt the model. The caveats are real but tractable: no published results anywhere, no VRAM or latency figures, no tests or CI, the value expert unreleased, ~26 GB of checkpoint shipped only as pickle, and a robot-control HTTP service that binds `0.0.0.0` with no auth. Concrete next step, about three weeks: (1) reproduce `Dexmal/DW05-Robotwin` on the RoboTwin 2.0 benchmark using the shipped `eval_dw05_single.py` and establish the numbers upstream never published, measuring VRAM and per-chunk latency while doing it; (2) write an Isaac Lab → DW05 JSONL exporter and fine-tune `DW05-Base` on a single roboticarray embodiment to test whether the 32-D masked action interface really absorbs a new robot as cheaply as it claims; (3) run the WorldArena harness against Isaac ground truth to get a quantitative read on how well the video expert predicts dynamics we control. On day one of the fork: convert the three checkpoints to safetensors locally, add `weights_only=True` to the five bare loaders, pin every dependency, and bind the robot server to localhost behind an authenticating proxy before it ever sees a real arm.
