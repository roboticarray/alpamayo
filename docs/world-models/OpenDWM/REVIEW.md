## What it is

OpenDWM is SenseTime's driving-world-model *codebase* rather than a single model: one config-driven framework (`src/dwm`) hosting the UniMLVG and MaskGWM papers plus a family of "cross-view temporal SD" (CTSD) pipelines built on Stable Diffusion 2.1 / 3.0 / 3.5. The video models generate **six surround-view camera streams jointly** (`CAM_FRONT_LEFT` through `CAM_BACK_LEFT`) with explicit cross-view and temporal attention (`enable_crossview`, `enable_temporal` on `dwm.models.crossview_temporal_dit.DiTCrossviewTemporalConditionModel`), conditioned on text, projected 3D bounding boxes, HD-map polylines, camera intrinsics/extrinsics, and ego pose. Ego action is not a separate input: `CrossviewTemporalSD.get_action_ids` (`src/dwm/pipelines/ctsd.py:98-156`) derives a per-frame `[speed_kmh, steering]` pair from the 4x4 `ego_transforms` sequence using a hardcoded bicycle model. There is a second, parallel LiDAR world model (VQVAE/VAE + MaskGIT or DiT, layout-conditioned, autoregressive), FID/FVD evaluation wired through `torchmetrics` with results checked into each config's `informations` block, and an experimental **interactive CARLA loop** (`docs/InteractiveGeneration.md`) where CARLA owns the simulation state and OpenDWM renders it as photoreal multi-view video streamed over RTSP. Everything is instantiated from JSON by `_class_name` strings, and there are no tests and no CI.

## Security findings

- `src/dwm/pipelines/lidar_maskgit.py:57` — `torch.load(path, map_location="cpu", weights_only=False)`, explicitly opted out of the safe path. This is the loader for the published LiDAR MaskGIT checkpoints.
- `src/dwm/pipelines/lidar_maskgit.py:257` — `blank_code = pickle.load(f)`. The README instructs you to download `lidar_vqvae_nwa_60k_blank_code.pkl` from Hugging Face and feed it here: **a distributed pickle artifact that is unpickled by design**. There is no safetensors alternative for it. If we use the LiDAR stack, regenerate this file locally rather than downloading it, or vet it with `pickletools` first.
- `src/dwm/common.py:109` — `pickle.loads(self.blob[start:end])` in the blob-backed dataset reader; any `.pkl`-packed dataset blob is executable content.
- `src/dwm/utils/lidar_visualizer.py:201` — `pickle.load(f)` on a dataset info file.
- `src/dwm/pipelines/lidar_vqvae.py:23`, `lidar_vae.py:34`, `unimlvg.py:31` — `torch.load(path, map_location="cpu")` with no `weights_only`, inconsistent with the CTSD pipeline right next door.
- `src/dwm/common.py:133-160` — `get_class` / `create_instance_from_config` resolve arbitrary `_class_name` strings through `importlib` and call them with config kwargs. Every config in `configs/` and `examples/` is therefore executable; the example configs even instantiate `torchvision.transforms.Resize` and `diffusers...BitsAndBytesConfig` this way. Never run a config you did not review.
- `requirements.txt:29` — `git+https://github.com/autonomousvision/kitti360Scripts.git`, unpinned VCS dependency. Four git submodules (`TATS`, `taming-transformers`, `waymo-open-dataset`, `DirectVoxGO`) are pinned by commit in `.gitmodules`/index, which is better.
- **Good news:** `src/dwm/pipelines/ctsd.py:32-34` and `lidar_diffusion.py:38-40` prefer `safetensors.torch.load_file` and fall back to `torch.load(..., weights_only=True)`. The video path we actually care about is the safe one. No `eval(`/`exec(` anywhere in `src/`; the only `subprocess` use is `src/dwm/tools/transcode_video.py:48` calling ffmpeg with a list argv (not shell). No hardcoded tokens found. No `trust_remote_code`.
- Dependency pinning is partial: `accelerate==1.4.0`, `diffusers==0.31.0`, `transformers==4.50.0`, `torchmetrics==1.6.0`, `protobuf==4.21.6`, `av==14.0.0` are exact; ~15 others (`Pillow`, `numpy`, `scipy`, `timm`, `opencv-python`, ...) are floating. No lockfile.

## Physics and dynamics

- **Action space**: the input is a sequence of 4x4 `ego_transforms`. `get_action_ids` (`src/dwm/pipelines/ctsd.py:98`) computes relative poses via `torch.linalg.solve`, then per frame: `speed = 3.6 * ||Δt|| * fps` (km/h) and `steering = atan2(...) / moving_distance * wheel_base * steering_ratio` with **`wheel_base = 2.7` and `steering_ratio = 14` hardcoded at `ctsd.py:141-142`**. So the "steering" the model was conditioned on is a steering-wheel angle for a generic sedan; it is not our vehicle, and for any roboticarray platform with a different wheelbase the number is wrong by a constant factor. An unconditioned frame is signalled by the sentinel `-1000.0` (`ctsd.py:143,151`), which is also what you get when the vehicle is nearly stationary (`|moving_distance| <= 0.01`) — steering is undefined at rest and the model is trained to expect that.
- **Other conditioning**: text prompt (weather, time of day, scene description), projected 3D boxes, HD-map polylines, per-camera intrinsics and extrinsics, plus optional BEV variants (`use_3dbox_bev`, `use_hdmap_bev` in `src/dwm/datasets/preview.py:126-127`). This is the only repo in the batch with real HD-map/layout conditioning.
- **Multi-camera**: six surround views generated jointly with cross-view attention — the only true multi-camera model reviewed. The view list is a config field (`sensor_channels`), and a 3-view reduced model exists for the CARLA streaming demo.
- **Horizon / resolution / fps**: training at `sequence_length: 19` frames, 10 fps, `fps_stride_tuples: [[10, 0.1]]`, resolution 256x448 per view (`torchvision.transforms.Resize` entries in the CTSD configs). Preview/inference runs `sequence_length: 179` with `sequence_length_per_iteration: 19` and `reference_frame_count: 3`, i.e. ~18 s of 6-view video built autoregressively. The DFoT and FIFO-diffusion variants exist specifically to push this further.
- **Evaluation**: FID and FVD through `torchmetrics`, with numbers committed into each config's `informations` block (e.g. `fid: 9.46`, `fvd: 91.55`, `fvd_on_nusc_by_3_ref_frames: 38.83` for `ctsd_35_tirda_bm_nwao`). This is genuinely good practice and better documented than any other repo here. But FID/FVD measure appearance, not dynamics: there is **no** controllability metric, no collision check, no trajectory-following error.
- **Known failure modes**: the interactive demo's own "Known issues" list is honest — generation speed and denoising-queue latency (the demo streams at `--fps 2`). Long autoregressive rollouts inherit reference-frame drift. Steering conditioning degenerates at low speed. Off-resolution inference is constrained by `pos_embed_max_size: 384`.

## Motion-control assessment

OpenDWM is the best architectural fit for roboticarray's stack, for a reason that has nothing to do with its action encoder. The CARLA interactive setup (`docs/InteractiveGeneration.md`, `src/dwm/streaming.py`, `src/dwm/utils/carla_simulation.py`) is a complete worked example of the pattern we actually want: **the simulator owns physics and state, the world model owns photorealism.** CARLA maintains the ego car, traffic and collisions; `streaming.py` pulls layout (boxes, map), camera parameters and ego pose out of it each tick and renders multi-view video; the video goes out over RTSP. Swap CARLA for Isaac Sim or Unreal and the same three interfaces apply — box list, map polylines, ego pose + camera rig — all of which Isaac Sim can emit natively. That gives us a genuine closed loop (Isaac for dynamics and collision truth, OpenDWM for sensor realism) without pretending a video model knows physics, and it directly addresses the sim-to-real appearance gap in AlpaSim.

For Alpamayo specifically: the model consumes ego *poses*, not waypoints, which is a slightly better match than either OpenDriveLab repo. Alpamayo-R1's `ActionSpace.action_to_traj` returns `traj_future_xyz (..., T, 3)` **and** `traj_future_rot (..., T, 3, 3)` — precisely the translation and rotation needed to assemble the 4x4 `ego_transforms` that `get_action_ids` expects. The adapter is a pose-composition, not a lossy projection, and `alpamayo_r1.geometry.rotation` already has the rotation helpers. It is also the only model here that generates all six cameras, so its output could in principle be fed **back into** Alpamayo, whose input is multi-camera — that closes a loop the other three repos cannot.

Caveats. First, the hardcoded `wheel_base = 2.7` / `steering_ratio = 14` means the conditioning is calibrated to a generic passenger car; for a different platform you either accept the mismatch or retrain. Second, at 256x448 per view the fidelity is well below what a perception stack expects — this is a research resolution. Third, speed: the interactive demo runs at 2 fps and lists generation speed as a known issue, so real-time closed-loop is out of reach today; batch/offline evaluation is the realistic mode. Fourth, the LiDAR models are layout-conditioned only, not ego-action-conditioned, so the multi-modal story is weaker than it looks.

## Extensibility

- **New dataset**: implement a `torch.utils.data.Dataset` under `src/dwm/datasets/` following the documented contract (`src/dwm/datasets/README.md`) and reference it by `_class_name` in a config. nuScenes, Waymo, Argoverse, KITTI-360, OpenDV and CARLA packages already share this interface, and `dwm.datasets.common.DatasetAdapter` composes them. `src/dwm/fs` adds fsspec-based access to ZIP blobs and S3, which matters if our data is not on local disk.
- **New sensor / view**: `sensor_channels` is a plain config list; the cross-view attention is built over whatever views you name. This is the only repo here where adding a camera is not a rewrite (retraining still required, but the code does not assume six).
- **New conditioning signal / action space**: conditions are assembled in `CrossviewTemporalSD.get_conditions` (`src/dwm/pipelines/ctsd.py:158+`); `get_action_ids` is a `@staticmethod` taking `batch` and `common_config`, so substituting our own action derivation (correct wheelbase, or direct waypoints) is a contained change. The `-1000.0` sentinel convention must be preserved.
- **New model or pipeline**: `src/dwm/pipelines/` holds one class per training regime (ctsd, unimlvg, lidar_vae, lidar_vqvae, lidar_maskgit, lidar_diffusion); `src/dwm/metrics/` holds torchmetrics classes. Both are selected by `_class_name`. This is a real plugin architecture, not a fork-and-edit codebase.
- **Coupling hotspots**: the hardcoded vehicle constants at `ctsd.py:141-142`; `pos_embed_max_size: 384` and the per-config `Resize` entries tie resolution to the checkpoint; the shipped example configs contain the author's absolute paths (`/mnt/afs/user/wuzehuan/...` in `examples/ctsd_35_6views_video_generation_with_layout.json`) and must be rewritten before anything runs; multi-stage training requires manually threading the previous stage's checkpoint path into the next config.

## Hardware and cost

Documented, unusually clearly, in the README: **32 GB** (e.g. V100) for multi-view *image* or short video (<= 6 frames per iteration), **80 GB** (A100/H100) for multi-view long video (6-40 frames per iteration) — for both training and testing. The default 6-view, 19-frame configs therefore need an 80 GB card. The CTSD 3.5 configs enable `bitsandbytes` quantisation of the text encoder (`BitsAndBytesConfig` in the example config) to claw back memory. The interactive CARLA setup recommends an A100 for the server and uses a deliberately shrunk model (reduced size, view count and resolution) — and still streams at only 2 fps, which is the clearest speed datapoint in the repo. No other wall-clock figures are given. Training throughput is implied by `average_total_batch_sizes: 96` at 40k steps in the config `informations`, i.e. a multi-node run. LiDAR temporal inference examples are launched with `torch.distributed.run --nproc-per-node 2`, so two GPUs there.

## Verdict and next step

**ADOPT, scoped.** OpenDWM is MIT-licensed with Apache-2.0 weights, is the only reviewed model that generates all six cameras jointly, the only one with HD-map and 3D-box layout conditioning, and the only one that ships a working example of a simulator-in-the-loop architecture. That combination maps onto roboticarray's stack better than anything else in this batch — not as a replacement for Isaac Sim, but as the neural rendering layer on top of it. The scope matters: adopt it as a layout-conditioned multi-view data generator and appearance-domain-randomisation tool, and treat its action conditioning as approximate (the bicycle-model constants are not our vehicle). Concrete next step: reproduce `ctsd_35_6views_video_generation_with_layout` on the shipped `carla_town04_package`, then write an Isaac Sim exporter that emits the same `data.json` schema `dwm.datasets.preview.PreviewDataset` reads (boxes, HD-map polylines, camera transforms, ego poses) — if an Isaac scene renders through CTSD, we have a photoreal sensor layer for AlpaSim, and the Alpamayo-pose-to-`ego_transforms` adapter is then a few lines on top. Before touching the LiDAR stack, deal with `blank_code.pkl`: regenerate it locally rather than unpickling a downloaded artifact. Budget an 80 GB GPU and do not expect real time.
